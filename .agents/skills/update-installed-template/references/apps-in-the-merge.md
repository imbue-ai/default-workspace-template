# The apps a template update brought

Checks for the merged worktree (`$WT`), before its boot check: one for an app
from an older template, and one for an app that has a record.

## An app from an older template

An app from an older template (one that is a root workspace member in the
template's layout, with no `uv.lock` of its own) needs converting to a
standalone project with `uv run --no-sync user-package-migration migrate`,
once the root venv is synced
(`.agents/shared/references/python-packaging-migration.md`, "A user app,
service or lib"); until then it fails to start. When resolving a conflict in
the root `pyproject.toml`, keep this workspace's explicit `members` list,
never the template's globs.

## An app with a record

A template carries each app its publisher's workspace built as ordinary
files, with the app's record (`system/config/apps/<name>.toml`) and its
generated program files. Run
`uv run --no-sync app-install --repo-root "$WT" check` from the repo root
(the merged worktree has no environment of its own to run it from).
`inconsistent` names each problem.

- **Two apps on one port** is settled by
  `uv run --no-sync app-install --repo-root "$WT" regenerate`, which moves
  the app whose record is newer and rewrites its program file. Commit what it
  lists under `changed_paths` in the worktree: the landing takes the
  worktree's commit and then removes the worktree, so an uncommitted change
  is left behind.
- **A conflict** is resolved in `/home/user/workspace`, with the user, like
  any other conflict of the merge. There, a conflict in a generated file (a
  program file under `system/supervisord.conf.d/` that begins "Generated by
  app-install", or a skill link) is never resolved by hand: take either side,
  then `uv run --no-sync app-install regenerate` writes what the merged
  manifest and record call for.
- **A conflict in a record itself** is this workspace's to keep (its port,
  its repositories), with only what the newer version changed about the app
  taken from the template.
