Workers are cleaned up at every level of a dispatch: a lead destroys a worker after merging it (or after `no-update-needed`), stops it after a failure, and never leaves a process running for a worker it is done with. The old rule for intermediate leads ("stop, never destroy") existed only so the eval capture could read a sub-worker's reports out of its lead's work dir; mngr already preserves every destroyed agent's transcript, so destroying loses nothing the capture reads.

The launcher carries the whole lifecycle. `launch` labels each worker `runtime_dir=<repo-relative runtime dir>` beside `lead_agent`, and a `mngr create` that fails because the name is taken now says which agent holds it, in what state, under which lead, and that `create_worker.py destroy --name <name>` frees it. `destroy` is recursive by default: one `mngr list` resolves the subtree, and before each agent is destroyed (deepest first, the root last) the runtime dirs of the workers it dispatched are pulled out of its worktree into the caller's tree at the same paths (`mngr rsync <agent>:data/.tasks/ ./data/.tasks/ ... -- --update --exclude=/<its own runtime dir>`), which carries even the runtime dirs of sub-workers a lead had already destroyed itself; unmerged commits and dirty worktrees are printed as warnings rather than refusals, `--delete-branches` adds `-b` for a superseded pass, `--no-recursive` names the children it leaves behind, and one outcome line per agent plus a non-zero exit report a partial failure. A new `stop` subcommand stops a subtree with `mngr stop --archive`, so a STOPPED worker carrying `archived_at` is one its lead stopped on purpose and dead-worker-recovery's restart advice applies only to the unlabelled ones. `launch-sync` reports `destroy_failed` in its result JSON and exits non-zero when its destroy left something behind.

Prose follows: `lead-proxy.md` ends `done` and `no-update-needed` with the destroy and `stuck` with the stop, and the intermediate-lead rule reads "destroy after merge, stop on failure"; `worker-failure.md` stops the worker as its step 3; `dead-worker-recovery.md` scopes the restart path to unarchived workers and salvages through the launcher's destroy; `harden-contention.md` supersedes with one `destroy --delete-branches` line; `harden-creation.md` names sibling sub-workers with the worker's own name as prefix; the crystallize, update, heal, and update-system-interface skills place the destroy between the merge and go-live.
