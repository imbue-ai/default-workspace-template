The `connect-external-service` skill now routes an MCP server through latchkey instead of through the workspace's own MCP client or a harness's MCP config.

A hosted server is a custom latchkey service: its OAuth sign-in goes through latchkey's new `mcp` login flow (sent as the `login` object of a `custom-service` permission request: the authorization endpoint as the login URL, and the MCP endpoint plus the token and registration endpoints its `/.well-known/oauth-authorization-server` publishes as the parameters), and a server that takes a key in a header is an ordinary custom service on the endpoint's domain. Either way the credential stays in Imbue Studio's credential store, the gateway attaches it and refreshes the token, and the connection is there for every chat, app and scheduled job. The server is then called as a JSON-RPC API through `latchkey curl`, the way latchkey's builtin `*-mcp` services already are. The scopes are fixed at sign-in and nothing adds one later, so the agent asks for broad scopes up front; a scope found missing afterwards means asking the user to disconnect the service and setting it up again.

A server published as a package to run in the workspace is no longer a way to reach a service: it only calls the service's API with a key, so the skill sends the agent to that API (a custom latchkey service, or the direct API with a key from the secret card) instead of running a stranger's code with the workspace's access. With that, `mcpc`, `mcp-servers.json` and `mcpc login` are gone from the skills' guidance; the `use-template` skill treats an `mcp-servers.json` in an older template as a list of connections to request through latchkey.
