The `latchkey` skill is replaced by `connect-external-service`, one skill for reaching anything outside the workspace on the user's behalf. Its SKILL.md is a routing table: one row per method, in order (a builtin latchkey service; a custom latchkey service the user pastes a key into; the service's own MCP server; a custom latchkey service the user signs in to, capturing the session the service's website uses; its direct API with a key the user supplies through a secret card; the browser), each with the cheap test that says whether it is workable, the sentence to say, and the reference to read; the tests start from `latchkey services list` and `mcpc`, which name the connections that already exist. The agent takes the first workable row and explains rather than asking, and does not rule a row out from a probe made without the user's credential. The latchkey text lives on as `references/latchkey.md`, with the custom-service `header` and `credential_instructions` options (the latter puts the agent's directions to the key beside the input in the approval window, which covers the chat), a section on choosing between the cookie and token sign-in flows (and on where the sign-in window and the gateway's requests run), and a pointer to the direct-API row where it used to say to have the user type credentials into a file. `references/direct-api.md` is new, and so is `references/mcp.md`, which reaches every MCP server through `mcpc`, one MCP client the whole workspace shares, instead of any harness's own MCP config: servers are listed in `mcp-servers.json` at the repo root, each gets a session through `mcpc connect`, and tools are called with `mcpc @<name> tools-call`, so a newly connected server works in the same turn, from any chat on any harness, from an app, and from a scheduled job, with no chat restart. An MCP server the service does not publish itself is never run, hosted or local: it would be a stranger's code holding the user's key, or a middleman on their data; its source only informs a key or direct-API connection. A hosted server's OAuth sign-in runs through `mcpc login`, held open in the background while its consent page is handed to the user in a workspace browser; a hosted server that takes a key names it as `${VAR}` in its header, records the secret file it needs as `secretsFile`, and is connected under `with_secrets.py`.

The skill ships `scripts/request_secret.py`, which files a secret request with the chat app and prints it; the chat renders a card with one password input per variable, the user submits, and the agent is told the file and the variable names, never the values. A value reaches a program only through `python3 system/scripts/with_secrets.py data/.secrets/<name>.env -- <command>`.

Alongside: the eight skills that named the latchkey skill now point at the new one; `agentic-browser-fleet`'s description says to arrive through connect-external-service rather than load it directly; it says the window `new` opens is minimized, that `handoff` brings it up in front of the user, and that the agent shows it with `layout.py open browser` whenever else the user should watch, rather than telling the user to open it from the launcher; and it no longer says a launch-task worker runs in an isolated container (it runs in a worktree of the same workspace); `use-ai-integration` says to delete and re-snapshot `anthropic.env` rather than edit it; `build-app` takes `--secrets-file` and documents `[[secrets]]` in `app.toml` and the wrapped program command, and `update-app`'s preview runs such an app under the same wrapper for each declared file; `manage-scheduled-tasks` and the service-processes reference say how a job or program runs under a secret file; the worker reports a needed secret instead of requesting one; and `migrate-workspace`'s `retired-skill` audit now flags a migrated workspace's own references to the old `latchkey` skill.

Templates carry their secrets: `publish-template` aggregates every app's `[[secrets]]` and every skill's `secrets:` front matter (plus the files the snapshot's `mcp-servers.json` servers and supervisord programs run under) into `[[requirements.secret]]` entries with `file` and `variables`, refuses to assemble when a referenced file is undeclared or a declared variable is missing from the publishing workspace; `use-template` files one secret card per entry up front, and connects each MCP server once the file it runs under is stored, once the user has signed in, or at once when it needs neither.
