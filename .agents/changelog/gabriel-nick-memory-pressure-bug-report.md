A scaffolded app's supervisord program now carries `startsecs=30` and `startretries=5`, so a broken app gives up instead of restarting forever. An app that dies before it has stayed up 30 seconds counts as a failed start, which sends supervisord into backoff and then FATAL; one that runs for a while and then exits is still restarted as before. Built-in services keep retrying indefinitely, which is deliberate -- the workspace is unusable without them -- so a user app's block now differs from theirs, and `build-app`'s documented program blocks (scaffolded, inline wrap-existing, and wrapper-script) carry the same two settings.

The scaffolder wrote `startretries=1000000` copied from the built-in services, and supervisord's default `startsecs` is one second, so an app that stayed up just over a second and then died was treated as a clean exit and restarted immediately, at full speed, for as long as the workspace lived. On one production workspace an app did that 46,939 times in a single day and kept going for four days; nobody was told, because a crash loop is only visible to someone who runs `supervisorctl status`. Each restart also re-registered the app, which is what drove that workspace's service event log to 1.1 GB.

`scaffold_flask_lib_test.py` pins the property rather than the numbers: a scaffolded program must declare a finite retry count and a `startsecs` long enough that a fast death counts as a failed start.

Surfacing a crash-looping app to the user (rather than only bounding it) is still open -- supervisord's FATAL state has no path into the workspace UI today.
