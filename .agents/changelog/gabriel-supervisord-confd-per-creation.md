The `build-app` scaffolder writes the app's supervisord program to its own `system/supervisord.conf.d/<name>.conf` instead of appending to the shared `system/supervisord.conf`. That was the last shared file a scaffold authored, so scaffolding two apps now writes only new files and two agents can build two creations in one workspace without one editing a file the other owns. The one shared file a scaffold still writes is `uv.lock`, which `uv sync` regenerates to add the new member; it is derived rather than authored, so it stays out of a creation's footprint and is regenerated on merge rather than treated as a conflict.

The scaffolder's port pre-flight and its duplicate-name guard both scan every drop-in as well as the main config, and count only regular files: a glob is matched against whatever is on disk, so a directory named like a drop-in used to be handed to a caller that reads it, turning the pre-flight into a crash on an unrelated directory someone happened to create. Without that the pre-flight would have handed a new app port 8081, which the `browser` service holds in its own drop-in. The name guard also covers `[eventlistener:*]` declarations, since supervisord holds programs and listeners in one process-group namespace. Both, and the fact that a scaffold now authors no shared file, are pinned by a new `scaffold_flask_lib_test.py`.

`service-processes.md` states the rule without an exception: every supervisord program in this workspace is declared in exactly one file under `system/supervisord.conf.d/`, named after it.

`harden-contention.md` now records what the split does and does not buy the merge-time freshness check: no shared authored file is left in a creation's footprint, so two concurrent creations no longer collide textually, but a path-scoped diff still cannot see a change to something a creation depends on -- a shared library under `system/libs/`, a skill script an app calls, another creation's `app.toml` -- so a green check means "nothing this creation owns moved", not "this pass is still valid". It also carves generated lockfiles out of the "any merge conflict means a stale pass" rule. `uv.lock` is regenerated by every scaffold and marked `merge=binary`, so without the carve-out two concurrent creations would conflict there as a matter of course and force one into a full re-harden -- reintroducing, at the merge step, exactly the serialization this layout removes.

Every boot smoke-check now checks that the drop-ins are actually there, not just that the config parses. An `[include]` glob that matches nothing yields a config that realizes cleanly and runs no services at all, which is reachable now that the main config declares no programs of its own. So the check requires at least one realized program everywhere it is performed: `publish-template`'s assembly (exit 4), `use-template` and `update-installed-template` before they fast-forward the workspace onto a merged tree, and `update-published-template`'s re-cut. `publish-template`'s assembly additionally refuses a `--base-ref` whose tree does not name `system/supervisord.conf.d` (exit 5, alongside the existing `pyproject.toml` and `system/supervisord.conf` requirements).

`github-sync` writes its own drop-in rather than appending to the shared config; `update-self` classifies `system/supervisord.conf.d/**` as a service-class path; and `migrate-workspace` scans the drop-ins when collecting the source's and this workspace's app ports, which it needs to detect collisions before a migration.

`migrate-workspace` reads which directory holds those drop-ins out of each config's own `[include] files` globs rather than assuming `supervisord.conf.d/`, on both sides of the migration, and reads those globs the way supervisord's own parser does: `files =` and `files:` alike, an indented continuation folded into the value above it, comments dropped. It also substitutes `%(here)s` with shell parameter expansion rather than `sed` and globs with `IFS` emptied, so a source path holding a space, a `|` or an `&` cannot be read as syntax. The source-side listing is built by a named helper rather than inlined into the SSH call, so the skill's own tests run that shell against a local workspace and pin every one of those spellings; it is the one reader `system/test_supervisord_layout.py` cannot compare with the rest, since it expands over SSH. It matters most for the source, which is a workspace someone else configured and is read over SSH: against one that named its directory anything else, the old scan found no programs at all and reported every real app's port as free, so a collision would have surfaced as two programs bound to the same port after the migration instead of before it. The source listing still costs the one round trip it did before. Both sides resolve each pattern against the absolute directory of the config declaring it, as supervisord does: a relative one would be substituted into a `%(here)s` pattern and then joined back onto itself, so every drop-in would be looked for one directory deeper than it is and the scan would come back with the main config alone.
