update-self, build-app and the agent docs move to the app-environments layout: the built-in apps share the workspace venv, and every user-built package is a standalone project.

- **update-self runs and tests the install the services use.** The shell and chat pre-flights boot `.venv/bin/system-interface` and `.venv/bin/chat-app` (or the fresh venv the apply swaps in), the entry points supervisord runs, instead of bare names from the agent's PATH, which found per-app uv tools the services never ran. The per-app tool refresh, snapshots, rollback rebuild and shadowing sweep are gone; a change to a built-in app's `pyproject.toml` re-syncs the venv, and only `uv.lock`, the root `pyproject.toml` and the plugin manifest reinstall the mngr tool. A landed update removes the per-app tools older builds left.

- **User packages are standalone.** A user app, service or lib under `system/` (any package the root `members` does not name) has its own `uv.lock` and `.venv`, so a dependency it adds never moves the chat's versions. The update migrates old-layout ones with the new `user_package_migration.py` (`migrate --dry-run`, then `migrate --shared-lock <pre-merge lock>`; `relock` for a stale lock): it keeps their versions, turns workspace sources into editable path sources, rewrites their program lines and one-off commands, and takes them out of the root `pyproject.toml`. The worker checks each package's lock, puts the dry run in its report, and gives each converted package its suite and boot from its own venv. An apply syncs each user package it changed in place.

- **Broken user things get fixed after an update, not reported.** After a successful apply, the lead says in one chat line what it is fixing, sends a repair worker with the evidence, and finishes once it is fixed or the worker gives up (still `UPDATED`, with a detail naming what is left). The results message says at most one plain sentence about the restructuring.

- **build-app** scaffolds a standalone project: an `app-schema` path dependency, a lock seeded from the root lock, its own test dependencies and pytest root, a linked venv, and a program line that links, syncs `--locked` and execs from its own `.venv/bin`. It no longer installs an app as a uv tool or touches the root lock.

- **Previews and isolated boots** of a user package run from its own venv (`serve_isolated_instance.py --project`). `migrate-workspace` converts the packages it lands (`convert-packages`), and `use-template` and `update-installed-template` say an older template's app needs converting. `AGENTS.md`, `running-python.md`, `service-processes.md` and `spec-summary.md` describe the two kinds of package.
