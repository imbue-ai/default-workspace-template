The update flows are inverted: `update-self` now owns one general, atomic apply, and `update-system-interface` calls it for its go-live.

`update_self.py` gains `apply` -- a single deterministic, idempotent, rollback-on-failure motion that lands a prepared merge and makes the live workspace consistent with it: merge (fast-forward for update-self, ordinary for update-system-interface), pre-apply snapshots (built bundle, root venv, both uv tool environments, node_modules), dependency refresh, a `setup_system.sh` re-run when provisioner paths changed (before any restart), the worker's already-built bundle (live build fallback), pre-flight, restart, health probes to the frontend standard, the VERSION_HISTORY.md ledger entry, and `env-converge upgrade` post-success. On any failure the entire merge is reverted as a forward revert commit and the snapshots restored -- plain file copies needing no network, no package manager, and no working mngr. The worker branch and report survive every rollback, so a diagnosed retry is a quick re-land.

A full-information marker under `data/.state/update-apply/` (DRI agent, rollback point, phase, PID, snapshot manifest) makes interruption detectable and self-healing: a concurrent apply refuses while one is live, re-running the same apply resumes it, and the new `recover --if-stale` subcommand rolls a stale one back unattended (bootstrap at boot, a cron entry every 5 minutes).

The one outcome that does not resolve itself -- a rollback that could not put a healthy workspace back -- now leaves an `emergency.json` beside the marker naming the reason, the DRI agent, and where the kept pre-apply copies are. That exit clears the marker and its rollback restores the tree, so without the record the state needing a person most was the one nothing could see; the system interface's banner reads it. Nothing takes it down by itself: only an outcome that ends with the live workspace confirmed healthy, frontend included, clears it -- a later update that lands over a UI it could confirm, or a `recover` of a *new* interruption that probes afterwards (the boot-time pass runs before anything is up, so it cannot; nor does an apply that exits 0 naming a UI that was already broken) -- and after a repair by hand the skill's exit-3 guidance has the agent verify the workspace and delete the record, since otherwise a workspace that is fine goes on telling its user it may be broken.

The apply bands itself into the new near-exempt `UPDATE_APPLY` OOM band and tags only its memory-hungry forward steps (npm, the uv installs, the pre-flight boot) back to the expendable band -- nothing is expendable during rollback or recover. The `oom_priority` import is guarded so the staged copy still runs on trees that predate the package.

`reveal_system_interface.py` shrinks to the `preview`/`unpreview` adapters; the `update-system-interface` SKILL's merge + reveal steps become one apply call, and the `update-self` SKILL's 5b/5c collapse likewise (its ledger prose and env-converge step moved into the script). The update-self single-flight check becomes an "updating workspace" lease held through worker, approval, and apply, and the skill gains the canonical migration-required refusal (create a new workspace, then `/migrate-workspace`) plus post-rollback guidance. `classify_path` gains a `requires_restart` flag: vendored-mngr source and `.mngr/settings.toml` changes now restart the services agent, so nothing live keeps reading state newer than its own code.

The apply and the worker flow also close the gaps two real update incidents exposed. A failed provisioner run (`setup_system.sh`) no longer rolls the whole release back on its own: a failed tool install leaves the tree and services consistent, so the apply carries on to the restart and probes (a load-bearing provisioner change still fails those and still rolls back) and, when the update lands, records the gap at `data/.state/update-apply/provision-incomplete.json` and says so on stderr for the skill to re-run the provisioner after the fix. The provisioner now runs under the image build's environment (`HOME=/root`, an explicit PATH) rather than the calling agent's. Every forward step carries a wall-clock budget, so a hung `npm ci`, build, refresh, provisioner, or restart becomes a rollback naming the step instead of an open-ended wait, and the marker records when each phase was reached -- every apply prints an `apply phase timings:` line, the benchmarking input for those budgets and for the pre-flight and health poll budgets, which were raised from 30s to 240s. The served bundle is verified against the merged source: the frontend build stamps its output with the frontend source tree hash, a stale or unverifiable `--worker-bundle` falls back to a live build instead of being served, and a live build whose bundle does not match the merged tree rolls back; that verification is also what lets the apply skip the live `npm ci` when the worker's bundle will be installed. The pre-flight boot no longer inherits `MNGR_AGENT_ID`, so it cannot clobber the live layout. `classify-merge` refuses a `--local` that already contains `--target` (the degenerate re-run that silently classified an 818-file merge as empty) and points at the merge commit's first parent.

On the skill side, a successful pass now `mngr stop`s its worker instead of destroying it, so the worker's transcript stays reachable for bug reports; `create_worker.py launch --destroy-existing` clears that stopped predecessor on the next pass (a still-running one is refused). The worker guide's review gates are scoped to the files whose merged content differs from the release rather than the whole upstream diff, which over an 800-file release is the difference between reviewing four reconciled files and reviewing upstream's code.
