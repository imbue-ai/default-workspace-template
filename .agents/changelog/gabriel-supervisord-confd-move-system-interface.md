`service-processes.md` no longer carves `system_interface` out of "supervisord only manages the programs declared under `system/supervisord.conf.d/`". That program now lives in a drop-in like every other, so the rule holds without an exception: every supervisord program in this workspace is declared in exactly one file under `system/supervisord.conf.d/`, named after it.

Publishing a template now checks that the drop-ins are actually there. `publish-template`'s assembly refuses a `--base-ref` whose tree does not name `system/supervisord.conf.d` (exit 5, alongside the existing `pyproject.toml` and `system/supervisord.conf` requirements), and its boot smoke-check now fails when the config realizes no programs at all (exit 4) -- an `[include]` glob that matches nothing parses cleanly and would otherwise publish as a "bootable" template with no services.
