The update flows are inverted: `update-self` now owns one general, atomic apply, and `update-system-interface` calls it for its go-live.

`update_self.py` gains `apply` -- a single deterministic, idempotent, rollback-on-failure motion that lands a prepared merge and makes the live workspace consistent with it: merge (fast-forward for update-self, ordinary for update-system-interface), pre-apply snapshots (built bundle, root venv, both uv tool environments, node_modules), dependency refresh, a `setup_system.sh` re-run when a file it reads changed (its scripts or `.mngr/apt-snapshot-timestamp`; a `.mngr/settings.toml` change restarts the services agent instead of paying that run; before any restart), the worker's already-built bundle (live build fallback), pre-flight, restart, health probes to the frontend standard, the VERSION_HISTORY.md ledger entry, and `env-converge upgrade` post-success. On any failure the entire merge is reverted as a forward revert commit and the snapshots restored -- plain file copies needing no network, no package manager, and no working mngr. "Any failure" includes one nobody predicted: past the merge the pre-apply copies are the only ones left, so an unexpected exception is caught as a last resort and rolled back like a named step failure, with its traceback kept in the report. A step that cannot be spawned at all (npm, uv or mngr missing from the PATH the apply inherited) is named the same way rather than escaping as one of those. The worker branch and report survive every rollback, so a diagnosed retry is a quick re-land.

A full-information marker under `data/.state/update-apply/` (DRI agent, rollback point, phase, PID, snapshot manifest) makes interruption detectable and self-healing: a concurrent apply refuses while one is live, re-running the same apply resumes it, and the new `recover --if-stale` subcommand rolls a stale one back unattended (bootstrap at boot, a cron entry every 5 minutes).

The one outcome that does not resolve itself -- a rollback that could not put a healthy workspace back -- now leaves an `emergency.json` beside the marker naming the reason, the DRI agent, and where the kept pre-apply copies are. That exit clears the marker and its rollback restores the tree, so without the record the state needing a person most was the one nothing could see; the system interface's banner reads it. Nothing takes it down by itself: only an outcome that ends with the live workspace confirmed healthy, frontend included, clears it -- a later update that lands over a UI it could confirm, or a `recover` of a *new* interruption that probes afterwards, in both cases whatever the UI was doing before that apply began (the boot-time pass runs before anything is up, so it cannot; nor does an apply that exits 0 naming a UI that was already broken) -- and after a repair by hand the skill's exit-3 guidance has the agent verify the workspace and delete the record, since otherwise a workspace that is fine goes on telling its user it may be broken.

The pass now records itself for the Minds app in one file, `data/.state/update-apply/run.json`, via a new `run-status` subcommand: `start` (chat agent name from `$MNGR_AGENT_NAME`, unattended flag) as soon as the pass holds the updating-workspace lease, and exactly one terminal `verdict` (`UPDATED`, `UPDATED_WITH_REBUILD_ITEMS`, `ALREADY_CURRENT`, `NEEDS_RECREATION`, `STUCK`, `REFUSED`, with a plain-language detail line) from whichever section ends the pass. The app polls this file over `mngr exec` alongside the apply marker and the run's chat agent -- there is no event stream -- so a run started by hand inside the workspace is just as visible as one the app dispatched. There is one record per workspace, so the two writes are ordered around the lease that makes that safe: a pass that stops because another is already updating never writes at all, and a verdict is filed under the agent recording it rather than under whatever name the file carries -- otherwise a real run's outcome could land under an aborted pass's name, which the app matches by chat name and would discard. The phase order's load-bearing property is now stated as an invariant at the phase constants: the marker is on disk before anything that can disturb the live interface, which is what the app's stuck-edge probe depends on to tell a mid-apply outage from a real one.

The apply asks for the new near-exempt `UPDATE_APPLY` OOM band and tags only its memory-hungry forward steps (npm, the uv installs, the pre-flight boot) back to the expendable band -- nothing is expendable during rollback or recover. The band is best-effort and usually does not hold: lowering `oom_score_adj` below the inherited value needs `CAP_SYS_RESOURCE`, which the container lacks, so an apply launched from a chat agent or the recovery cron keeps its launcher's band and says so in a warning. The `oom_priority` module the apply reads is the *pre-merge* tree's -- whatever release the workspace is updating from -- so the load is guarded on the whole surface the script reads, not just on the package being present: a tree that predates any of it (every release through minds-v0.4.1 predates the shared shell-tag helper) runs unbanded and untagged with a note, rather than raising mid-apply past the merge and the snapshots, where nothing would catch it and the workspace would be left half-applied.

`reveal_system_interface.py` shrinks to the `preview`/`unpreview` adapters; the `update-system-interface` SKILL's merge + reveal steps become one apply call, and the `update-self` SKILL's 5b/5c collapse likewise (its ledger prose and env-converge step moved into the script). The update-self pass is now unattended: the missing-backup go-ahead, the mid-pass conflict escalation, the pre-apply system-interface preview, and the 5a approval wait are all gone -- the lead audits the worker's evidence, decides merge conflicts itself (defaulting to the workspace's current behavior), applies, and then reports what changed, every decision made on the user's behalf, and a rollback offer honored by landing a forward revert through the same apply (the over-ceiling `--override` confirmation, which fires at launch, also survives; a missing backup is flagged in that report instead of blocking). One mid-pass gate remains, judged on outcomes rather than merge mechanics: the worker now verifies every user creation the update touches against the merged result (screenshots it looks at for visual surfaces, exercised hook points for apps reaching into the system interface's API or state) -- a creation that merely moved or changed applies and gets a restore offer in the report, while a creation the update cannot keep, after a genuine attempt to adapt it, holds the pass untouched and asks the user with the evidence. The update-self single-flight check becomes an "updating workspace" lease held through worker, report audit, and apply, and the skill gains the canonical migration-required refusal (create a new workspace, then `/migrate-workspace`) plus post-rollback guidance. `classify_path` gains a `requires_restart` flag: vendored-mngr source and `.mngr/settings.toml` changes now restart the services agent, so nothing live keeps reading state newer than its own code.

The apply and the worker flow also close the gaps two real update incidents exposed. A failed provisioner run (`setup_system.sh`) no longer rolls the whole release back on its own: a failed tool install leaves the tree and services consistent, so the apply carries on to the restart and probes (a load-bearing provisioner change still fails those and still rolls back) and, when the update lands, records the gap at `data/.state/update-apply/provision-incomplete.json` and says so on stderr for the skill to re-run the provisioner after the fix. The provisioner now runs under the image build's environment (`HOME=/root`, an explicit PATH) rather than the calling agent's. Every forward step carries a wall-clock budget, so a hung `npm ci`, build, refresh, provisioner, or restart becomes a rollback naming the step instead of an open-ended wait, and the marker records when each phase was reached -- every apply prints an `apply phase timings:` line, the benchmarking input for those budgets and for the pre-flight and health poll budgets, which were raised from 30s to 240s. The served bundle is verified against the merged source: the frontend build stamps its output with the frontend source tree hash, a stale or unverifiable `--worker-bundle` falls back to a live build instead of being served, and a live build whose bundle does not match the merged tree rolls back; that verification is also what lets the apply skip the live `npm ci` when the worker's bundle will be installed. The pre-flight boot no longer inherits `MNGR_AGENT_ID`, so it cannot clobber the live layout. `classify-merge` refuses a `--local` that already contains `--target` (the degenerate re-run that silently classified an 818-file merge as empty) and points at the merge commit's first parent.

On the skill side, a successful pass now `mngr stop`s its worker instead of destroying it, so the worker's transcript stays reachable for bug reports; `create_worker.py launch --destroy-existing` clears that predecessor on the next pass when its process is gone (stopped, or exited on its own); one still running or waiting is refused, and a `mngr create` that mngr itself refuses now comes back as a message and a non-zero exit rather than a traceback. The worker guide's review gates are scoped to the files whose merged content differs from the release rather than the whole upstream diff, which over an 800-file release is the difference between reviewing four reconciled files and reviewing upstream's code.

The update-self flow now surfaces its own chat tab. The minds app sends the user into the workspace when it starts an update, and the conversation running it is what they are meant to land on -- but the workspace UI can only place a tab in front of a client that is connected when the chat appears, and from the app's machines list that is often nobody yet. Step 3 now runs a `surface-chat-tab` helper (from the target version's copy of the skill, so it reaches a workspace on its very first update) that keeps trying to open the tab until a client is there to show it, then stops for good; it is best-effort and never blocks the update.

The run record now carries the in-flight facts the Minds app shows a user. `run-status delegate <worker>` records the background worker the lead has handed the merge to (Step 3b, before the lead starts its background poll), because the lead's own chat is idle for the whole worker phase and an idle update chat is what the app reads as "waiting for you"; with the worker named, the app reads the worker's liveness instead, and the verdict clears the name. `run-status hold <CUSTOMIZATION|CONFLICT> --detail "..."` records that the pass has stopped to ask the user something and why, `run-status resume` clears it, and a verdict clears it on its own; the lead records the hold before it asks (Step 4), so the app can say "waiting for you: something you built can't survive this update" rather than only that the update agent has gone quiet. A merge conflict where every resolution breaks something the user built is now that same hold with `CONFLICT` as its reason, instead of a decision the lead makes alone. And the apply mirrors its marker into the record on every restamp (`apply_phase`, `apply_updated_at`) and clears both with it, so the app reads the apply's liveness from `run.json` alone and never has to know the marker exists.

The apply now runs its pre-flight boot of the merged backend before it rebuilds or installs the frontend bundle, so a combined release whose backend cannot boot is rejected while the live bundle is still the one that was serving, instead of after `static/` has been rewritten and must be restored from its snapshot.

The worker guide's impact analysis (Step 4a) now enumerates `system/vendor/**` alongside the other changed paths, and points the worker at the vendored mngr's changelog directories as the place removed behavior is announced in prose -- the class of change no test failure surfaces, and the one that broke a workspace app when an update retired an environment variable it read.

`check-app-errors` now looks for soft failures too: lowercase "failed" / "keep last" / "No such file or directory" lines that exit 0 and keep going, across stdout as well as stderr, plus the tail of every recently-changed log -- and it reconciles the scheduled jobs against their logs, since one that has failed on every run since it was created is invisible to `supervisorctl status`.

The apply's live provisioner run drops every inherited `*_VERSION` variable from its environment, so `setup_system.sh` always installs the merged tree's pins rather than whatever an older image exported: on an image built while the Dockerfile still carried `ENV CLAUDE_CODE_VERSION`, an update bumping Claude Code silently reinstalled the old version and passed its own pin check. The provisioner's inputs (the files whose change triggers that run) now include every installer the script chains -- `write_apt_sources.sh`, the secret scanners, agy, owner-exec, and dufs -- and a test keeps the two lists aligned, so a pin bump in an installer alone reinstalls the binary instead of landing inert.

`changelog-entries` anchors its pathspecs at the repository root, so it returns the same list from any working directory. A git pathspec is cwd-relative, and the worker guide had the tool run from the staged skill's scripts directory, from where the changelog glob matched nothing and the "what's new" digest came back empty with no error; the guide now says to run from the worktree root as well. `run-status` writes `run.json` newline-terminated, so a reader that `cat`s it and echoes a sentinel sees the sentinel on its own line. The SKILL tells the lead to run the apply in the foreground: a backgrounded apply leaves the chat idle exactly while the workspace goes dark, and its provisioner warning unread.
