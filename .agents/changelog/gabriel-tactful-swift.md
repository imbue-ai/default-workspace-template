The update-self flow now lands an update as one atomic, recoverable apply, runs unattended, and records itself for the Minds app.

`update_self.py apply` is the single motion that lands a prepared merge and makes the live workspace consistent with it. It merges (fast-forward for update-self, ordinary for update-system-interface), copies the pre-apply state aside (built bundle, root venv, both uv tool environments, node_modules), refreshes dependencies, re-runs `setup_system.sh` when a file the provisioner reads changed, pre-flights the merged backend on a throwaway port, installs the worker's already-built bundle or builds one live, restarts the services agent, probes the backend and the frontend, writes the `VERSION_HISTORY.md` ledger entry, and runs `env-converge upgrade`. On any failure, including an exception nobody predicted or a step that cannot be spawned at all, it reverts the whole merge as a forward revert commit and restores the copies. Those restores need no network, no package manager and no working mngr. The worker branch and report survive every rollback, so a diagnosed retry is a quick re-land. `update-system-interface` calls the same apply for its go-live; `reveal_system_interface.py` keeps only the preview adapters.

Every apply restarts the services agent. The earlier per-path rule (restart for the system-interface backend, vendored mngr source, `.mngr/settings.toml`, bootstrap, supervisord, and the libraries the system interface imports) was a list nobody could keep complete; the cost of a restart the diff did not strictly need is a UI blip during an update the app already covers. The provisioner re-run stays keyed on the files the provisioner reads, but which installers `setup_system.sh` chains is now read off the script in the merged tree rather than kept in a hand-maintained list, so a release that adds or retires an installer is read as it ships, and a pin bump in an installer alone still reinstalls the binary. Re-provisioning on every apply was considered and rejected: a forced run measured 145 seconds of network on a staging host, and only 6 of the last 20 releases touched a provisioner input.

A failed provisioner run no longer rolls the release back on its own. A failed tool install leaves the tree and services consistent, so the apply carries on to the restart and the probes; a load-bearing provisioner change still fails those and still rolls back. When the update lands anyway, the gap is recorded at `data/.state/update-apply/provision-incomplete.json` and named on stderr for the skill to re-run the provisioner after the fix. The live provisioner run uses the image build's environment (`HOME=/root`, an explicit PATH, every inherited `*_VERSION` dropped) so it installs the merged tree's pins rather than an older image's.

Every forward step carries a wall-clock budget, so a hung `npm ci`, build, refresh, provisioner or restart becomes a rollback naming the step. The apply prints an `apply phase timings:` line, the benchmarking input for those budgets; the pre-flight and health poll budgets were raised from 30s to 240s. The served bundle is verified against the merged source: the frontend build stamps its output with the frontend source tree hash, a stale or unverifiable `--worker-bundle` falls back to a live build, a live build whose bundle does not match the merged tree rolls back, and a verified worker bundle lets the apply skip the live `npm ci`. The pre-flight runs before the bundle is touched, so a backend that cannot boot is rejected while the live bundle is still serving. The environment refresh reinstalls the mngr and system-interface tools from their uv receipts unioned with the merged tree's `system/config/mngr_plugins.toml`, so a release that ships a new plugin reaches an existing workspace. The pre-flight boot no longer inherits `MNGR_AGENT_ID`, so it cannot clobber the live layout.

A marker under `data/.state/update-apply/` (DRI agent, rollback point, phase, PID, snapshot manifest) makes an interruption detectable and self-healing: a concurrent apply refuses while one is live, re-running the same apply resumes it, and `recover --if-stale` rolls a stale one back unattended (bootstrap at boot, a cron entry every five minutes). The marker is on disk before anything that can disturb the live interface; that ordering is stated as an invariant at the phase constants because the app's stuck-edge probe depends on it. A rollback that could not put a healthy workspace back leaves `emergency.json` beside the marker naming the reason, the DRI agent and where the kept copies are; the system interface's banner reads it, and only an outcome that ends with the live workspace confirmed healthy, frontend included, clears it. The apply bands itself into the system interface's own OOM band, read off the tree it is applied to so a staged apply on an older release bands itself the same way, and tags its memory-hungry forward steps back to the expendable band; nothing is expendable during rollback or recover. Measured on docker, lima and imbue_cloud hosts, the banding holds from a chat agent and from cron alike (the kernel checks `oom_score_adj_min`, which nothing in the container raises). The `oom_priority` module the apply reads belongs to the pre-merge tree, so the load is guarded on the whole surface the script reads and an older tree runs unbanded with a note rather than raising mid-apply.

The pass records itself for the Minds app in `data/.state/update-apply/run.json` through the `run-status` subcommand: `start` (the chat agent's name) once the pass holds the updating-workspace lease; `delegate <worker>` when the lead hands the merge to its background worker, so the app reads the worker's liveness while the lead's chat is idle; `hold --detail "<one plain line>"` and `resume` around the one question the pass may stop to ask, the line being what the app's modal and banner lead with; and exactly one terminal `verdict` (`UPDATED`, `UPDATED_WITH_REBUILD_ITEMS`, `ALREADY_CURRENT`, `NEEDS_RECREATION`, `STUCK`, `REFUSED`) with a plain-language detail line. The apply mirrors its marker phase and restamp into the same record and clears them with it, so the app never has to know the marker exists. A pass that stops because another is already updating never writes, and a verdict is filed under the agent recording it, so a real run's outcome cannot land under an aborted pass's name.

The pass is unattended. The lead audits the worker's evidence, decides merge conflicts itself (defaulting to the workspace's current behavior), applies, and then reports what changed, every decision made on the user's behalf, and a rollback offer honored by landing a forward revert through the same apply. Two things still wait for the user: an `--override` past the version ceiling, asked at launch unless the launch already carries the confirmation, and a creation the update cannot keep. For the latter, the worker verifies every user creation the update touches against the merged result (screenshots for visual surfaces, exercised hook points for apps reaching into the system interface); a creation that merely moved gets a restore offer in the report, while one the update cannot keep, after a genuine attempt to adapt it, holds the pass untouched and asks the user with the evidence. A merge conflict where every resolution breaks something the user built is that same hold. The single-flight check is an "updating workspace" lease held through worker, report audit and apply; the skill gains the canonical migration-required refusal and post-rollback guidance; a missing backup is a caveat in the report rather than a blocker. The worker guide's review gates are scoped to the files whose merged content differs from the release, its impact analysis covers `system/vendor/**` and the vendored mngr's changelogs, and `classify-merge` refuses a `--local` that already contains `--target`.

A successful pass `mngr stop`s its worker instead of destroying it, so the transcript stays reachable for bug reports; the next pass clears a stopped predecessor with plain `mngr list` and `mngr destroy`, and `launcher_contract_test.py` holds every `create_worker.py` invocation in the prose to the launcher interface of the oldest release the app updates from. A `mngr create` that mngr itself refuses comes back from `create_worker.py` as a message and a non-zero exit rather than a traceback. The flow surfaces its own chat tab (`surface-chat-tab`, retried until a client is connected) so a user sent into the workspace lands on the conversation running the update. `changelog-entries` anchors its pathspecs at the repository root; `check-app-errors` also looks for soft failures and reconciles scheduled jobs against their logs.

`update_self.py` is now the command line over sibling modules in the same `scripts/` directory: the update target and ceiling, change classification and the apply plan, the Minds-app/bootstrap/system-interface contract (`update_apply_contract.py` holds every state path, phase, verdict and record shape), the workspace layout, banding, the process seams, the served environment, the probes, the ledger, and the apply/recover orchestration. The directory is staged and run as one unit, so the sibling imports resolve to the staged copies. The SKILL.md is condensed to the happy path, under the 500-line body the skill validator recommends, with the version ceiling, the cross-version handoff contract, the results-message rules, the apply outcomes and rollback guidance, and the shallow-history heal moved to `references/`; the worker guide likewise, with its provisioning-change and review-gate rules in their own references.
