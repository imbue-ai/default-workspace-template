The checks the workspace runs on its own skills now leave out the skills an installed app carries: an app whose record says it was installed from someone else's repository is kept as it came, without an entry in `.agents/third-party-skills.toml`.

The manage-routines skill says where a routine's file lives when it belongs to an app (`system/apps/<package>/routines/<id>.toml`), that `routines add --app <name>` writes there for an app built or installed in the workspace, that rescheduling such a routine is kept as the user's choice without touching the app's file, and that any other change or a removal is made by changing the app.

The update worker's environment gate now converts each app built before apps had records with `app-install migrate`, regenerates every app's program files and skill links with `app-install regenerate`, and runs `app-install check`; an app that cannot be converted keeps running and is reported as a follow-up.

The build-app scaffolder now registers the app it writes through `app-install`, which allocates the port, writes the app's record (`system/config/apps/<name>.toml`), and generates its supervisord program; a registration the workspace refuses names every problem and leaves no app directory behind. The scaffolded runner imports the app SDK (`imbue.app_sdk`), reads its host and port from the environment with no port of its own, and serves the shell's two browser modules through the SDK. `--secrets-file` takes a `--secrets-variable` for each variable and writes the manifest's `[[secrets]]` block, which the generated program runs under. The skill says that the program file and an app's skill links are generated (change `app.toml` and run `app-install regenerate`), where an app's skills, routines and environment units go, that another app is found by name, that an app carries its own data migrations, that a wrapped server is an app directory with a `[run]` table registered with `app-install add` and has no request guard, and that an app is removed with `app-install uninstall`.

New skill: `install-app`, which installs one app someone published from its repository URL with `app-install install`, after the same trust warning a template gets, and then sets it up with the user: the permissions and secrets it declares, the apps it expects, and its adaptation notes. `use-template` hands an app's URL over to it.

The worker references `type-app.md` and `type-skill.md` say what holds for an app with a record: a skill it owns lives in the app's directory and is part of the app, so `skill:<name>` names the app; its references are kept in its record rather than its `app.toml`; its program files are generated; and its `[scope] exclude` globs are relative to its own directory. The update-app skill and the shared `service-processes.md` reference say how such an app is changed and removed: its `app.toml` and `app-install regenerate` in place of an edit to its program file, and `app-install uninstall` in place of taking it apart by hand. The update-app skill, the build-app skill and `harden-creation.md` say the same of references: only a built-in app takes `[[references]]` in its `app.toml`, and for an app with a record a worker names the file in its report rather than writing the record.
