The checks the workspace runs on its own skills now leave out the skills an installed app carries: an app whose record says it was installed from someone else's repository is kept as it came, without an entry in `.agents/third-party-skills.toml`. A skill an app built in the workspace carries is held to the checks like any other, and `validate_skill.py` checks it against the workspace's own tree whether it is named by its link under `.agents/skills/` or by its directory inside the app.

The manage-routines skill says where a routine's file lives when it belongs to an app (`system/apps/<package>/routines/<id>.toml`), that `routines add --app <name>` writes there for an app built or installed in the workspace, that rescheduling such a routine is kept as the user's choice without touching the app's file, and that any other change or a removal is made by changing the app.

The update worker's environment gate now converts each app built before apps had records with `app-install migrate`, regenerates every app's program files and skill links with `app-install regenerate`, and runs `app-install check`; an app that cannot be converted keeps running and is reported as a follow-up.

The build-app scaffolder now registers the app it writes through `app-install`, which allocates the port, writes the app's record (`system/config/apps/<name>.toml`), and generates its supervisord program; a registration the workspace refuses names every problem and leaves no app directory behind. The scaffolded runner imports the app SDK (`imbue.app_sdk`), reads its host and port from the environment with no port of its own, and serves the shell's two browser modules through the SDK. `--secrets-file` takes a `--secrets-variable` for each variable and writes the manifest's `[[secrets]]` block, which the generated program runs under.

The build-app skill's step for choosing a name refuses one that differs from another app's only by a hyphenated suffix, and its scaffold step says that the port and the program file are never chosen or written by hand. Its `scaffold-output.md` reference describes the record and the generated program file, the two ways the scaffolder fails, and the secrets flags. Its `wrap-existing-server.md` reference makes a wrapped server an app directory with a `[run]` table registered with `app-install add`, and opens with what a wrapped server lacks: a request guard. `forward-port-cli.md` is reached from `scaffold-output.md`, since no registration is written by hand.

The shared references both build-app and update-app read carry the rest. `apps/manifest.md` says how an app with a record runs (`[run]`, `[[services]]`, `[[secrets]]`, a `command` of one word), that its program files and skill links are generated and changed with `app-install regenerate`, where an app's skills, routines and environment units go and when a unit runs, and that only a built-in app takes `[[references]]` in its `app.toml`. `apps/code.md` says that the starter takes its port from the environment, that another app is found by name with `resolve_app_url`, and that an app carries its own data migrations; `apps/api-schema.md` names the SDK's modules; `apps/gotchas.md` says what to do when an allocated port is taken.

New skill: `install-app`, which installs one app someone published from its repository URL with `app-install install`, after the same trust warning a template gets, and then sets it up with the user: the permissions and secrets it declares, the apps it expects, the environment units it carries (which run at the next boot unless run by hand), and its adaptation notes. `use-template` hands an app's URL over to it.

The harden-worker skill's `type-app.md` and `type-skill.md` references say what holds for an app with a record: a skill it owns lives in the app's directory and is part of the app, so `skill:<name>` names the app; its references are kept in its record rather than its `app.toml`; its program files are generated; and its `[scope] exclude` globs are relative to its own directory. The update-app skill (a standing instruction, `applying-a-change.md` and `removing-an-app.md`) and the shared `service-processes.md` reference say how such an app is changed and removed: its `app.toml` and `app-install regenerate` in place of an edit to its program file, and `app-install uninstall` in place of taking it apart by hand. The harden-worker skill's `harden-creation.md` and the shared `review-gates.md` say that for an app with a record a worker names a file that uses the app in its report rather than writing the record.
