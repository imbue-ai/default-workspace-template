Made the `update-system-interface` reveal unable to leave the workspace without an interface, which is how a failed update could previously take the UI down for good.

The reveal now takes a copy of the compiled interface before it starts. Both of its steps destroy before they produce -- the dependency install deletes the installed packages first, and the build empties the output directory first -- so a failure part-way through used to leave nothing to serve. Recovery then re-ran the very build that had just failed, which meant a broken build environment (an unreachable package registry, a build killed for memory) could not be recovered from at all. Restoring the copy needs neither the package manager nor the network, so that failure mode no longer costs you your interface. A rebuild during recovery is only attempted when there was no interface to save in the first place.

In the one case where recovery cannot get the interface back either, the copy is kept and where to find it is printed with the alarm, rather than being cleaned up along with everything else. That is the situation the copy exists for: putting it back by hand needs no package manager and no network, and by then it is the only working interface left anywhere, since the one in the workspace was erased before the build that failed. That only applies to an update that touched the interface itself, which is the only thing that erases it -- when an update to the workspace's server goes wrong the copy is identical to what is already there, so the alarm does not offer it and send you off to replace the interface with itself. An undo that cannot run its own steps raises that same alarm and keeps the copy too, instead of reporting the "nothing was changed" outcome over a half-undone workspace and cleaning the copy up on the way out. And when there is no copy at all -- there was no interface to save, or saving it failed -- the update says so the moment it skips it, so an alarm without a copy on offer is never a mystery.

The reveal now also checks that the interface actually works before declaring success, instead of only asking the backend whether it is alive. The backend answers happily while the compiled interface is missing, and the "not built" page it serves instead is itself a perfectly normal response, so nothing caught it. The check now confirms the page really is the app and that its script loads as JavaScript -- covering both the missing-interface case and the blank screen that an unserved script path produces. A rollback is held to the same standard, so it can no longer report that it restored a healthy interface when it did not.

That check is scoped to changes the update itself causes: the same probe runs before the update, and only an interface that was working beforehand has to be working after. A workspace that was already broken when the update started has the problem reported rather than the update rolled back, since undoing an unrelated change would not have fixed it. That applies to what the update says about itself as well, whether it landed or was rolled back: neither outcome claims the interface is healthy when the check that would have established it was never armed, so the closing line names what was confirmed and what was not. Every one of those checks retries when the workspace does not answer at all, so a single slow response cannot decide the outcome on its own: beforehand it would have quietly concluded the interface was already broken and stood the check down for the rest of the run, and afterwards it would have undone an update that had landed perfectly well. None of them retries a workspace that answers and tells them the interface is broken, since asking again only arrives at the same answer more slowly.

Two narrower fixes: a build that reports success without producing anything is now treated as a failure rather than revealed as if it had worked; and changes to interface files outside `frontend/src/` (`index.html`, the build config, the TypeScript config, bundled media) are now recognised as interface changes. They previously classified as no change at all, so the reveal reported "nothing to reveal" and left the merged code running against a stale interface.

The update itself is also now protected from being stopped when the workspace runs low on memory, while the build it runs is not. Previously the whole update ran as one of the first things in line to be stopped -- ahead of every chat and every agent -- which was backwards: losing the build is an ordinary failure the update undoes cleanly, but losing the update *itself* skips the undo entirely and leaves a half-applied change, no interface, and the saved copy of the old one stranded where nobody knows to look. The update now runs at the same protection as the interface it is maintaining, and marks its own heavy steps (the dependency install, the build, the trial boot) as expendable so they keep giving way first. Only the update itself is protected: previewing a change before it lands leaves a second copy of the interface running afterwards, and that copy is disposable by definition, so it stays first in line to be stopped rather than being kept alive ahead of your chats. This steers the choice rather than dictating it, and it only covers running low on memory -- a workspace that is stopped outright still stops the update wherever it is.
