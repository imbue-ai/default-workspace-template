update-self now works out which earlier updates' rollbacks still need undoing with a new `update_self.py pending-rollbacks` command, which the worker runs before it merges, and the apply refuses a merge that leaves one in place by the same rule. Before, the worker guide reverted the newest rollback it found. That could be an earlier release's rollback that its own retry had already undone, and the worker then stopped on an empty revert. Now each rollback nothing has undone is reverted, newest first, whether the pass retries that release or moves to a newer one. An update's rollback now names the release it rolled back in a `Rolled-back-update:` trailer, which is how it is told apart from a user's rollback of an app change: that one carries the same subject and is left alone. A rollback made before the trailer is recognised by the history it undid instead, including the rollback of a failed retry of a release already in history, where all the retry landed was the revert of the first rollback. Before, the apply caught a skipped revert only on a retry of the same release; now it catches it on any pass.
