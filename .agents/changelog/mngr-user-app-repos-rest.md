The publish-template skill's `github_repo.py` creates and closes a repository through `github_sync.repositories`, the library `app-install link` uses for an app's dev repository, instead of carrying its own copy of those requests. Its commands, output and exit codes are unchanged.

New skill: `update-installed-app`, which brings a newer version of an installed app in with `app-install update` over the workspace's own changes to it. It tells the user before starting when the new version is a major one, handles each result (a conflict or failing checks wait in the update's worktree and are finished with `--continue` or given up by removing it), checks the app against the user's own data afterwards, and says how to go back: restore the copy of the data the update made, then reinstall the earlier version by the commit it was on. Its `SKILL.md` holds the standing instructions and five steps; an update that waits and the app's data across an update are its two references.

The github-sync skill describes an app's dev repository (`<name>-dev`, private, kept current by the sync service): enabling sync runs `app-install link` for each app built here or changed after it was installed, one app can have one without workspace sync (`link --create-dev-repo`, then `github-sync sync-app`), what each state in `github-sync status` means and what to do about it, and what anyone given access to a dev repository sees: history no secret scan has run on, with the message of every workspace commit that touched the app. The detail is in the skill's `references/app-dev-repositories.md`, which `SKILL.md` names where each part is needed.

The build-app skill links a new app after its first commit when GitHub sync is on (`app-install link`; step 3 and the wrapped-server path name `references/link-new-app.md`). A skill built for an app is made under `.agents/skills/` like any other and recorded as one of the app's references with `app-install reference add`; the app takes it in when it is published, so the flows that build a skill (`fetch-process-show`, `crystallize-creation`, `update-creation`, `heal-creation`) are as they were (`apps/manifest.md`, the harden worker's `type-app.md` and `type-skill.md`, `AGENTS.md`). `apps/code.md` has one short section on using another app: find it by name, call its API from the app's own backend, and never read its stored data. The rule that an app brings its own older data forward when its stored shape changes is the harden worker's (`type-app.md`) and the publish worker's, and is no longer read while an app is first built. The update-app skill sends a newer version of an installed app to `update-installed-app`, and its `references/removing-an-app.md` says what to check before removing an app other things use and what `app-install uninstall` reports as kept: data, secret files, sharing grants, routine state, repositories, and the apps that depended on the one removed.

The template skills (`publish-template`, `use-template`, `update-published-template`, `update-installed-template`) say up front that a template shares a whole workspace and that one app is shared with `publish-app`, added with `install-app` and updated with `update-installed-app`. A template carries the apps the workspace built as ordinary files with their records; `use-template` and `update-installed-template` run `app-install check` on the merged tree (for the latter, in its new `references/apps-in-the-merge.md`).

The update-self skill links each app the workspace built after an update has landed, when GitHub sync is on (`app-install link`, or `link --refresh` for one already linked), and hands an app the worker could not convert or regenerate to a repair worker without holding the update. The manage-routines skill says what can be changed on a routine an app owns and how to go back to the app's schedule (`references/app-routines.md`). The migrate-workspace skill registers each carried-over app with `app-install` (`regenerate`, `migrate` or `add`) in place of a hand-written program block. The install-app skill says what the Imbue Studio app has already done when it sends `/install-app <url>`, that a dev repository's URL installs the same way, from its `main`, and that getting the data to flow between an app and the apps it depends on is the agent's to work out: install a missing one that names its repository, and have one app collect data that two would otherwise each collect.

The harden-worker references and the shared `review-gates.md` say that a skill an app carries is part of the app by where it is, that `skill:<name>` for it resolves to the app, and that a path elsewhere that starts using an app is recorded with `app-install reference add` in place of a line in the worker's report.

New `publish-app` skill: publishes one app to a public repository of its own on the user's GitHub account, for the first version and every later one, through `app-install publish` (compare, set-version, assemble, push, record), with a scope gate and a publish gate only the user can pass; the scan of the app and the version bump run in a background worker (`references/scan-worker.md`). Its eight steps are in `SKILL.md`, with the GitHub access commands, the worker's task file and launch commands, every result other than the expected one (a worker that reports it is stuck among them), and what the lead does once a version is published in `references/github-access.md`, `references/dispatching-the-worker.md`, `references/results.md` and `references/after-publishing.md`. After every publish of a Python app the lead stops the app, starts it again and checks it on the user's data, so the app changes over to what was published while someone is looking. Publishing is when an app takes in the skills it needs: `references/skills-the-app-needs.md` says which skills (one the app runs, reads the data of or imports, and one that only drives it), and what the user is told at the scope gate; once the version is published the lead moves the skill's data from `data/.skills/` to the app's own data directory; the worker moves the skill into the app's `skills/` under a name that starts with the app's, moves its code into the app's package, and repoints whatever else used it. A skill another app also uses goes to the app that owns the data, which the other app then calls and lists under `[[dependencies]]`; when neither owns it, the data becomes an app of its own first. The worker also moves a Python app from the workspace's own app SDK, which it reaches through a path into the workspace, to the released `imbue-app-sdk` (a range starting at the version the workspace runs), makes its lock again and runs its tests; an app that needs an SDK newer than the newest release cannot be published until that release exists, and the worker says so. The build-app scaffold's `pyproject.toml` comment says the same: an app built here follows the workspace's SDK, and publishing is what moves it to the released one. The build-app scaffold now writes a `.gitignore` into the app's directory, every pattern one the workspace already ignores, since an app's own repository does not inherit the workspace's. The publish-template scripts take `set_repository_topics` and `hint_for_push_failure` from `github_sync.repositories`.

The update worker's guide runs `app-install verify <name> --template <target>` for each app the update converted or regenerated, which records the template version the app's checks passed on.

The use-template and update-installed-template skills merge the fetched commit by its hash in their scratch worktree: `FETCH_HEAD` belongs to the checkout that fetched, so the merge named it where it does not exist.

`test_a_server_this_process_spawned_reads_as_gone_once_killed` in the shared scripts' `serve_isolated_instance_test.py` no longer fails now and then with `ChildProcessError`: the child of its `crashed-during-boot` case exits only once the test lets it, so the finalizer of the `Popen` the spawner drops cannot reap it before the test looks at it.
