The publish-template skill's `github_repo.py` creates and closes a repository through `github_sync.repositories`, the library `app-install link` uses for an app's dev repository, instead of carrying its own copy of those requests. Its commands, output and exit codes are unchanged.

New skill: `update-installed-app`, which brings a newer version of an installed app in with `app-install update` over the workspace's own changes to it. It tells the user before starting when the new version is a major one, handles each result (a conflict or failing checks wait in the update's worktree and are finished with `--continue` or given up by removing it), checks the app against the user's own data afterwards, and says how to go back: restore the copy of the data the update made, then reinstall the earlier version by the commit it was on. Its `SKILL.md` holds the standing instructions and five steps; an update that waits and the app's data across an update are its two references.

The github-sync skill describes an app's dev repository (`<name>-dev`, private, kept current by the sync service): enabling sync runs `app-install link` for each app built here or changed after it was installed, one app can have one without workspace sync (`link --create-dev-repo`, then `github-sync sync-app`), what each state in `github-sync status` means and what to do about it, and what anyone given access to a dev repository sees: history no secret scan has run on, with the message of every workspace commit that touched the app. The detail is in the skill's `references/app-dev-repositories.md`, which `SKILL.md` names where each part is needed.

The build-app skill links a new app after its first commit when GitHub sync is on (`app-install link`; step 3 and the wrapped-server path name `references/link-new-app.md`). The shared app references say that an installed app's data outlives its code across updates, so an app keeps a data migration for every shape a published version wrote (`apps/code.md`), and that a path elsewhere that uses an app is recorded with `app-install reference add` (`apps/manifest.md`). The update-app skill sends a newer version of an installed app to `update-installed-app`, and its `references/removing-an-app.md` says what to check before removing an app other things use and what `app-install uninstall` reports as kept: data, secret files, sharing grants, routine state, repositories, and the apps that depended on the one removed.

The template skills (`publish-template`, `use-template`, `update-published-template`, `update-installed-template`) say up front that a template shares a whole workspace and that one app is shared with `publish-app`, added with `install-app` and updated with `update-installed-app`. A template carries the apps the workspace built as ordinary files with their records; `use-template` and `update-installed-template` run `app-install check` on the merged tree (for the latter, in its new `references/apps-in-the-merge.md`).

The update-self skill links each app the workspace built after an update has landed, when GitHub sync is on (`app-install link`, or `link --refresh` for one already linked), and hands an app the worker could not convert or regenerate to a repair worker without holding the update. The manage-routines skill says what can be changed on a routine an app owns and how to go back to the app's schedule (`references/app-routines.md`). The migrate-workspace skill registers each carried-over app with `app-install` (`regenerate`, `migrate` or `add`) in place of a hand-written program block. The install-app skill says what the Imbue Studio app has already done when it sends `/install-app <url>`, and that a dev repository's URL installs the same way, from its `main`.

The harden-worker references, the shared `review-gates.md`, and the crystallize, update and heal skills say that a skill an app carries is part of the app by where it is, that `skill:<name>` for it resolves to the app, and that a path elsewhere that starts using an app is recorded with `app-install reference add` in place of a line in the worker's report.

New `publish-app` skill: publishes one app to a public repository of its own on the user's GitHub account, for the first version and every later one, through `app-install publish` (compare, set-version, assemble, push, record), with a scope gate and a publish gate only the user can pass; the scan of the app and the version bump run in a background worker (`references/scan-worker.md`). Its eight steps are in `SKILL.md`, with the GitHub access commands and every result other than the expected one in `references/github-access.md` and `references/results.md`. The build-app scaffold now writes a `.gitignore` into the app's directory, every pattern one the workspace already ignores, since an app's own repository does not inherit the workspace's. The publish-template scripts take `set_repository_topics` and `hint_for_push_failure` from `github_sync.repositories`.

The update worker's guide runs `app-install verify <name> --template <target>` for each app the update converted or regenerated, which records the template version the app's checks passed on.

The use-template and update-installed-template skills merge the fetched commit by its hash in their scratch worktree: `FETCH_HEAD` belongs to the checkout that fetched, so the merge named it where it does not exist.
