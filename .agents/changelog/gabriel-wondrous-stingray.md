An update no longer fails and rolls back when the npm dependencies are not installed. The apply ran `npm ci` only when the merge touched `package.json` or `package-lock.json`, but ran the frontend build whenever frontend source merged -- so a merge that changed neither manifest built into a tree with no `node_modules` at all, died with `sh: 1: tsc: not found`, and rolled the whole update back. Whether the manifest changed says nothing about whether the dependencies are there; both are now asked, the way the recovery path already asked them. A tree that does have its dependencies, with no manifest change, still skips the refresh -- it is the slowest and most memory-hungry step of the apply.

The `build-app` scaffolder no longer keeps its own copy of the registry's reserved-name list. It carried a third copy that had drifted, so nine names scaffolded cleanly and then failed to register -- the scaffold would mint a half-built app package that died at manifest validation. It now asks `forward_port.py` itself whether a name can be registered, and keeps only the names of its own built-in apps, which the registry has no reason to know about.
