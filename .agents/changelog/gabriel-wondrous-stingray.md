An update no longer fails and rolls back when the npm dependencies are not installed. The apply ran `npm ci` only when the merge touched `package.json` or `package-lock.json`, but ran the frontend build whenever frontend source merged -- so a merge that changed neither manifest built into a tree with no `node_modules` at all, died with `sh: 1: tsc: not found`, and rolled the whole update back. Whether the manifest changed says nothing about whether the dependencies are there; either is now reason enough to refresh. A tree that does have its dependencies, with no manifest change, still skips the refresh -- it is the slowest and most memory-hungry step of the apply.

The `build-app` scaffolder no longer keeps its own copy of the registry's reserved-name list. It carried a third copy that had drifted, so nine names scaffolded cleanly and then failed to register -- the scaffold would mint a half-built app package that died at manifest validation. It now asks `forward_port.py` itself whether a name can be registered, and keeps only the names of its own built-in apps, which the registry has no reason to know about.

Finding a defect in built-in code is now itself a reason to escalate it upstream, rather than something the user has to think to ask for. `update-self`'s review gates are built to surface exactly this class of finding, and they deliberately do not fix it locally -- a fix to a file that is byte-identical to the release only manufactures divergence the next update must reconcile. But the flow then had no outlet: findings were labelled "submit-upstream-changes candidate" and recorded in the workspace's own ticket tracker, which cannot reach the code that needs changing. Every workspace that hit the same bug rediscovered it and buried it again. `update-self` now has a terminal step that submits those findings or surfaces them to the user with the submission offered, and AGENTS.md states the general rule and names both channels.

`/assist` now sends exactly one report per pass, covering every built-in issue it found, instead of one report per issue. Each report pops a modal over the user's workspace, so a report per issue meant a queue of modals to read and submit one at a time for a single session's work. Issues can be split apart upstream; they cannot be un-popped here.
