When the workspace does have a footprint, the worker no longer judges by hand which of the user's creations the update touches: for every app with an `app.toml` it runs `app-manifest footprint` over the merge's two ranges (base to the pre-merge local ref, and that ref to the merge), and the resulting scope files say by rule which creations carry the workspace's own content and which of those the update reached inside their footprint -- the app's directory, its supervisord drop-ins, and the paths its manifest claims. Those creations and their references head the consumer list in 4a, the customization-survival check in 4b runs over exactly the files the update changed inside each, and a manifest the merged tree can no longer satisfy (a referenced path the release removed) fails the command and is merge work to fix in the branch rather than something to discover by suite. Dependency the footprint cannot see -- a user app importing a shared lib or calling the shell's API -- stays with the grep and coupling steps, and this evidence never licenses skipping a gate.
