An update-self pass on a workspace with no code of its own no longer spends half an hour testing upstream's release.

Before, the worker guide scoped the test suites to `projects_to_validate` but left the depth of everything else to judgment, so on a clean pull of a 1414-file release the worker still ran the root, system-interface and chat suites (twice, to chase flakes), built both frontends, and booted throwaway copies of the shell and the chat app, "as extra coverage". It also ran the full impact analysis, enumerating consumers and researching toolchain release notes, on a workspace whose only local change was the version history. On a two-core workspace that was 33 of the 42 minutes a user watched the update run.

Now `classify-merge` also reports the workspace's own content (`local_only`) and whether any of it is code (`has_local_footprint`), and the worker guide reads both by rule, the way the review gates already are: the impact analysis is skipped when there is no local footprint (nothing of the user's can depend on the update; only the provisioning classification and a check of gitignored cron drop-ins for paths the update removed remain), each validation item runs only when its condition holds, with whatever the worker edited in the branch itself counted in (an empty `projects_to_validate` runs no suite; a service that arrived exactly as upstream shipped it is left to upstream's own testing, and only one the workspace created or modified is booted; a toolchain bump with only built-in dependents needs no release-note research), and widening either is a `question` gate rather than a silent deviation. The report records which branch applied and the lead's audit requires that record. The lead's launch step now says to arm the worker poll in the background and end its turn rather than sleep on it, per the lead-proxy reference, which is the other place the same pass lost time.

The same pass also showed three ways the apply itself lost the hour after the merge, on a workspace baked at minds-v0.4.2. Running the root test suite deleted the workspace's live mngr install: the sweep that removes a stale mngr copy resolved the install to keep from the test's fake `mngr` but swept the image build's home on its own, so the suite passed while the apply then had no `mngr` on its PATH and rolled back. The sweep now takes the homes it may touch from its caller (the agent's home and the image build's for a live apply, temporary directories under test). A rollback re-provisioned the restored tree but left the merged tree's provision-guard marker behind, so the retry of the same merge skipped the provisioner in zero seconds and reported UPDATED with Claude Code still at the old pin while the settings required the new one; the apply now runs the provisioner past the guard on every run, since it only runs it when a file the provisioner reads changed. And the 4c rule counted the rollback revert a retry must make as an in-branch edit, sending the worker back for review gates that were a no-op over one markdown file; that revert no longer counts when the tree it leaves is identical to the landed merge, with both shas as the evidence.
