An update-self pass on a workspace with no code of its own no longer spends half an hour testing upstream's release.

Before, the worker guide scoped the test suites to `projects_to_validate` but left the depth of everything else to judgment, so on a clean pull of a 1414-file release the worker still ran the root, system-interface and chat suites (twice, to chase flakes), built both frontends, and booted throwaway copies of the shell and the chat app, "as extra coverage". It also ran the full impact analysis, enumerating consumers and researching toolchain release notes, on a workspace whose only local change was the version history. On a two-core workspace that was 33 of the 42 minutes a user watched the update run.

Now `classify-merge` also reports the workspace's own content (`local_only`) and whether any of it is code (`has_local_footprint`), and the worker guide reads both by rule, the way the review gates already are: the impact analysis is skipped when there is no local footprint (nothing of the user's can depend on the update), each validation item runs only when its condition holds (an empty `projects_to_validate` runs no suite; a built-in service that arrived clean is left to the apply's own pre-flight; a toolchain bump with only built-in dependents needs no release-note research), and widening either is a `question` gate rather than a silent deviation. The report records which branch applied and the lead's audit requires that record.
