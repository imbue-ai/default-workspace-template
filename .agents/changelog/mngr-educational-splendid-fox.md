`update-self` now updates a workspace to the release its Mind app was built against, and says nothing about releases beyond it.

It used to take the newest release at or below the app's, and when that left something on the table it told the user "there's a newer version available, but it needs a newer Mind app", offering `--override` to take it anyway. Under release channels and staged rollout that names a version the user's own updater may not offer for days: the app said "up to date" while the workspace pointed elsewhere. The app announces its own updates; the workspace stays quiet about them.

Matching the app exactly also turns two silent substitutions into faults the agent reports: the upstream not carrying the release the app names, and the app naming no release at all (a dev build reports its branch). Neither picks a different release to update to. An operator testing a dev build passes the ref they want as `--override`, unchanged, as is the confirmation for an override the app cannot vouch for; an app on a release candidate now takes the matching candidate template, the pairing that was verified. The code calls the app's version that now -- `AppVersionUnavailableError`, `AppVersionNotReleasedError`, `--app-version` (`--ceiling` still works) -- and keeps "ceiling" only where something can pass it, in `exceeds_ceiling`.

The `minds-api` skill's create recipe reads a `branch` from `GET /api/v1/app/version` and sends it, and `migrate-workspace` step 0 says the same. Its documented body carried only `git_url`, which builds the new workspace from the template's default branch -- unreleased code, recorded as the app's release -- and an agent picking a version unaided would reach for the newest tag upstream, which the app may not support.
