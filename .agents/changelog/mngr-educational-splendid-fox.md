`update-self` no longer tells the user about template releases newer than their Mind app.

A workspace capped at its app's version used to hear that a newer release "is available upstream but needs a newer app", with a suggestion to update the app or pass `--override` to go past it. It said so even while the user's release channel had not rolled that app version out to them, when the app itself reported it was up to date. Releases above the app's version are now treated as if they do not exist: the already-on-this-release refusal and the post-update message never name one, the refusal for an app older than every release no longer suggests `--override`, and a workspace whose own update flow predates the cap is moved to the capped release without being asked about the newer one it picked. `resolve-target` drops the `latest_available` and `held_back_by_ceiling` output fields. The Mind app announces its own updates on the user's channel.

The `minds-api` skill's create recipe now sends a `branch`, read from `GET /api/v1/app/version`, and `migrate-workspace` step 0 says to do the same. The documented body carried only `git_url`, and an omitted `branch` means the repository's own default branch, so the new workspace was built from whatever that branch held that day -- unreleased code, stamped with the app's release anyway, since the recorded version falls back to the app's own when no branch was named -- while an agent left to pick a version on its own would reach for the newest tag upstream, the release the app may not support yet.

`update-self` now targets the release the Mind app was built against, rather than the newest release at or below it. The two answers were the same whenever the app's tag was in the upstream, which is every release the app has ever shipped; where they differed, the old rule quietly substituted a release nobody had verified with this app. When that tag is missing -- or the app names no release at all, as a dev build does -- `resolve-target` now fails and says which it was, and the skill reports it as a fault rather than updating to something else. An operator testing a dev build passes the ref they want as `--override`, which is unchanged, as is the confirmation for an override the app cannot vouch for. An app on a release candidate now takes its workspace to the matching candidate template, the pairing that was actually verified, instead of the stable release before it.
