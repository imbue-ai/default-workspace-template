Worker dispatch no longer silently loses the worker's report when a task file was authored without shell expansion.

A task file written with the Write tool rather than the documented heredoc carried a literal `lead_agent: $MNGR_AGENT_NAME`, so the worker had no valid address to rsync its report to: it never reported back, and the lead's poll waited out the full timeout with no error. `create_worker.py launch` now stamps `lead_agent` from the launching agent's own `MNGR_AGENT_NAME` before provisioning, overwriting whatever the file holds -- the agent that launches is the one that polls for the report, so its identity is authoritative. Outside an mngr agent (no `MNGR_AGENT_NAME`, e.g. a manual invocation) the file's own value is used as a fallback, and an unresolved one fails fast with exit 2 instead of creating an unaddressable worker.

Task-file authors no longer set `lead_agent` at all. The field is gone from every task-file frontmatter template and from the prose that listed it as a reporting field, across launch-task, crystallize-creation, update-creation, heal-creation, update-system-interface, use-ai-integration, migrate-workspace, publish-inspiration, and update-self. `finish_report_path` stays author-supplied.
