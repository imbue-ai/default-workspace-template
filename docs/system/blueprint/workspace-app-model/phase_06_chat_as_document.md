# Phase 6: chat as a document

Contracts: [contracts.md](contracts.md) sections 4.3 (chat row), 10, and 11.
After this phase every chat renders inside an iframe at the `chat` origin, served by the same system-interface process, and behaves as it did before.
This file describes what landed, as amended after the implementation and its review passes.

## Goal

Split the chat pages and their bundle out of the shell's document and serve them at a registered `chat` origin from the existing process, with the instances API implemented over the existing agent manager, so phase 7 can make the shell generic with chat already an ordinary app.

## Behaviour

- The chat document is one page per agent, loaded once per tab and kept alive by the live-surface registry exactly as service iframes are; its frame carries `data-service-name="chat"` and the chat's live key.
- The transcript's scroll management keys its visibility on the page's own layout (`isFrameRendered`: the document's root has a height), not on `shell:shown` and `shell:hidden`: hiding the pane drops the frame's layout in the same pass that the scroll container starts reporting zero sizes, whereas the shell's messages arrive a redraw later, and a transcript redraw in between (a streamed event) would otherwise run against a zero-height element and lose the reader's place. The shell's messages feed presence.
- Every request reaches the chat app by path, never by origin label: the desktop client's forwarder replaces the `Host` header with the backend's before handing a request over, and every loopback caller (the evals bridge, the update probes, `curl`) has no label to send. The chat pages, `/_instances`, and the API routes only the chat app serves go to it; everything else, `GET /api/agents` and the three verbs included, goes to the shell. The chat origin still exists in the browser (a separate origin, cookies, and storage for the frame), so the relay's origin checks and the sandbox hold.
- Presence: the page posts `hidden` when the shell's handshake lands (it may have loaded into a background tab), `visible` on `shell:shown`, `hidden` on `shell:hidden`, `closed` on `pagehide`, and a heartbeat of its current state every sixty seconds; a page visited directly, with no shell, follows the document's own visibility under a fixed client id. A subagent view posts no presence: the tracker keeps one report per chat and client, so a second page of the chat in the same client would overwrite the chat page's own, and the dock's chat panels alone counted before the split. The prioritizer treats an agent as open while any client has unexpired presence and visible while any client's last state is `visible`; the send route records `messaged`.
- The send path records the message for the client-activity log using the `clientId` and `viewId` from the handshake, adopted into the page's client identity.
- Permission cards: the chat page's embed endpoint sends `minds:open-request-modal` to `window.parent`, the relay forwards it to the chrome, and `minds:permission-resolutions` comes back down through the relay to every child frame; each chat page keeps its existing per-request filtering.
- `shell:open` is implemented for the chat app's addresses in this phase (a subagent's "View conversation" and the model bar's "start a chat on another provider" have no dock to call from inside the frame); its payload carries an optional `title` hint the shell uses until phase 7 titles tabs from the inventory. Phase 7 makes the handler generic.
- The instances API answers `503` until the manager has read its agent list from mngr once (the initial discovery, or the observe stream's first full snapshot): before that the list is empty because nothing has been asked, and from phase 7 the shell would prune every chat tab against it.
- The shell still owns rename, destroy, stop, and start through the in-process agent manager in this phase; the chat row's instances API exists but the shell does not read it until phase 7. Until phase 7 every nudge lands on a route the shell does not have (a debug-level log in the nudger).
- Keyboard: the close chord keeps reaching the shell from the chrome as today (`minds:close-active-tab`); the shell sends `shell:close-request` to the active frame so the page can flush pending state, then closes the tab. There is no veto.
- The provider chooser, the launcher's provider picker, and the first-run greeting stay on the shell; the chat page renders the chooser too, for the two places a chat opens it from (the model bar's "+ Add a provider" and a provider-fault notice), and the resulting chat opens through `shell:open`.

## The instances source

Per contracts 4.3's chat row, over `AgentManager`:

- `list_instances`: every non-primary agent (key = agent id, url `/<id>`, title = the `display_name` label or the true name, status `stopped` for a dead lifecycle, else `attention` while a filed permission request awaits its verdict, else `working` for thinking or tool-running, else `idle`; lifetime `explicit`; renameable), plus a provisional record for every chat still being created (the proto agent's id and its minted display name, `attention`, `referenced`, not renameable) and the subagent records the parent pages created (key `<agent-id>.<session-id>`, title `Subagent: <description>`, `idle`, `referenced`, not renameable). `last_active` is `null`.
- `create_instance("new", {account_id?})`: `create_chat_agent` on the given or most recently used account; no signed-in account is a `409`. `create_instance("subagent", {parent, session, description?})`: the existing record, or a new one; `parent` must be a listed chat.
- `delete_instance`: `destroy_chat_agent` for an agent; drops a subagent record; a provisional key and an unknown key are no-ops.
- `rename_instance`: `rename_chat_agent`; a collision is a `409`; provisional and subagent keys are not renameable.
- `set_location`: `400`.
- Records live in memory (the manager already holds the proto agents; the source holds the subagent descriptions): a restart forgets the subagent views, and the parent's page recreates one on demand. A subagent record whose parent chat is no longer listed is dropped the next time the list is read.

## Manual verification

The e2e suites were run locally against the built bundle: two chats side by side, the transcript, composer, tool-call expansion, live streaming, queued messages, rename, view switches, and the failed-load recovery all render inside chat frames.
The live container (`just minds-start`) was deferred again, as for phases 3 to 5; the permission-card round trip through the relay is covered by `relay.test.ts` and by the mngr repo's minds e2e jobs against the paired template branch.

## Deferred

- `last_active` on chat records is `null`; the manager exposes no cheap last-transcript-event time.
- The nudge posts to a route the shell gains in phase 7.
- Deleting a provisional instance while its `mngr create` runs is a no-op; the chat appears as an explicit instance when the create lands.
