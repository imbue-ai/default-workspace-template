# The desktop interface: contracts

Every cross-cutting schema, route, message, file format, and constant that [plan-desktop-interface.md](plan-desktop-interface.md) relies on.
The vocabulary is [concepts.md](concepts.md).
Every rule here is normative; where the plan's prose differs, this file is the truth.
Wire spelling is `snake_case` in JSON bodies and files, and `camelCase` in the contract messages between the shell and a page, as today.

## 1. Identifiers

- An **app name** obeys `forward_port.py`'s rule, unchanged.
- A **desktop id** is the slugified desktop name: `^[a-z0-9][a-z0-9-]{0,127}$`, never changing after creation.
- A **window id** is `win-<16 hex>`, minted by the shell when a window is opened, never reused.
- A **launch path id** matches `^[a-z0-9][a-z0-9-]{0,31}$` and is unique within its manifest; `open` is reserved for the synthesized one.
- A **client id** is the uuid the browser keeps in local storage under `si-client-id`, held to `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`.
- A **save id** is `save-<16 hex>`, minted by a window (browser sense) for each placements save it makes.
- A **report id** is `report-<16 hex>`, minted by a window for each `client_state` report that moves its client (section 6).
- A **page id** is `page-<16 hex>`, minted once by a window as its page loads, and carried on its `client_state` reports (section 6).
- A **path** is a path under an app's origin: a single leading `/` (never `//`), at most 2048 characters, no control characters, query string allowed.
- A **title** is trimmed, at most 256 characters; empty means "use the app's display name".

## 2. The manifest (`app.toml`)

Parsed by `app_manifest` with `extra = "forbid"`.

|---|---|---|---|---|
| `name` | string | yes | | An app name; equals the `--name` at registration. |
| `display_name` | string | yes | | Non-empty, at most 64 characters. |
| `description` | string | no | absent | One non-empty line, at most 200 characters: what the app is for, in the person's terms; shown wherever the app is described to an agent. |
| `api_schema_path` | string | no | absent | A path shaped like a launch path that answers an OpenAPI document of the app's HTTP API (`/api/schema` by convention); requires `description`, which the document carries as its own (the workspace app model's contracts section 2). |

| `program` | string | no | `name` | The supervisord program. |
| `internal` | bool | no | `false` | Hidden from every open surface. |
| `system` | bool | no | `false` | Part of the workspace itself rather than an app built on it: the minds Share tab lists it under a collapsed System group instead of offering it up front, and it can still be granted on its own. The shell announces it, with `internal`, in the services event (the workspace app model's contracts section 3); an `internal` app is never listed. The share gateway admits a per-app grant on any app that is not `internal`, so `system` changes nothing there. |
| `launch_paths` | array of tables | no | `[]` | Each `{id, label, path, method?, params?, presets?, text_param?, draft_param?, mention_param?, app_params?}`; `path` is rooted with one slash (never `//`), at most 2048 characters, carries no query string or fragment, and holds nothing a URL would escape (RFC 3986 path characters only: alphanumerics, `-._~`, the sub-delimiters, `:@`, and `/`); `method` is `GET` (the default: the page itself, with the params as its query) or `POST` (the shell posts the params and answers with the page to open; post-launch-paths plan section 3); `params` is an optional array of `{name, label, required}` naming the parameters; `presets` is an optional table of fixed string name-value pairs sent with every launch, whose names may not repeat a param's; `text_param` optionally names one of the params as the one the launcher fills with typed text, and `draft_param` as the one it fills with text to be drafted, either of which makes the launch path a free-text row of the launcher (launcher-and-getting-started plan section 3.1), and `mention_param` as the one the shell fills with a mention of the person whose tray entry was clicked (the multiplayer spec, section 7.5; never a launcher row), and `app_params` (`{name, display_name}`, two of the params) as the ones the shell fills with the name and display name of the app whose window's "Chat about this app" button was pressed (section 9.2; never a launcher row); at most one of the four. The names `client_id`, `desktop_id`, and `window_path` are the shell's envelope and are refused as param or preset names. |
| `default_shortcut` | table, or array of tables | no | absent | `{launch = "<id>", mode = "focus" \| "new"}`, or several as `[[default_shortcut]]` (at least one, launches unique), each seeded in order; `launch` names a declared launch path, or `open` when the app declares none, whether or not that path takes text (a `text_param` or `draft_param`). When absent, an app a program runs gets its first launch path taking no text, no mention, and no app, or its first when every one takes one, in `focus` mode (plan section 3.6). |
| `seeds_shortcuts` | bool | no | `true` | Whether a desktop is given the app's default shortcuts by itself. `false` keeps them off every desktop (the seed of a new desktop, and the reconcile that offers a late app's shortcut, both skip the app); the launcher still lists the app, and its shortcut can be added there. |
| `launcher_rank` | integer | no | absent | At least 1; the app's place among the launcher's leading tiles. |
| `pin` | table | no | absent | `{path, style = "plain" \| "avatar", scope = "linked" \| "independent", default_mode = "bar" \| "floating"}`; `path` obeys the launch path rule; a registered, non-internal app then has exactly one pinned window on every desktop (pinned-taskbar-entries plan section 7.1). |
| `window_closed_path` | string | no | absent | A path shaped like a launch path; the shell posts every closed window of the app there (section 5.3), for an app whose resources live as long as their windows (`docs/system/specs/window-bound-resources.md`). |
| `suggestion_settings_path` | string | no | absent | A path shaped like a launch path, declared by the one app that holds the workspace's suggestion switches. `GET` there answers `{"settings": {...}}` holding `is_next_step_suggestions_enabled` and `is_new_chat_suggestions_enabled`, and `PUT` there with either switch or both changes those and answers the same. The shell's workspace routes pass a client's read and write to it (section 5.7), and ask the first registered app that declares one. |
| `message_handlers` | array of tables | no | `[]` | Each `{type, path}` or `{type, show, showing?, reload_when_raised?}`: `type` is a message type the app takes, a lowercase prefix, `:`, and a lowercase kebab-case name (at most 64 characters; `minds:focus-chat`, `open:file`), unique within the manifest and never `shell:` (the app contract's own prefix). A type names what the message means, not who sends it: the minds chrome and apps' pages send them alike (section 5.6). With `path`, a route under the app's origin shaped like a launch path, the shell posts every message of that type there. With `show`, a page template, the shell shows the page of the app it builds from the message; `showing`, a list of page templates, names the app's other pages that count as already showing it; `reload_when_raised` (boolean, default `false`) has a window the show raises at the `show` page itself reloaded, while one at a `showing` page is only raised (section 5.6). A page template is a path with `{field}` placeholders (a field name: a letter, then letters, digits, and `_`) naming the message's fields, optionally ending in a fixed query string; it starts with a single `/` or a placeholder (whose value is itself a rooted path), carries no fragment, and holds nothing a URL would escape outside its placeholders. A handler gives exactly one of `path` and `show`, and `showing` and `reload_when_raised` only beside `show`. |
| `keybindings` | array of tables | no | `[]` | Each `{id, label, default_chords?}`: an action the keyboard can trigger in the app, which the Keyboard shortcuts dialog lists for re-binding (section 5.1). `id` matches `^[a-z0-9][a-z0-9_-]{0,63}$`, unique within the manifest, and is the key a person's chosen chords are stored under, so it stays stable across releases; `label` is one line of at most 80 characters saying what the action does; `default_chords` (default `[]`, unbound) are the chords that trigger it out of the box, in the `workspace_profile` library's canonical grammar (modifiers in ctrl/alt/shift/meta order), which the app's own resolved-chords route and the shell's catalog both check. |
| `references`, `scope`, `wiring` | | | | Unchanged. |
| `preview` | table | no | the scaffold convention | How a throwaway instance boots for a preview (`PreviewSpec`; the workspace app model's contracts section 2 has the field-by-field rule): `command` (default: the program as its console script), `ports` (named free ports; `main` always), `env`, `args`, `copies` (repo-relative directories copied into the instance's scratch space, by key), `health_path` (default `/health`), `open_path` (default `/`), `open_path_takes_key`. `command`, `args`, and `env` values may carry `{port:<name>}`, `{copy:<key>}`, `{host}`, `{scratch}`, and `{registry}`; `open_path` may carry `{key}` exactly when `open_path_takes_key`. Absent, the table is `env = {<PACKAGE_UPPER>_PORT = "{port:main}", <PACKAGE_UPPER>_HOST = "{host}", <PACKAGE_UPPER>_DATA_DIR = "{copy:data}"}` over `copies = {data = "data/.apps/<name>"}`. |

## 3. The registry (`data/.state/apps.toml`)

Written only by `forward_port.py`.
Each `[[apps]]` row carries `name`, `url`, `label`, `icon`, `internal`, `program` from the registration and `display_name`, `description`, `api_schema_path`, `critical`, `stop_when_no_windows`, `uses_microphone`, `system`, `priority`, `default_shortcuts` (array of inline tables `{launch, mode}`; a row an older registration wrote may carry one `default_shortcut` inline table instead, read as a list of one), `seeds_shortcuts` (written when the manifest gives it; absent reads as `true`), `launch_paths` (array of inline tables `{id, label, path, method?, params?, presets?, text_param?, draft_param?, mention_param?}` with `params` as the array of names, `method` written when the manifest gives it, and `presets` only when non-empty), `launcher_rank`, `pin` (inline table `{path, style?, scope?, default_mode?}`, each absent key reading as the manifest's default), `window_closed_path`, `suggestion_settings_path`, `message_handlers` (array of inline tables `{type, path}` or `{type, show, showing?, reload_when_raised?}`, as the manifest gives them), and `keybindings` (array of inline tables `{id, label, default_chords}`, `default_chords` written as `[]` for an unbound action) from the manifest.
`instances`, `instances_url`, and `actions` are no longer written; a row that still carries them (an app not yet re-registered) is read with those keys ignored.
The shell validates every row on read and skips one that fails, with a warning.

## 4. Shell state files

Under `data/.state/system_interface/`, written atomically under one process-wide lock.

### 4.1 `desktops.json`

```json
{
  "version": 1,
  "desktops": [
    {
      "id": "home",
      "name": "Home",
      "color": "#2f6b4f",
      "glyph": 0,
      "wallpaper": {"kind": "bundled", "name": "apricot-coast"},
      "shortcuts": [
        {"target": {"kind": "launch", "app": "chat", "launch": "new"}, "mode": "new", "cell": {"column": 0, "row": 0}}
      ],
      "windows": [
        {"id": "win-0123456789abcdef", "app": "chat", "path": "/?chat=agent-3f2a", "title": "Plan the launch", "opened_at": "2026-09-19T14:11:02.824Z", "is_pinned": false, "scope": "linked"}
      ],
      "owner": null
    }
  ]
}
```

- `desktops` is in display order: creation order, as rearranged by the order route (section 5.2); the first is the fallback desktop.
- `color` is `#RRGGBB`; `glyph` is `0..9`; both are kept as written and drawn nowhere since the desktops phase of the multiplayer spec (its S7). `wallpaper` is `{"kind": "bundled" | "file", "name"}` or `null`, with `name` matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`.
- `owner` (default `null`) is whose desktop it is by convention (the multiplayer spec, section 8.1): a participant key for the desktop seeded for a visitor on their first arrival (section 5.5) and for one a visitor creates, `null` for the workspace owner's, which every desktop from before the key was kept is, except that the first start of a shell that keeps it gives each such desktop `users.json` (section 4.3a) records for a visitor that visitor's key, once (marked done by the `visitor_desktops_adopted` file beside `desktops.json`). "Mine" is `owner` null when the requester is the owner (under either of the owner's keys), else `owner` equal to the requester's key. A desktop whose owner has left the roster is left behind: it keeps its key, and the owner's overview lists it under "Left behind" so the owner can view and delete it. There is no access control.
- `shortcuts`: `target.kind` is `launch` (the only V1 kind); at most one shortcut per `(app, launch)`; `cell.column` and `cell.row` are integers at least 0.
- `windows` is in opening order; ids are unique across every desktop; `path` and `title` obey section 1; `is_pinned` (default `false`) marks the app's pinned window, and `scope` (default `linked`) is `linked` or `independent` (pinned-taskbar-entries plan section 3.2). An independent window's `path` stays its home path.
- A file whose `version` is not 1, or that fails validation, is logged and treated as absent: the shell then creates the default desktop. The old `projects.json` is never read. A desktop that still carries the retired `sharing` key is read with the key dropped, and so is a window that still carries the retired `is_settling` key.

### 4.1a `default_shortcuts_offered.json`

`{"version": 2, "targets": [{"kind": "launch", "app": "chat", "launch": "root"}, {"kind": "launch", "app": "screen", "launch": "browser"}, ...]}`: the target of every default shortcut the shell has offered (plan section 3.2), sorted by app and launch.

- A desktop's creation (the default desktop's seeding, `POST /api/desktops`, a visiting user's desktop) adds the targets of the default shortcuts it was made with. The reconcile that runs on every read of the desktops and after every change of the registry's rows adds each default shortcut target it has just offered to every desktop.
- A listed target is not offered again, so a default shortcut the user removed stays removed, even when its app deregisters and registers again (a target with no shortcut left on any desktop has nothing dropped below, so it stays listed); an app that declares a further default shortcut is offered only that one.
- The same reconcile drops, from every desktop, each shortcut of an app no registry row names, since nothing would run it (the update-self apply removes the row of an app the release retired, and a preview's teardown its own), and takes the dropped shortcuts' targets off the file, so each is offered again if its app registers again. A registry with no rows drops nothing.
- A desktop created while no other desktop stands, such as the default desktop seeded over a `desktops.json` read as absent (section 4.1), starts the file over: it then lists only the targets of the shortcuts that desktop was made with.
- A version 1 file (`{"version": 1, "apps": [...]}`, written while an app had at most one default shortcut) reads as each listed app's first default shortcut target, and is rewritten as version 2 on the first read with registry rows.
- A missing file, or one of another version or that fails validation (logged), reads as listing the first default shortcut target of every app with a shortcut on any desktop, and the next reconcile writes it; with no `desktops.json` either, the default desktop's seeding writes it.
- `desktops.json` carries none of it.

### 4.1b `desktop_themes.json`

`{"version": 1, "default": "<theme id>" | null, "desktops": {"<desktop id>": "<theme id>"}}`: the workspace's default theme, and each desktop that wears another (Desktop settings > Theme). Themes themselves are folders (`docs/system/blueprint/workspace-themes/`, section 3).

- Kept beside `desktops.json` rather than in it: a shell from before themes still reads that file after a rollback, and its records refuse a key they do not know.
- A desktop missing from `desktops` wears the default; a `default` of null is the standard theme. Setting a desktop back to the default drops its entry, and deleting a desktop drops its entry too. A desktop id comes back after a delete, so creating a desktop drops any entry its id left behind (a desktop a shell from before themes deleted), and seeding the default desktop drops every desktop's entry.
- A missing file, or one whose `version` is not 1 or that fails validation (logged), reads as the standard theme everywhere.
- A theme that is no longer available (its folder removed, or failing validation) is worn as the standard theme; the file keeps the choice, so the theme comes back when its folder is fixed.
- The desktop record on the wire (section 5.2) carries its own choice as `theme`, or null when it wears the default.

### 4.2 `placements/<desktop_id>/<client_id>.json`

```json
{
  "version": 1,
  "updated_at": "2026-09-19T14:12:40.001Z",
  "placements": [
    {"window_id": "win-0123456789abcdef", "frame": {"x": 0.05, "y": 0.06, "width": 0.6, "height": 0.7}, "state": "NORMAL", "is_minimized": false}
  ]
}
```

- `placements` is back to front; last is on top.
- `frame` values are floats in `0..1` with `x + width <= 1` and `y + height <= 1`; `state` is `NORMAL`, `SNAPPED_LEFT`, `SNAPPED_RIGHT`, `MAXIMIZED`, or `FULLSCREEN` (the window fills the whole viewport, taskbar and title bar included; the Screen spec's L2 layer, section 12). A file written before `FULLSCREEN` existed never carries it, and a reader without it refuses a file that does, as it refuses any state it does not know.
- `is_detached` (default `false`) marks a window pulled out into a desktop window of the embedding chrome's own (mngr's `specs/pull-out-window/spec.md`): the desktop draws nothing for it, its frame kept for a return, and its page is shown there; a file without the key reads as attached, and a writer without it drops the flag on its next save. Orthogonal to `state` and `is_minimized` (a detached placement that is also minimized is still a pulled-out window, its own desktop window on screen; the window stays out); a detached placement is never the focused one.
- A placement naming a window the desktop no longer holds is dropped on read.
- A window with no placement reads as `{frame: cascade(n), state: NORMAL, is_minimized: true}` at the start of the list (the bottom of the stack), where `n` is the count of stored placements. A pinned window with no placement is answered by the layout route as `{frame: {x: 0.05, y: 0.05, width: 0.9, height: 0.9}, state: NORMAL, is_minimized: true}` at the start of the list instead (pinned-taskbar-entries plan section 3.2), unwritten until the client saves or an op edits that client's layout.
- The old `layouts/` directory is never read.

### 4.3 `clients.json`

`{"version": 3, "clients": {"<client_id>": {"active_desktop": "<desktop_id>", "last_seen": "<RFC 3339>", "user_id": "<user_id>" | null, "participant": "<participant key>" | null, "entries": {"<app>": {"mode": "bar" | "floating", "style": "plain" | "avatar", "position": {"x": 0.9, "y": 0.85} | null, "is_window_shown": true}}, "shown_history": ["<window_id>" | "home", ...], "desktop_revision": 0, "desktop_moved_by": "<page_id>" | null, "viewport": {"width": 1440, "height": 823.5} | null}}}`.
`user_id` is the signed-in visitor the client last arrived as (section 5.5), null for the owner or an anonymous client; an entry without the key reads as null. `participant` is who the client last arrived as under the multiplayer spec's keys (`user:<user_id>`, or `owner` for the owner of a workspace that has not shared; the spec's section 4.1), null for a record from before the key was kept. `entries` (default `{}`) is how the client shows each pinned entry.
`desktop_revision` (default `0`) counts the moves of `active_desktop`: every write that changes it adds one, as does a report the shell lands off a deleted desktop (section 6) even when the stored desktop stays, under the same lock as the write, so the revisions order the moves as they were written.
`desktop_moved_by` (default null) is the page whose report wrote the current revision, null when an op or an arrival did; the shell keeps it to order a page's reports against the moves it had not heard of (section 6), and does not answer it.
`shown_history` (default `[]`) is what the client's phone layout showed (`plan-phone-interface.md`), most recent last: window ids, and `"home"` for the home grid, each at most once and at most 20; a close drops the window from every client's history.
`viewport` (default null) is the backdrop size the client's desktop layout last reported (`POST /api/clients/<client_id>/viewport`, section 5.4), in CSS pixels: the box its window frames are fractions of, which a window viewing one of the client's desktops draws the layout at (the multiplayer spec, section 8.3); null for a client that never reported one (a phone, a pulled-out window, an older shell).
A version-1 file (with `device_kind` and `active_view`) is read with `active_view` taken as the active desktop when a desktop of that id exists, else the first desktop, and then read as a version-2 file.
A version-2 file (written while a pinned entry could float by default, and a drag of one saved that default mode as the client's own) is read with every client's entries in `bar` mode with a null `position`, and rewritten at version 3 on the next write.

### 4.3a `users.json`

`{"version": 1, "users": {"<user_id>": {"desktop_id": "<desktop_id>", "desktop_name": "<name>", "email": "<email>" | null, "display_name": "<name>" | null, "last_seen": "<RFC 3339>"}}}`.
One entry per signed-in visitor the shell has made a desktop for (plan section 3.10): the desktop and its name as of the user's last arrival (a rename is picked up by the next arrival), and the identity as of that arrival.
A user id matches `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`, as the identity header carries it.

### 4.4 `window_paths/<client_id>.json`

`{"version": 1, "windows": {"<window_id>": {"path", "title"}}}`: the client's own path and title for each independent window, written by that client's location reports and an agent's `navigate` targeting it; entries for windows since gone are dropped on read, and the file is pruned with the client.

### 4.5 `avatar_selection.json`

`{"version": 1, "design": "<design id>"}`: the workspace's avatar design; absent or unreadable reads as the default (`imbue-character`). The registered designs live at `data/.apps/system_interface/avatars/catalog.json` (`docs/system/avatar-designs.md`).

### 4.5a `tour.json`

`{"version": 1, "is_seen": true | false, "resume_index": <int> | null, "is_finished": true | false}`: whether the show-around tour has started in this workspace (by itself or from the launcher), the card it resumes at after the agent's reply interrupted it (`null` when nothing waits to resume), and whether it has nothing left to show (`false` in a file written before the field); absent or unreadable reads as unseen with nothing to resume in a workspace the bootstrap marked new on its first boot (an empty `offer_tour` file beside it), so a new workspace offers the tour once; in any other workspace (one that already existed when an update brought the tour in) it reads as seen, and the tour runs only from the launcher. The tour begins the first time the workspace's agent goes to work (the avatar's `working` mood, or a page's `shell:agent-working`, section 7), after `tour_start_ms` of work when the page's query string names it, at once otherwise; the agent going idle while a card is up interrupts the tour, whose Next then shows a pause notice and records the card that would have come next. It neither begins nor resumes by itself while any page's last `shell:first-conversation-step` (section 7) says the workspace's first conversation is still following its script; a page saying that conversation is over lets it begin at once when an agent is already at work, and otherwise it begins the next time one goes to work. The launcher's row starts it whatever a page says, and a record is settled as finished whatever a page says.

`is_finished` is the page's to decide and to write; a tour that waits to resume is not finished, and neither default (unseen, or seen in a workspace the tour was never offered in) is. The page writes it true when Done on the last card or Exit walkthrough is pressed, and the workspace owner's page writes it for a record it reads as seen with nothing to resume (a tour a reload cut off, or a workspace the tour was never offered in), when it is a page the tour could begin on (the desktop layout, not a pulled-out window, so a second page loading beside a tour on screen does not end it); every other write carries the value the record already had. Every write of a record with `is_finished` true also sets the `tour_finished` marker (section 4.5b), which no later record takes back.

As the tour's last card shows (not when its Done is pressed), and when Exit walkthrough is pressed on a card before it, the page relays a message of type `onboarding:show-checklist` with no fields, as its own (`sender` `system_interface`), through `POST /api/embedder-messages` (section 5.6), and puts each window a `show` handler answers with at the frame `{x: 0, y: 0, width: 0.3, height: 0.85}`: normal, shown, and on top of this client's stack, with no other window moved or resized. It first reads the shell's layout until a read of its own is the one it holds (at most three reads), so the frame is set over the placement the show wrote. The shell names no app: the message goes to whichever app registered the type, and when none did (or in a preview or a solo shell) nothing happens. A relay that fails places nothing and is logged to the page's console, with no notice: nobody asked for the window by hand. A window the show found on another desktop is left as placed. The pause notice opens nothing, and a tour run again from the launcher does the same as the first.

### 4.5b The onboarding markers (`data/.state/onboarding_activity/`)

Beside the shell's own directory, not in it, and shared with the rest of the workspace: one empty file per fact about what the workspace's owner has already done, set once and never removed, whose modification time is when it was last set (`system/libs/onboarding_activity`, which resolves the directory to the main checkout's `data/` from a git worktree and lets `$ONBOARDING_ACTIVITY_DIR` override it). The shell sets two of them and reads none:

| Marker | Set when |
|---|---|
| `tour_finished` | `tour.json` is written with `is_finished` true |
| `phone_layout_used` | the workspace owner's client reports what its phone layout shows (`POST /api/clients/<client_id>/shown`); a visitor's report sets nothing |

The other markers (`second_chat_started`, `permission_request_filed`, `app_build_started`) are set by their own writers, which that library's README lists. A marker that cannot be written is logged, and the request that noticed the fact answers as it would have.

### 4.6 Wallpapers

Bundled wallpapers ship at `imbue/system_interface/static/wallpapers/<name>.<ext>`; file wallpapers live at `data/.apps/system_interface/wallpapers/<name>.<ext>`.
Accepted extensions: `png`, `jpg`, `jpeg`, `webp`.
The `name` of a wallpaper reference is the file name without its extension.

## 5. Routes

All on the shell (`MINDS_WORKSPACE_SERVER_URL`, default `http://127.0.0.1:8000`).
Every error body is `{"detail": "<message>"}`.
`POST /api/client-activity`, `POST /api/bubbles`, `POST /api/chats-activity`, and `POST /api/layout/broadcast` are loopback-only (`403` otherwise); every other route is for browsers too.

### 5.1 Page and app routes

Unchanged: `GET /` and the SPA catch-all (with `X-Frontend-Built`), `/assets/<path>`, `/favicon.ico`, `GET /api/health`, `GET /_static/app_contract.js`, `POST /api/apps/<name>/stop`, `POST /api/apps/<name>/start` (refused for critical apps; a stop leaves the app's port held by the shell, which starts the app again on the first request, and a start releases it first and counts against the app's wake budget (which only wakes the app did not come up from spend), answering `502` once it is spent: `docs/system/specs/stop-when-no-windows.md`, sections 5.4 and 5.5), `POST /api/client-activity`, `/api/ws`.
Added by the stop-when-no-windows spec (section 7): `POST /api/apps/<name>/quit`, refused as a stop is (`403` in a preview, `404` unknown, `400` for a row with no program, a critical app, or a row inside a critical app's program), which closes every window of the app on every desktop through the ordinary close (a pinned window stays), stops its program at once, and answers `{"name", "is_running"}`.
Presence (the share identity spec, `specs/share-identity-and-presence/spec.md` in the mngr repository, section 4.7, and the multiplayer spec's section 4.3): `POST /api/presence/heartbeat` takes `{"input_age_seconds": <number from 0 to a century of seconds> | null}` (how long ago the page last saw keyboard or pointer input, which the shell stamps against its own clock, so a skewed page clock pins nobody active or idle; an age beyond the bound is `400`, like any body off this shape; a page from before the age may still send `last_input_at`, an RFC 3339 moment, which is accepted and clamped to the shell's now; an older page's other fields are ignored, and no body at all reads as none), plus `client_id` (the page's own) and `input_windows` (`[{"window_id", "app", "kind": "input" | "focus"}, ...]`, the windows whose pages reported input since the last answered heartbeat, which section 6's `window_input` records; a `client_id` off the rule, a field or an entry off its shape, or no `client_id` at all records presence and drops the reports, never the heartbeat), and reads the requester's `X-Imbue-Identity` header. It touches the mtime of `data/.state/presence/users/<id>.json`, where `<id>` is the header's `user_id`, or `owner` for the owner of a workspace that has not shared, writing the file with `{"user_id", "email", "owner", "first_seen", "last_input_at"}` on first sight and rewriting it when the snapshot or the newest input time changes (a late heartbeat never moves that time backwards; a heartbeat that moves it pushes `roster_updated`, section 6), and answers `{"identity": {"owner", "user_id", "email", "agent_id", "agent_name", "granter"}, "participant": "<participant key>"}`, the key being `user:<user_id>` or `owner`. A visiting agent's request (an `agent_id`, no `user_id`) answers `204` and records nothing: its presence is the gateway's last-seen record. A user is connected while that mtime is within 70 seconds, and the file is never removed. `GET /api/presence` answers `{"users": [present_user, ...]}`, one entry per connected account (the `owner` record is left out, since it names none): `user_id`, `email`, `display_name`, `profile_picture_url`, `owner`, `first_seen`, `last_seen` (the mtime), `last_input_at`. `display_name` and `profile_picture_url` are the account's profile as imbue_cloud holds it (`null` when it has none or cannot be reached): fetched from `GET {SHARE_BROKER_URL}/users/<user_id>/profile` (public; answers `{"user_id", "display_name", "profile_picture_url"}`), the broker named in `data/.secrets/share.env`, with a 2 second bound, and cached -- answers and failures alike -- for 5 minutes under `data/.state/presence/profiles/<user_id>.json`. `GET /api/presence`, the heartbeat, and `GET /api/roster` never wait on that fetch: they answer from the cache as it stands (a stale entry included while the workspace is still shared), fetch what is missing or stale on one background thread, and push `presence_updated` and `roster_updated` again when that changed what the cache answers. There is no leave route: a page that goes away simply stops heartbeating.
The roster (the multiplayer spec, section 4.2): `GET /api/roster` answers `{"participants": [participant, ...]}` in display order (the owner, then every account the workspace-level grants of `data/.secrets/share_grants.toml` name, then every account a workspace-level domain grant admitted -- the presence records whose email's domain the grants still name, since a domain grant names nobody -- then every invited email, then every visiting agent of `data/.secrets/agent_access/grants.toml`, then the workspace's own agent), each `{"key", "kind": "person" | "invited" | "visiting_agent" | "workspace_agent", "display_name", "profile_picture_url", "email", "handle", "color", "is_owner", "is_connected", "last_seen", "last_input_at", "is_admitted_by_domain"}`. The owner's key is `user:<user_id>` once their heartbeats have named an account and `owner` otherwise; a person's name is their profile's (else the name their arrival recorded, else what the Imbue Studio desktop recorded of the account in `data/.secrets/share_identities.json` when it granted them, `{"version": 1, "identities": {"<user_id>": {"email", "display_name"}}}`, written beside the grants with every save, else their email's local part, else `Guest`), and their picture, when the profile names one, is the shell's own `GET /api/roster/<key>/picture?v=<version>` (the bytes fetched once from the profile's URL with a 5 second bound and kept under `data/.state/presence/profiles/<user_id>.picture.json` until the profile names another URL, a failed fetch remembered there for the profile cache's 5 minutes; `v` is a digest of that URL, so a newer picture is a newer address and an answer under the current version is cached for good, one under an older version or none being the same bytes uncached; `404` for a key that is not a listed person's or a person with no picture; the answer carries `X-Content-Type-Options: nosniff` and the image policy of the avatar and theme icon routes, since the bytes are an outside host's), since the pages' content security policy admits no outside image; a visiting agent is connected while the gateway's `data/.state/agent_access/last_seen.json` saw it within the 70-second window; the workspace agent is named after the workspace and pictured by the selected avatar's `icon.png`. `handle` is the display name with runs of whitespace as one hyphen and anything outside `[A-Za-z0-9._-]` dropped (an invited email's local part), a later collision suffixed `-2`, `-3`, ... after `agent`, which the workspace agent holds. `color` is one of eight, by the key's hash. The page knows its own entry by the `participant` its heartbeat answered.
`POST /api/client-activity` takes `{"client_id", "desktop_id", "kind": "message", "app", "key", "text"}`: the client that sent a message to an app's page, the desktop it was on (from the shell's handshake), the app, the page's marker (a chat id; `""` for a page without one), and the text; the shell appends it to the client-activity log as a `message` event (the text truncated), which is what `workspace-layout context` and an op's requester attribution read.
The tray's feed (the multiplayer spec, sections 6.4 and 6.5; the models are `workspace_layout.feed`): `POST /api/bubbles` takes `{"speaker", "chat_id", "chat_title", "text", "message_id", "mentions": [key, ...], "kind": "message" | "notification"}` (who said what, by participant key, in which chat, the text as the bubble shows it, the message's id, the people it mentions, and whether it is a message somebody sent or a chat's notification to the user, `message` when absent), which the shell broadcasts as `bubble` (section 6) to every window but the speaker's own clients: the clients whose records carry the speaker's key, and for the owner (a speaker named by the owner's account key or by the synthetic `owner` key) the ones recorded under either. `POST /api/chats-activity` takes `{"chats": [{"chat_id", "title", "status": "working" | "background" | "idle" | "attention" | "stopped" | "error", "kind": "agent" | "room"}, ...]}`, every chat as the chat app lists it, which the shell keeps (the last report, sent to every window that connects later) and broadcasts as `chats_activity`. Both answer `204`, `400` for a body off these shapes, and `403` off loopback; the chat app posts them best-effort and never waits on the answer.
Removed: `POST /api/apps/<name>/changed`, `POST /api/apps/<name>/instances` and every `/instances/<key>/...` relay route, `POST /api/tabs/<tab_id>/instance`, every `/api/projects/...` route, `GET` and `POST /api/layouts/<view_id>`.
Added: `GET /api/updates/pending` (`200 {"notice": notice | null}`: the update notice -- the rollback point the last `update_self.py apply --keep-rollback-point` kept, whose fields the workspace app model's contracts section 5 lists -- or `null` when none is kept); `POST /api/updates/pending/confirm` (runs `update_self.py confirm-last`; `204`; `409` when none is kept or while a rollback runs; `500` naming a failed script); `POST /api/updates/pending/rollback` (starts `update_self.py rollback-last` detached, its output going to `data/.state/update-apply/rollback-last.log`, and answers `202` once the script has written its first progress into the record, so a second window's press reads that progress rather than starting a second script; `409` when none is kept, one is already running, the point was already taken back, or the script refused, in its own words; `500` when the script could not be started or wrote no progress within 30s). An unknown path under `/api/` answers `404 {"detail": "No such API route: /<path>"}` rather than the app shell.
Keyboard shortcuts (the user-profile-state spec in the mngr repository, sections 9.3 and 10; the files and the delivery flow are the shell's README): `GET /api/keybindings/me` answers the requester's resolved chords for the shell's own actions `{"app", "chords_by_action"}`, the route every built-in app that declares `[[keybindings]]` (section 2) serves at its own API base; `GET /api/keybindings/catalog` answers `{"apps": [{"app", "display_name", "actions": [{"id", "label", "default_chords", "chords", "source": "default" | "account" | "unsent" | "workspace"}, ...]}, ...], "is_owner", "can_save_everywhere", "has_pending_permission", "unsent": [{"app", "action", "chords"}, ...]}`, the shell's own actions and every registered app's `keybindings` read from its registry row (so an app that is stopped is listed; an app that declares none, or a row whose default chords are off the grammar, is left out) resolved for the requester, with the owner's undelivered "everywhere" saves (`[]` for a visitor); `POST /api/keybindings` takes `{"app", "action", "chords", "scope": "workspace" | "account"}` and answers `{"chords", "delivery"}`, the chords in the canonical spelling and, for an `account` save, the delivery's `{"status", "detail"}` (`DELIVERED`, `NOTHING_TO_DELIVER`, `PERMISSION_PENDING`, `PERMISSION_REQUIRED`, `UNAVAILABLE`, or `UNREACHABLE`; `null` for a `workspace` save), `400` for a chord off the grammar or an action no app declares, `403` for a requester with no account or a visitor's `account` scope; `POST /api/keybindings/reset` and `POST /api/keybindings/discard` take `{"app", "action"}` and drop the requester's override of the action, or (owner only, `403` otherwise) one undelivered "everywhere" save; `POST /api/keybindings/deliver` (owner only) takes `{"resolution"?, "resolutions"?: [{"request_id", "resolution": "granted" | "denied"}, ...]}`, the verdicts the page observed, and retries the undelivered saves. The three answer the delivery's `{"status", "detail"}`. Every read resolves for the requester's `X-Imbue-Identity`, and every write announces `keybindings_changed` (section 6).
A preview shell (`system-interface --preview`, booted by `preview_app.py` over a seeded copy of the state directory and a copied registry) answers `POST /api/apps/<name>/stop`, `POST /api/apps/<name>/start`, `POST /api/apps/<name>/quit`, and the two notice verbs with `403 {"detail": "This is a preview of a proposed change; it cannot change the live workspace."}`; every other route edits its own copy or reaches only its own windows, so it stays live. Its page carries the meta tag `system-interface-preview` (content `true`), which the frontend reads to offer no Quit, and never the staleness tag. A preview shell neither parks ports nor stops or wakes apps: a POST launch of a stopped app from a preview fails as one to any unreachable app does.

An open with `is_new` writes the requesting client's placement (section 10, cascade) on top of its stack, minimized when `minimized` is true (a phone's opens: no other client's layout gets a placement, so the window reads as minimized for everyone), and broadcasts `placements_updated` for that client, and `desktops_updated` for everyone.
An open answered with `is_new: false` restores and raises the existing window in the requesting client's layout, writes it, and broadcasts `placements_updated` for that client.
A close drops the window from every layout file of the desktop and broadcasts `desktops_updated` and one `placements_updated` per rewritten layout.
After that, when the window's app registered a `window_closed_path` and the app is running (a stopped app's port is the shell's own parker, which would wake the app to tell it a window closed), the shell POSTs `{"path", "window_id", "desktop_id"}` to the app's `url` plus that path from a thread of its own, with a 2 second timeout, and neither waits for nor acts on the answer; a deleted desktop's windows are posted the same way. An app may take the posted `path` as proof that a window showed the resource it names (the terminal marks it window-seen before sweeping), while reading what is shown now from `GET /api/desktops`.
A close is also what starts the clock of the stop-when-no-windows spec (section 6): an app that declares `stop_when_no_windows` and has no window left on any desktop is stopped 60 seconds later, once a client has arrived at the shell since it started, unless it is not `internal` and a per-app share grant names it (its visitors reach it without the shell, so their use leaves no window to count).
A location that changes nothing writes and broadcasts nothing.

When the recorded desktop no longer exists, or the desktop under its id is not the user's (its `owner` is not their key: a desktop the owner makes after deleting theirs can take the id), the shell seeds another the same way and answers the recorded one's name (as of the user's last arrival) as `replaced_desktop_name`, which the page shows once (`data-replaced-desktop-notice`).

### 5.6 Messages

`POST /api/embedder-messages` takes `{"type", "client_id", "payload", "sender"?}`: a message a client's shell page received, its type, that client, the message's other fields, and who sent it (`embedder` for the minds chrome, else the name of the app whose frame sent it; `embedder` when absent; for logs only).
The route keeps its name from when only the minds chrome sent messages; a type names what a message means, and the chrome and apps' pages send them alike.
The shell page posts every message the chrome sends it, once, when some app's `message_handlers` names its type, and posts nothing otherwise; a solo page (section 9) posts none of the chrome's messages, since its client is the main window's; either way it still rebroadcasts every such message to its child frames unchanged (the workspace app model's contracts section 11).
It posts every message a page sends it with `shell:message` (section 7), whatever its type, from a solo page too: the client is the main window's, so what a handler shows lands on that client's desktop in the main window (or stays in its own window when it is popped out, section 8).
Before it posts a message it saves a layout change of its own that is still waiting to be saved (the raise of the window whose page was clicked), so a window a handler brings forward is raised over that change and ends in front.
A failure reaches the user as a notice carrying the answer's `detail`, and a page shown while the client has only pop-outs open (`has_no_desktop_window`) as a notice to reopen the main window.
For every registered app whose row names the type, the shell delivers the message by the handler's form, every `path` handler first and then every `show` handler, each in registry order:

- `path`: the shell posts `{"type", "client_id", ...payload}` (the message itself, with the client added) to the app's `url` plus `path`, with a 10 second timeout, and reads no payload. An app that refuses says why as the `detail` of a JSON answer (as a launch path's refusal does), which the shell quotes; any other answer's text is quoted as it is.
- `show`: the shell builds the page from the handler's template, and each `showing` page from its own, replacing every placeholder by the payload field it names, which must be a string, percent-encoded one path segment at a time (as `encodeURIComponent` encodes: a space as `%20`, `?` as `%3F`, `#` as `%23`, non-ASCII as its UTF-8 bytes; a value ending in `/` that the template follows with `/` joins it as one slash, so `{path}/` of `/` is `/`), and the result must be a rooted path. It then runs the `show` op (section 8) in-process for the declaring app and the message's client, with that page, those `showing` pages, and no `repoint`, as a requester `{"app": <the declaring app>, "marker": ""}`; when the handler's `reload_when_raised` is true and the op raised a window at that page itself (`shown` is `raised`, and the window was not at one of the `showing` pages), it then sends that client's windows a `refresh` `layout_op` naming the window (`{"window"}`), so a page whose content changed under the same path shows it now. A missing or non-string field, or a page that is not rooted, is that handler's refusal, and so is a `show` the op refuses (an unknown client, say); the other handlers still get the message.

It answers `200 {"type", "deliveries": [{"app", "status", "detail", "shown", "has_no_desktop_window", "window_id"}, ...], "detail": null}` when every handler took it (`detail` empty; a `show` delivery's `status` is `200` and it carries the op's `shown` and `has_no_desktop_window` (section 8) and the window's id, which are `null` for a posted message); `502` with the same body and a `detail` naming each app that answered otherwise, could not be reached, or could not have its page built or shown (its `status` then `null` unless the app answered); `404` when no app handles the type (`detail`: `Nothing in this workspace handles '<type>'`); `400` for a type off the manifest rule, a bad client id, a sender that is not an app name, or a payload carrying `type` or `client_id`; and a preview shell `403`, its page posting none of the chrome's messages (the workspace app model's contracts section 6).

The shell page announces `opensLinks: true`, `opensCustomSchemeLinks: true`, `reportsChatOnScreen: true` and, when the embed contract it is built with is version 16 or later (whose validator lets a `minds:focus-chat` with no `chatId`, which brings the chat root up, reach it), `reportsProviderChooserOnScreen: true` with `minds:workspace-ready` (the Imbue Studio embed contract, version 16; a chat's own page sends `minds:chat-on-screen {chatId}` once it is shown and its transcript is drawn, which the chat root and the shell forward up unchanged, and the chat root sends `minds:provider-chooser-on-screen {}` once its provider chooser is drawn while it is shown, which the shell forwards up unchanged) and so takes `minds:open-link {url}`: a popup (or an external page replacing a frame) a page of this workspace asked for, which the desktop app turned away from a window of its own (the workspace link routing plan). It classifies the URL with `workspace_ui`'s `links.ts`: a `file:` URL on this machine is delivered as `open:file` above, with sender `embedder`; an external link (web, `mailto:`, `tel:`, or custom-scheme: any scheme a browser does not load itself, such as `slack:` or `vscode:`) is delivered as `open:web` for a web link and `open:<scheme>` otherwise (`open:mailto`, `open:tel`, `open:slack`) `{url}` above to the app registered for it, and with none goes back out with `minds:open-external {url}` (sent to a chrome whose `minds:embedder-capabilities` says `opensExternalLinks: true`, and for a custom-scheme link `opensCustomSchemeLinks: true` too, or that handed the link over itself; otherwise the page opens a browser tab, except that a custom-scheme link facing a chrome that opens external links but not custom-scheme ones (an older desktop app, which shows a popup of one as an empty window) navigates the page itself to it, which opens no window and leaves the page where it is), synchronously within the click; a scheme the message-type rule cannot name (one with a `+` or `.`) has no app to take it; a file and line or a host and port written without a scheme (`q4.md:12`, `localhost:3000/app`), which parses as a custom-scheme URL, is refused as unroutable, as is any custom-scheme link of that shape (`sms:5551234`; `sms:+15551234` stays a link); a local URL whose host is `<x>.localhost` (any port), `<x>` an openable (non-internal) app's label or else name, opens as that app's window at the URL's path and query, raising one already there, and so does one on a loopback host name (`localhost`, `127.0.0.1`, `[::1]`) at the scheme and port of an openable app's registered backend `url`; any other local URL is delivered as `open:url` above, with sender `embedder`; one of this workspace's app addresses (`<label>.<coordinate>`, the label resolved to its openable (non-internal) app by the registry; the coordinate the page's own, or the domain the workspace was last shared under, read off the apps' `share_url`) opens as that app's window at the address's path and query, raising one already there; another workspace's address, or one no app is at, is refused with a notice. A window already there that the client has popped out (section 8) is raised in its own window rather than brought back onto the desktop, as an `open` op raises it. A path at the app's pin path with a query string or fragment of its own (the chat's `/?chat=<id>`) is shown through the show route (section 5.3) instead, with the pin path as the one page to repoint, so it lands in a window already at that path, else the app's window on screen at its pin path, else its pinned window, and opens a window only when the app has none of these.

The shell also sends `minds:highlight-chrome {anchor}` (contract version 9) while a show-around tour card, or a page's coach card (`shell:show-coach-card`, section 7), is about a control of the Imbue Studio chrome: `anchor` is `workspace-switcher`, `permissions`, `settings`, `share`, or `help`, and `null` clears the ring when the card goes. It is fire-and-forget; the card's words never depend on the ring, so a chrome that does not know the message, or a plain-browser visit with no chrome, reads the same.

### 5.7 Workspace routes

The routes under `/api/workspace/` are for a client outside the workspace (the Imbue Studio desktop app, through mngr's forward, and the hosted web client), not for the shell's pages: each reads or changes state the workspace owns, where a client used to run a command in the workspace.
`system/apps/system_interface/workspace_routes_api.json` is their full description (every request and answer, as an OpenAPI document, each route naming its operation under `x-workspace-operation`), and is what a client is checked against; this section says what holds across them.

`GET /api/workspace/status` answers `{"schema": 1, "template_ref", "operations": [...], "compatibility": 1, "initial_data": {...}}`: the version of the checkout (the ref its newest `update-self` merge names, or its nearest `minds-v*` tag when there is no such merge or the tag is a newer release, else empty), the name of every operation the shell has a route for, the template's compatibility number, and how the workspace's initial data stands.
A client asks before the first operation it sends a workspace and calls a route only for an operation named there, so a workspace whose shell names fewer is still served by the client's older path.
A preview shell names none, and answers every route that changes the workspace `403` with the code `PREVIEW`: it serves a copy, and cannot change the live workspace.

`compatibility` is one whole number the template holds in one place (`WORKSPACE_COMPATIBILITY` in `workspace_api_models.py`), and a status without it means 1.
It is raised only by a change a client built before it could not work with: a route that changes in a way the frozen descriptions forbid, a format a client's own programs write, or a page the embed contract cannot carry.
A change every supported client still works with leaves it alone, and it is never lowered.
A client is built with the highest number it knows. One that reads a higher number still opens the workspace and stops, starts and destroys it, and refuses everything else it would do inside it rather than read a missing operation as a template too old to have it and run its older command.

`initial_data` is `{"state", "detail", "applied_at"}`: whether the workspace's boot applied the document it was handed when it was created (below).
`state` is `NONE` when the boot found no document and has applied none, `APPLIED`, or `FAILED`; `detail` says why for `FAILED`, naming each part that is not written, and is empty otherwise; `applied_at` is when it was applied, in seconds since the epoch, and null unless `APPLIED`.
A status without the member is a template from before the initial data, which ignores the document. The status keeps its schema, since the member is an addition.

| `update.read` | `GET /api/workspace/update` |

| `update.schedule.write` | `PUT /api/workspace/update/schedule` |
| `update.schedule.refresh` | `PATCH /api/workspace/update/schedule` |

A route asks for no more than the request guard does: it reads the requester's identity, so an identity header that does not parse is refused, and it does not ask for the owner, since whoever a proxy admits to the shell already reaches the terminal and every file a route writes.
The one exception is `GET /api/workspace/backups/credentials`, which answers a secret to a client outside the workspace and so answers the owner alone (`403` with the code `OWNER_ONLY` otherwise).
A refusal is `{"detail", "code"}` under a 4xx (`INVALID_REQUEST`, `PREVIEW`, `INVALID_GRANTS`, `INVALID_PROFILE`, `INVALID_TIMEZONE`, `INVALID_DESTINATION`, `BACKUP_OPERATION_RUNNING`, `OWNER_ONLY`, `INVALID_UPDATE_SETTINGS`), a route that could not do what it was asked is the same under a 5xx (`GRANTS_UNREADABLE`, `WRITE_FAILED`, `NOT_AT_WORKSPACE_ROOT`, `SUGGESTIONS_UNAVAILABLE`, `SUGGESTIONS_UNSUPPORTED`), and an answer that describes what the workspace did, including that it declined, is a 200 with an `outcome`.
A refused grants document also carries `refusals`, one `{"scope", "kind", "value", "message"}` per entry, and a `BACKUP_OPERATION_RUNNING` carries `lease`, who holds the backup lease.

Two routes answer before their work is done, and a client reads on:

- `PUT /api/workspace/backups/destination` names where the backups go and answers the backup state, under `202` when the request left the workspace something to do and under `200` when it did not. `GET /api/workspace/backups` then says how the setup stands.
- `POST /api/workspace/update/start` answers `200` with an outcome when a quick check declines (no update-self skill, no signed-in account, an update running or about to), and otherwise `202` with the outcome `STARTING` and an attempt id while the update's chat is created; `GET /api/workspace/update` then holds the attempt under `last_start`, with its outcome once it has one. An attempt whose process is gone reads as `CREATE_FAILED`.

**The workspace sets up its own backups.**
A client names where the backups go and supplies the storage credentials that destination needs, and nothing else: the workspace makes the repository's password, initialises the repository, installs `data/.secrets/restic.env`, and tries again by itself when any of that fails.
The supervised `backup-setup` program does it (`system/libs/workspace_backup_setup/`; supervisord knows it as `backup_setup`), so a setup outlasts a restart of the shell, and one the program was stopped in is taken up when it starts.

The body of `PUT /api/workspace/backups/destination` is `{"destination"}` with the storage where the client has some:

| `destination` | What comes with it |
|---|---|
| `IMBUE_CLOUD` | `imbue_cloud_storage`: `{"repository_url", "rest_username", "rest_password"}`, as the connector's `POST /backups/repositories` answers them |
| `OWN_STORAGE` | `own_storage`: `{"repository", "backend_env"}`, the variables of the storage as the user typed them |
| `NONE` | Nothing: backups are off |

- A request for what the workspace already holds changes nothing and answers the state, except that a setup that had failed is tried again at once.
- A request that would change something is refused with `409` and the code `BACKUP_OPERATION_RUNNING`, naming the holder, while another backup operation holds the backup lease. The workspace's own setup holding it refuses nothing: the request replaces what the setup was asked, and an attempt under way ends without installing anything, so backups can be turned off or sent elsewhere while an attempt hangs.
- A destination named with no storage is set up from what the workspace kept for it, and reads `AWAITING_STORAGE` when it kept nothing.
- Storage offered for the repository the workspace already uses is taken only once the workspace finds that the storage refuses what it holds: a repository at the backup store has one token, and a client that asks the connector for another ends the first.
- `NONE` moves `restic.env` aside to `restic.env.<timestamp>`, which the workspace keeps, and the backup service goes idle. Until the new destination is ready, a change of destination leaves the previous one in use.
- A password among the variables of the user's own storage is refused with `400` and the code `INVALID_DESTINATION`, as is a destination the workspace does not know.

`GET /api/workspace/backups` answers everything a client reads about the backups:

| Field | Meaning |
|---|---|
| `destination` | `NONE`, `IMBUE_CLOUD` or `OWN_STORAGE` |
| `setup` | How the setup stands: `state`, `detail`, `started_at`, `finished_at` and `retry_at` |
| `is_configured` | Whether `restic.env` is in place, which is what the backup service runs on |
| `is_verification_enabled` | The verification flag |
| `repository` | The address of the destination's repository, with any credential in it taken out; `""` when there is none or the workspace does not know it yet |
| `credentials_digest` | The SHA-256, in hex, of the text of the `restic.env` in use; `""` when there is none |
| `lease` | Who holds the backup lease: `holder`, `taken_at` and `expires_at`; null when nobody does |

| `setup.state` | Meaning |
|---|---|
| `NONE` | No destination is chosen |
| `AWAITING_STORAGE` | A destination is chosen, and the workspace holds no storage credentials that work for it |
| `INITIALIZING` | An attempt at the setup is running, or about to |
| `READY` | `restic.env` is in place for the destination |
| `FAILED` | The last attempt failed; `detail` says what failed, with the credentials' values redacted, and `retry_at` when the next one starts |

A failed setup is tried again after a minute, then after twice as long each time, up to an hour, for as long as the destination stands.
Once an hour, and when it starts, `backup-setup` checks that the credentials in use still open the repository; a storage that refuses them leaves the setup `AWAITING_STORAGE`, with `restic.env` where it is.

`GET /api/workspace/backups/credentials` answers `{"env_text", "digest"}`, the whole text of the `restic.env` in use and the digest the state answers as `credentials_digest` (both `""` when there is none), to the owner alone. The workspace makes the repository's password, so this is how an owner's client comes to hold a copy: it reads the credentials when the digest differs from that of its own copy.

A `restic.env` the workspace's program did not write is taken as the destination. An Imbue Studio desktop from before these routes writes the file by its own command, and again from its own copy when it updates the backup service; a current desktop's restore and its migration of the backup store write it too, and a current desktop's update of the backup service writes none into a workspace that has the backup lease. The setup then reads `READY` for the repository the file names, the destination's kind is read off the file (Imbue Cloud where the repository is a `rest:` address whose user name is the workspace's own id, storage of the user's own otherwise), and a file such a writer moved aside reads as `NONE`.

**One backup operation at a time.**
The workspace holds a backup lease: a file at `/run/backup-operation.lease` that names its holder, when it was taken, and when it expires. It lasts ten minutes from when it was taken or last renewed, and one past its expiry is free. Under `/run` it outlasts the workspace's services being stopped and does not outlast a reboot.
The workspace's own setup takes it as `setup`. A program of the Imbue Studio desktop that changes backups (`restore`, `backup-service-update`, `store-migration`) takes it through `python3 system/scripts/backup_lease.py`, run from the workspace root: `take --holder <name>`, `renew --holder <name>`, `release --holder <name>`, `read`, and `hold --holder <name> [--keep] -- <command>`, which runs a command under the lease, renews it every minute for as long as the command runs, and gives it back when the command ends unless `--keep` is given.
`take`, `renew`, `release` and `read` each print one JSON line, the lease as it stands or `null`. `take` and `renew` exit 75 when the caller does not hold the lease afterwards, and `hold` exits 75 without running its command when someone else holds it, and with the command's exit code otherwise. `hold` prints the lease only when it exits 75, naming who holds it: otherwise its output is its command's own.

`GET /api/workspace/sharing` also lists the apps that can be shared by themselves, as `shareable_apps`: every registered app that is not internal, in the registry's order, each `{"name", "label", "display_name", "is_system"}` (its grants' key, its origin label, the name a person reads, and whether it is part of the workspace itself). An internal app is reached only through a share of the whole workspace.
`PUT /api/workspace/profile` leaves the stored snapshot alone when the one sent equals it apart from `written_at`, and answers `is_written: false` then: a client sends the snapshot whenever it opens the workspace, and the shell watches the file, so a rewrite would announce a change that did not happen.

**The workspace arms its own updates.**
`PUT /api/workspace/update/settings` stores the update settings and answers them as stored: `channel` (the release channel the workspace follows), `feed_base_url` (where that channel's file is read from, empty on a tier that publishes none), `is_auto_update_enabled` (the account's answer to whether its workspaces arm their own updates), `is_auto_update_enabled_here` (this workspace's own answer, which wins; null when it has none), `window_start_hour` and `window_end_hour` (whole hours 0 to 23 that differ, the owner's local hours an armed update may start in, as the account sets them), and `window_start_hour_here` and `window_end_hour_here` (this workspace's own hours, which win over the account's: both set, or both null when it has none).
Settings that cannot be the workspace's are refused with `INVALID_UPDATE_SETTINGS`.
The hours are read in the timezone the workspace records (`data/.state/user_timezone`), and in UTC when it records none.

The three settings that are the workspace's own (`is_auto_update_enabled_here`, `window_start_hour_here`, `window_end_hour_here`) are optional in a request.
One a request leaves out keeps its stored value, and one sent as null is cleared.
A client that writes the account's settings into a workspace leaves all three out, so it cannot wipe an answer the owner gave in another client, and neither can a client from before a setting existed.
Every other setting is required, and an answer carries them all.

The update dispatcher, which cron runs every minute, reads `<feed_base_url>/<channel>-web.json` at most once an hour and keeps the version it names (`templateRef`). That is the channel's version: the newest version the workspace may take.
While arming is on, nothing is armed or running, and no decision waits for the user, the dispatcher arms a schedule for the channel's version when the workspace is behind it, unless the user skipped that version or a run already went out for it.
A channel file that cannot be read arms nothing, and the last version read stays on display.
The dispatcher's cron line is written at every boot as well as by the routes, so a workspace no client has asked anything of runs it.

In `POST /api/workspace/update/start`, `PUT` and `PATCH /api/workspace/update/schedule`, the values a client used to compute are optional, and one left out is the workspace's own:

- `ceiling` left out is the channel's version. When the workspace has read none and cannot, the answer is `200` with the outcome `NO_CHANNEL_VERSION`, unless the request names a version the user chose (`override_ref`), which needs no other.
- `window_start_minute_utc` and `window_length_minutes` left out (together) are the settings' window. With no settings the answer is the outcome `NO_UPDATE_SETTINGS`.
- `is_backup_configured` left out is whether the workspace holds `data/.secrets/restic.env`.

A schedule armed with the workspace's own values keeps them current: the dispatcher rewrites them when the channel moves, the settings change, or the timezone's offset does. A `PATCH` rewrites each value it leaves out with the workspace's own, and leaves it as it is where the workspace has none.

A request that names `ceiling` is from a desktop app built before the workspace read its channel, and is served as it always was. Such a desktop names its newest version in every request of its sweep, every 300 seconds, so the workspace holds itself to that version for 15 minutes after the last such request: it arms no update past it, takes the older of the two for a request that names none, and leaves an armed schedule to that desktop's own refreshes.

`GET /api/workspace/update` also answers `settings` (null when no client has written any) and `channel_version`: `{"channel", "template_ref", "read_at", "checked_at", "error"}`, the version as the workspace last read it and how the last read went (null when it has read nothing for the settings' channel), so a client shows what is available without reading the feed.

A read route changes nothing in the workspace, and reads no feed.
The update routes act on the workspace the shell runs from, so they are refused with `NOT_AT_WORKSPACE_ROOT` when the shell's working directory is not the workspace root.

**The initial data.**
Whoever creates a workspace leaves one JSON file of mode 0600 in the machine's host directory, `$MNGR_HOST_DIR/initial_data.json`: `{"schema": 1, "profile", "timezone", "update_settings", "backups"}`.
Each part has the shape of the request of the route that writes the same thing (`PUT /api/workspace/profile`, `PUT /api/workspace/timezone`, `PUT /api/workspace/update/settings`, and `PUT /api/workspace/backups/destination`, which names where the workspace's backups go), and a part that is left out, or null, writes nothing.
The boot sequence applies it each time the workspace's services are started, after the workspace's Python packages are in place and before the clock is set (`apply-initial-data`, `system/libs/workspace_initial_data`), by handing each part to the writer its route calls; the timezone is recorded only where none is, and is in force from that very start.
A zone the workspace's tz database does not know is no refusal of the `timezone` part, since whoever builds the document cannot know that database: the part counts as applied, no zone is written, and the workspace keeps UTC until a client writes a zone through `PUT /api/workspace/timezone`, which still refuses such a zone with `INVALID_TIMEZONE`.
A `timezone` part of the wrong shape (no `zone`, or a `zone` that is no text) is refused.
The trigger is the file being there, not a first boot: a pool machine's first boot is over when it is baked, and its document is written when it is adopted, before its services are started again.
When every part is written the step records that in `data/.state/initial_data/state.json` and deletes the document, which holds storage credentials.
A document that does not parse, whose `schema` is above 1, or a part of which its writer refuses, is left where it is with the reason recorded, and the boot goes on; a part its writer refuses does not stop the others, and no reason quotes a credential of the document.
Each part is applied at most once: the next start tries the parts that were refused and no other, so it never puts the create's value back over what the owner chose since, and never names the create's backup destination again after the owner turned backups off.
The step keeps the document's digest and how far each part has come beside the status, and records that a part is about to be written before it writes it. A part the step was interrupted in the middle of is therefore not written again either: its `FAILED` stands, and the document is deleted once no part is left to try.
The backup part is handed to the function `PUT /api/workspace/backups/destination` calls, under that route's rules: the destination and its storage are recorded for `backup-setup`, and a destination named while another backup operation holds the backup lease fails the part, which the next start tries again.
The status route answers how it stands, as `initial_data` (above).

**Suggestions.**
The workspace's two suggestion switches are the settings of one of its apps, which names where they are read and changed in its manifest (`suggestion_settings_path`, section 2).
`GET /api/workspace/suggestions` answers `{"is_next_step_suggestions_enabled", "is_new_chat_suggestions_enabled"}`, and `PUT /api/workspace/suggestions` changes the switches its body names, leaves one it does not name (or names as null), and answers both.
The shell passes each request to that app over loopback, sending a write exactly the switches the client named, so the app keeps the one lock on its settings and tells its own open pages of a change.
When the app is not running, does not answer within 10 seconds, or answers something other than its settings, the answer is `503` with the code `SUGGESTIONS_UNAVAILABLE`, and asking again later is right.
When no registered app declares the path, or the one that does has no such route or answers settings without the switches, which is an app from before it could, the answer is `501` with the code `SUGGESTIONS_UNSUPPORTED`.

**Apps and the wallpaper.**
`GET /api/workspace/apps` answers `{"apps": [...]}`: every registered app that is not internal, in the registry's order, each `{"name", "label", "display_name", "is_system", "icon"}`. They are the apps `shareable_apps` lists, each with the SVG markup of its registry row as `icon`, or `''` when it has none. The apps with `is_system` false are the ones built on the workspace, which a client lists as the workspace's own. An icon is the app's own markup, so a client draws it as an image (a `data:` address), where nothing in it runs.
`GET /api/workspace/wallpaper` answers the image the workspace's first desktop wears, as `GET /api/desktops` orders them, under the image's own content type, and `204` with no body when that desktop wears its theme's default, the workspace has no desktop yet, or the image is gone. The image carries an `ETag` and `Cache-Control: private, no-cache`, so a browser that holds it asks again and is answered `304` while it has not changed, with no header of the page's own. The read creates no desktop.
Neither loosens the request guard: each is a workspace route, called from the web client's own code with the workspace's session, and an image element of another site is refused the wallpaper as it is refused `/wallpapers/<kind>/<name>`.

## 6. The WebSocket

Route `/api/ws`, one connection per browser window.

Inbound: `client_state {"client_id", "active_desktop", "previous_desktop", "report_id", "is_following", "page_id", "revision"}` on connect and on every desktop switch.
A report that moves the client (the user's switch, naming the desktop it left in `previous_desktop`; or the page's landing, its landing on the first desktop when the one it showed was deleted, and its re-registration on a reconnect onto a desktop other than the one its client record names, naming none) carries a fresh `report_id` and `is_following` false: the shell records the active desktop and `last_seen`, and logs a `desktop_switch` activity when `previous_desktop` differs.
The client-activity log (`<state dir>/events/client_activity/events.jsonl`, the `message` and `desktop_switch` shapes of section 5) also records every window open as a `window_opened`: `{"timestamp", "type": "window_opened", "event_id", "source": "client_activity", "client_id", "desktop_id", "app", "window_id", "is_new", "requester"}`, written by the windows, launch and show routes and the `open` and `show` ops alike, with `client_id` empty for an open with no client to place it for, `is_new` false when an `if_present` focus answered an existing window, and `requester` the op's requester as a `layout_op` message spells it (section 8), empty for a client's own open. Never the path or the title: the event says which app was used, not what was shown.
It also records a person interacting with a window as a `window_input`: `{"timestamp", "type": "window_input", "event_id", "source": "client_activity", "client_id", "desktop_id", "app", "window_id", "kind": "input" | "focus"}`, one per client, window and UTC minute, from the windows the heartbeat reports (section 5.1): `input` when the window's page reported a key or pointer press (`shell:input`, section 7), `focus` when focus landed in a page that has declared no capabilities, which reports nothing itself; `app` is the desktop's record of the window when it still exists, else the reported name, which must be registered; `desktop_id` the window's desktop, else the client's active one, else empty. A window reported with both kinds in one heartbeat is written as `input`, and a second report inside the minute writes nothing. Never the path, the title, the key or the pointer position.
The log is bounded: past 8 MiB it is staged aside before a write and gzipped on a thread of its own, two archives kept, and its readers read the live stream alone.
Every report carries the window's `page_id`, and a moving report also carries, in `revision`, the newest desktop revision the window had heard (pushed, or read from its client record).
The shell does not record or broadcast a moving report whose `revision` is below the client's `desktop_revision` unless the page that wrote that revision is the report's own: such a report was made before the window heard of a move something else made since (an op, an arrival, another window of the client), and the window follows that move's `active_desktop_changed` instead, so the move is never undone by a report that crossed it on the way.
The shell sends the reporting connection alone an `active_desktop_changed` naming the client's record (its `desktop_revision`, a null `report_id`), since the move may have been announced before the connection could hear it (an op landing as the page loads); a window that heard it already ignores it.
A window's own reports are exempt because it makes them faster than it hears them back (rapid switches); since a report is recorded only past moves its page heard or made, a page that wrote the latest revision wrote every one since the revisions it reports.
A report without a `page_id`, a moving report without a `revision`, or a following report with one is malformed and ignored.
A window that followed the client's stored desktop (an `active_desktop_changed`, or a newer record read on a reconnect), or that reconnects on the desktop its client record names, reports it with `is_following` true, a null `report_id` and a null `revision`: the shell registers the connection on that desktop and stamps the client's `last_seen`, and moves nothing, since a later move may already have replaced what the window followed.
A window takes an `active_desktop_changed` only when its `revision` is newer than any it has heard (pushed, or read from its client record), and not when it is the echo of a report the window has since replaced with another (what the later report leaves the client on is announced at a newer revision): so a window that switched several times before the first echo came back ends on its last switch, and no report a window makes in following can move the client and set its other windows following in turn.
A record read on a reconnect whose revision is below the newest the window had heard when it asked for it (or no record at all) was reset under the page, restored or pruned, and the window counts from the record's revision again.
A window that hears an `active_desktop_changed` newer than the record while it reads the record follows that news, and reports its reconnect with `is_following` true: its desktop may still be the one the news moved the client off.
A solo page (section 9) sends `client_state {"client_id", "is_pop_out": true}` on every connect instead: the shell registers the connection under the client, so the ops targeting the client (section 8) reach it, and records nothing else. It never becomes the client's report, never logs a desktop switch, and never supplies an active desktop to `context` or anything else: the client's active desktop stays its main window's.

## 7. The app contract (`app_contract.js`)

Built once, into the shell's static output, and served by every app at `/_static/app_contract.js` from its own origin (the shell serves it too, with `Access-Control-Allow-Origin: *`): a page imports it as a module, and a module import is a fetch without cookies, which the desktop client's forwarder and the share gateway refuse across origins.
Exports `connectToShell({onHandshake, onShown, onHidden, onCloseRequest, onNavigate, onTheme, onKeybindingsChanged, capabilities})` returning `{isFramed, hasShell(), focused(), location(path, title), openPath(path, ifPresent), startWithText(text), draftText(text), showCoachCard(text, place), agentWorking(isWorking), firstConversationStep(isPending), sendMessage(type, fields), openLink(url), disconnect()}`.
`hasShell()` is true once a `shell:handshake` with a client id has arrived from the parent. `openPath` sends `shell:open` below; `startWithText` sends `shell:start-with-text`; `draftText` sends `shell:draft-text`; `showCoachCard` sends `shell:show-coach-card` with `place` as its one place (`{chromeAnchor}` or `{target}`; `coachCardPlaceOf(payload)` reads a payload's back, or `null`); `agentWorking` sends `shell:agent-working`; `firstConversationStep` sends `shell:first-conversation-step`; `sendMessage` sends `shell:message`; `openLink` sends `shell:open-link`.
Beside it the shell builds and every app serves `/_static/context_menu.js`, the element context menu of the element-reference-menu plan (section 9 there), which drafts through `draftText` and opens a link by clicking it.
It also builds the page kit, `/_static/workspace_theme.css` and `/_static/workspace_theme.js`, which a page built as plain HTML loads to wear the workspace's theme (the workspace-themes plan, section 5.3). The kit follows `shell:theme` through the contract's `followShellTheme(onTheme)` (same arguments as `onTheme`), which listens without connecting, so it runs beside a page's own `connectToShell`.

Link rule: once a shell's handshake has arrived, a page's link clicks follow one rule, so no app carries link code of its own.
The module listens for `click` and middle-button `auxclick` on the window, the last stop of a click's bubbling, so a page's own handlers see the click first; a click already `defaultPrevented`, a link with a `download` attribute, a plain click on a link whose `target` names an `iframe` of the page (which loads it there), and a link to any other of the browser's own schemes (`javascript:`, `data:`, `blob:`, `about:`) are left to the page; a custom-scheme link is handed on.
- A link to the page's own origin navigates the page as usual; a new-window click on one (a middle or modified click, or a `target` other than `_self`, `_top` and `_parent` included) opens a window of the page's app there instead (`shell:open` with `ifPresent: "focus"`).
- Any other link (a local URL, an address of another app or another workspace, a share address, a `file:` URL, or an external link: the Imbue Studio desktop app's `isExternalUrl`, `mailto:`, `tel:`, or an http(s) URL off this machine, or its `isCustomSchemeUrl`, a custom-scheme link) goes to the shell with `shell:open-link`. A `file:` link works only this way: a browser refuses a web page's navigation to a `file:` URL, popup or not, before anything else sees it.

The page's script popups follow the rule too, for what the workspace opens itself: while connected, the module replaces `window.open`, and a call to a page of the page's own origin sends `shell:open` (`ifPresent: "focus"`), and one to a local URL, an address of another app (on the page's own share domain too), or a `file:` URL sends `shell:open-link`; either answers `null`, as a blocked popup does. A call to any other site, to `about:blank` or another scheme, or with no URL goes to the browser's own `window.open` unchanged, so a script that needs the window it opened (a sign-in popup it watches) still gets it. A call naming a frame of the page (an `<iframe name>`) goes to the browser's own `window.open` too, and one naming `_self` follows the rule for a plain click: the page's own origin navigates the page natively, and any other link sends `shell:open-link` and answers `null`. Disconnecting puts `window.open` back.

A page no shell has handed a handshake -- an unframed page, or one framed by something else, such as the chat root opened on its own -- leaves its clicks and popups to the browser.
`capabilities` is `{navigation: boolean, closeChord: boolean}` and must agree with the handlers: giving `onNavigate` without `navigation: true`, or `navigation: true` without `onNavigate`, is an error the module throws at connect, and so is `closeChord: true` without `onCloseRequest`. A page that declares `closeChord` owns the close chord: the shell sends `shell:close-request` and leaves the window open (the Screen's viewer sends Ctrl+W to the remote that way, which closes a browser tab there).

Following rule: after every `desktops_updated`, for every live page of a window whose stored `path` differs from that page's last reported path, the shell sends `shell:navigate` when the page declared navigation, else reassigns the iframe `src`, and records the stored path as that page's last report at once, so a second broadcast before the page lands does not navigate it again.
A page's own report never navigates it.

Nested frames: an app page that frames another page of its own origin (the chat root) forwards `minds:` messages from that frame to `window.parent` unchanged, re-posts the inner page's `shell:focused` as its own, and forwards the inner page's `shell:open` of a sub-agent view, its `shell:draft-text`, its `shell:show-coach-card`, its `shell:message`, and its `shell:open-link`, from one module named in `test_embed_ratchets.py`'s allowlist.
An inner page's `shell:agent-working` it does not forward, since the shell would take every inner page's report for the one frame's: it keeps each inner page's last report, dropped when that page's frame is removed or loads again, and posts its own `shell:agent-working`, true while any of them is, when that changes and again on a `shell:handshake` while it is true.
The chat root, not the pages it frames, posts `shell:first-conversation-step`: it is loaded whichever chat is on screen, and reads the answer off the chat list its app pushes.
From the same module it posts the shell's `shell:handshake` down to each inner page as the page loads, and again when the shell sends a new one, so the inner page's app contract has a shell (`hasShell()`) and follows the link rule; a root no shell frames has no handshake to post down, and drops what its inner pages post for the shell.
A `shell:open` whose path is the root's own (`/` or `/?chat=<id>`) it answers itself, by selecting that chat in place, rather than asking the shell for a second root window.
The shell and the minds chrome accept messages only from frames they created, so nothing else reaches them from an inner frame.

Chat presence: a chat's own page (never a sub-agent view) posts `POST /api/chats/<chat-id>/presence` on its own origin with `{"instance_id", "client_id", "state", "is_focused", "sequence"}`. `instance_id` is minted once per page load, and the chat app keeps one standing report per chat and instance, so a pulled-out chat and its hidden copy in the main window never overwrite each other; `client_id` is the handshake's, and informational. `sequence` numbers the page's reports from 1 in the order it sends them; each is its own request, so the chat app can receive two in either order, and it drops a report numbered at or below the instance's standing one. `state` is `hidden` when the handshake lands, `visible` on `shell:shown`, `hidden` on `shell:hidden`, and `closed` on `pagehide` (after which the instance counts as neither open nor visible); a page visited directly follows the document's visibility instead. `is_focused` is `document.hasFocus()`, reported again on every window `focus` and `blur`, and the page heartbeats its current report every 30 seconds. A chat is open while any instance's `visible` or `hidden` report is under ten minutes old and visible while any such report says `visible` (the memory prioritizer's signals); an instance is *watching* the chat while its last report is `visible`, focused, and under 90 seconds old. `GET /api/chats/<chat-id>/watchers` (loopback only) answers `{"watched_by": [instance_id, ...]}`, which the notify-user script sends on as the notification's `watched_by`. The same script tells the chat app about each notification with `POST /api/chats/<chat-id>/notification` (loopback only, `{"message", "title"}`), which the chat app posts to the shell as a `notification` bubble over the agent's entry (section 5.1), titled with the chat's title. When a report turns a chat from unwatched to watched, the chat app posts `POST /api/v1/agents/<agent-id>/notifications/read` (empty body) for the chat's current agent through the latchkey gateway's `minds-api-proxy`, once per such turn; an app that answers 404 is ignored.

## 8. The op route and `workspace-layout`

`POST /api/layout/broadcast` with `{"op", "args", "requester"}`, loopback only.
`requester` is `{"app", "marker"}` (`{"app": "chat", "marker": "<chat-id>"}` for a chat's agent, from `MINDS_CHAT_ID`, else `MNGR_AGENT_ID`), or `null`; `self` in a window argument names the window of `app` on the target client's active desktop whose path, as the target client sees it (its own stored path for an independent window), carries `marker` as a path segment or a query value; `pinned` names the pinned window of `app` on that desktop (`404` when it has none, `400` with no requester).
Targeting: `args.client`, else the client that most recently messaged the requester while it is connected, else the one connected client (when a client messaged, only if both last arrived as the same user), else that messaging client though it is not connected, else `412` listing the connected clients; `open` alone, with nothing settling the client, writes the window on `args.desktop` (else the first desktop) with no placement instead, so it reads as minimized for every client, and answers with `client_id` and `layout` null.
`args.desktop` names the desktop an op edits by name or id and switches the target client to it once the op is applied, so an op refused on the way leaves the client where it was.
`args.force` (default `false`) lets an op move a popped-out window (below): `minimize`, `restore`, `maximize`, `place`, and `open` act on it, `focus` and `close` take it and ignore it, and no other op takes it.

Popped-out windows (`docs/system/blueprint/popped-out-layout-ops/plan-popped-out-layout-ops.md`): a window is *popped out* for the target client when that client's placement of it is detached (section 4.2) and the client is connected (a solo page's connection counts, section 6). Then:

- `minimize`, `restore`, `maximize`, and `place` are refused with `423` and change nothing, the `args.desktop` switch included, unless `args.force`; forced, they apply (a forced `minimize` clears `is_detached` and minimizes, so the window goes out of sight rather than staying out), and the client is not switched to the window's desktop. A detached placement of a client that is not connected is moved the same way without `force`, so the pop-out reopened at its next launch finds its window back and closes (section 9).
- `focus`, and an `open` whose `if_present` focus finds the window at the path (without `minimized`), leave the placement as it stands and send the client's windows a `show` `layout_op` naming it, as `show` does below; `force` changes nothing here.
- `open` whose `beside` names a popped-out window opens as it would without `beside` (no pairing) and names that window as `unpaired_beside`, unless `args.force`, which brings the window back (raised where it stands) and pairs the two.
- `close` never checks: it closes the window for everyone, which ends every client's pop-out of it. `refresh`, `navigate`, `load`, `show`, and the shortcut and wallpaper ops are never refused.

`window` is a window id, `self`, `pinned`, or an app name (that app's most recently focused window on the target client's active desktop).
The bodies, the answers, and the records they carry are the models of `system/libs/workspace_layout` (`ops`, `answers`, `records`): one body model per op, carrying the arguments the table gives it, which the shell reads every body with, builds its answers from, and every caller reads them with. A body is refused with `400` before anything is looked up when it carries an argument its op does not take (`client` and `desktop` included: a `refresh` of an `app` and `reload_system_interface` take neither), lacks one the op requires, or breaks a rule of its arguments (a path that is not a window path, a `state` `place` does not set, a frame outside the unit square, an `open` naming both a `path` and a `launch` or `params`); the `detail` names every such argument. `context`, `desktops`, and `list` read no arguments and ignore what they are sent.
`show` knows nothing of what the path shows and reads no meaning into a query string. `showing` is a list of the app's other paths that count as already showing it (`path` itself always does). `repoint` is a list of the app's pages, each a path with no query string or fragment, whose windows `show` may point at `path`; absent or empty, step 2 below repoints nothing. A `showing` entry that is not a path, or a `repoint` entry that is not a page, is a `400`. For the target client, every path as that client sees it (its own stored path for an independent window), the first of these that applies:

1. `raised`: a window of `app` at `path` or a `showing` path, on the client's active desktop before any other and nearest the top of the client's stack first, minimized or not, is restored and raised; one on another desktop is raised there and the client switched to that desktop.
2. `navigated`: the on-screen window of `app` (one not minimized, or one pulled out, whose own desktop window is on screen whether or not it is also minimized) on the active desktop nearest the top of the stack whose page (its path before any `?` or `#`) is in `repoint` is set to `path` as `navigate` sets it (a linked window moves for every client, an independent one for this client) and raised; a window of the app on any other page is never repointed.
3. `pinned`: the app's pinned window on the active desktop is set to `path` the same way and restored.
4. `opened`: a window of `app` at `path` is opened on the active desktop for the client, shown and on top.

A window the first three settle on that is pulled out for the client stays out: its placement is left as it stands, and the client is not switched to its desktop.
Whichever of the four it is, once its edit is written the client's windows are sent a `show` `layout_op` naming the window and whether it is pulled out (`{"window", "is_detached"}`): for a pulled-out one the desktop's page asks the embedder to raise the window's own desktop window, as the taskbar entry's "Show" does, and so does the solo page of that very window (section 9), so the raise works with the desktop's window closed; a phone layout shows the window (`plan-phone-interface.md`).
An `open` that places its window for a client (not `minimized`) and a `focus` on a window not popped out likewise send that client's windows an `open` or `focus` `layout_op` naming the window (`{"window"}`) once written, which only a phone layout acts on.

`show` is answered like the document ops, with `desktop_id`, `desktop`, and `layout` those of the desktop the path is shown on, and `"shown"` one of the four above.
Document ops are applied to the files and answered with `{"ok", "desktop_id", "client_id", "desktop", "layout", "window_id"?, "is_raised_in_own_window", "is_brought_back", "unpaired_beside", "has_no_desktop_window"}`: the window was raised in its own window rather than on the desktop; the op brought a pulled-out window back onto the desktop; the popped-out window an `open`'s `beside` named and did not pair with (`null` otherwise); and the client is connected only through solo pages, so the window an `open`, `focus`, `show`, `restore`, `maximize`, or `place` put on its desktop shows when a desktop window opens. The two transient ops travel only as `layout_op` and are answered `{"ok", "target_client_id"}` (null when every client's windows apply it).
`split`, `move`, and every instance verb (`rename`, `delete`, `stop`, `start`, `replace-url`) are refused with an error naming the replacement; `chat:`, `terminal:`, and `app:` spellings are refused with an error saying to give an app name and a path.
Exit codes are `0`, `1`, `3` (a `409` or `503`), and `4` (a `423`: the window is popped out; `--force` overrides it).

## 9. Deep links

Honoured by the shell on page load for the requesting client, then stripped: `?desktop=<id>` switches to it; `&open=<app>:<path>` opens (or focuses) a window there; `&launch=<app>:<launch_id>` runs a launch path through the launch route (section 5.3) with a `new` target.
Unknown or stale targets are ignored silently.

`?solo=<window-id>` is *solo mode* (the pull-out-window spec, section 7.5): the page shows that one window edge to edge and nothing else, which is what a pulled-out window's desktop window loads. It is read and kept in the URL, unlike the deep link, so any reload of the page (the `reload_system_interface` op, the browser's own) comes back as the same pop-out. A solo page lands on the desktop that holds the window without reporting its desktop (its `client_state` is a pop-out's, section 6, and the client's active desktop stays its main window's), ignores every layout verb but its own window's detach and reattach, and never follows an `active_desktop_changed`.
`&reopened=1` beside it (also kept) says the embedder reopened the page's desktop window (a session restore, a reopen of the app, a backend retry) rather than opening it for a tear-out just now. A reopened page takes its first layout as the truth: when it says the window is back (brought back while the embedder was away), the page reports the window back at once, which closes it. A page without the flag (a tear-out, the window menu's "Open in its own window", or an embedder that does not send it) cannot: a first layout load that does not yet say the window is out waits a moment for the desktop's word (the main window's shell writes the detach as the window leaves, and that save is on its way while the solo page boots) and detaches the window itself only when none comes.
Either way its own window's return is reported to the embedder (`minds:detached-windows`) only once saved, since the embedder closes the page's window on that report; a later load that says the window is back is the desktop's word.

## 10. Geometry rules and constants

The constants below are theme metrics (section 11) unless marked as fixed.
Both editors (`shell/desktop_document.py` and `frontend/src/geometry/`) implement every rule and pass the shared vectors in `docs/system/blueprint/desktop-interface/geometry_vectors.json`, which the implementation phase creates.

- **Backdrop**: the viewport less the taskbar height, in pixels; fractions are relative to it.
- **Viewport** (fixed): the backdrop plus the taskbar's band below it, `{0, 0, backdrop.width, backdrop.height + taskbar height}` in backdrop pixels, which no frame in fractions of the backdrop reaches; what a `FULLSCREEN` window renders at, with no fit applied (the Screen spec, section 12). `frame_for_state` and `frameForState` answer it as its own value (`Viewport` / `"viewport"`, which the shared vectors spell the same way) beside the frames, and a rule over backdrop frames (pairing) reads a fullscreen window as the whole backdrop. While a fullscreen window is on the active desktop's screen the backdrop stops clipping and paints over the taskbar, which is covered rather than removed, so nothing else moves. A viewed desktop's fullscreen window (the multiplayer spec, section 8.3) fills its letterbox instead, which is the owner's backdrop alone: the viewer's backdrop keeps clipping and the taskbar keeps "Stop viewing".
- **Cascade** (fixed, in fractions): window `n` (zero-based, cycling every 6) gets `{x: 0.05 + 0.03 * (n mod 6), y: 0.06 + 0.04 * (n mod 6), width: 0.6, height: 0.7}`, then clamped into the unit square.
- **Snap frames** (fixed): left `{0, 0, 0.5, 1}`, right `{0.5, 0, 0.5, 1}`, maximized `{0, 0, 1, 1}`; fullscreen is the viewport above. A drag snaps to the first three only.
- **Fit** (render only): `pixels = fraction * backdrop`; width and height are raised to the minimum window size; then the frame is shifted so that at least the minimum visible title width of the title bar is inside the backdrop horizontally and the whole title bar height is inside vertically, top edge never above 0.
- **Snap zones**: a drag released with the pointer within the snap threshold of the left or right backdrop edge snaps to that half; within the threshold of the top edge maximizes; the top edge wins a corner.
- **Un-snap**: a drag of a snapped or maximized window beyond the un-snap distance makes it `NORMAL` at its kept frame's width and height, positioned so the pointer sits at the same horizontal fraction of the title bar it was pressed at, then clamped. A fullscreen window has no title bar to drag, so un-snap does not apply to it; its strip's Exit fullscreen, the window menu, the taskbar entry's Restore size, or a layout op (`restore`, `place`) brings it back to its kept frame.
- **Drag threshold**: a press becomes a drag after the drag threshold; below it, it is a click.
- **Press focus** (fixed): a press on a handle (a title bar, a resize edge, a shortcut, an entry) takes the document's focus back from any other window's page that holds it, as the browser would have on a press whose default the gesture source did not prevent; the pressed window's own page keeps it. A page left holding the document's focus would be raised again on every return of the embedder window's focus or at the next tick of the shell's focus timer (section 7, `shell:focused`), over the window the user chose.
- **Focus follows the focused window** (fixed): whenever the focused window changes, by any route (an agent's focus, a menu, a window a page opens), the document's focus is taken off every other window's page, for the reason Press focus gives. Only the focused window's page ever keeps it, so an agent opening or focusing a window takes the keyboard from the page the user was typing in. A press into a lower window's page is the one route that runs the other way: the press moves the document's focus into the page's frame, and the shell then raises the window (section 7, `shell:focused`). The shell raises on seeing a page's frame take the focus, so every route that changes the focused window must take the document's focus off the other pages, as above.
- **Gestured window on top** (fixed): while a move or resize is in progress, a raise of any other window is dropped, whatever asks for it (a page's focus report, the shell's own sight of a page taking the focus, a notification); the gesture's end raises its own window again.
- **Grid**: origin at the inset from the backdrop's top-left; `columns = max(1, floor((backdrop.width - inset) / cell.width))`, `rows = max(1, floor((backdrop.height - inset) / cell.height))`.
- **Nearest free cell** (fixed): among free cells, the one at the least Euclidean distance in cell units from the clamped target cell, ties by lower column then lower row.
- **Reading order** (fixed): `cell(i) = {column: i mod columns, row: floor(i / columns)}`.
- **Placement of shortcuts** (render only): shortcuts whose stored cell is inside the grid and unclaimed take it, in shortcut order; every other shortcut takes the nearest free cell to its clamped stored cell, in shortcut order.
- **Room made for a dragged shortcut** (drawn by the client alone; nothing new is stored, so `frontend/src/geometry/grid.ts` implements it and `desktop_document.py` does not): the held shortcut takes the cell the pointer is in, clamped into the grid, and the shortcut that was in it -- and only that one -- steps aside to the **nearest free cell** (above), reckoning the cell the held shortcut is leaving as free. A free cell needs nothing stepping aside, so the rest of the grid never moves. The arrangement is drawn live -- the shortcut that stepped aside slides to its cell for the length of the drag and no longer, so a grid re-fitted by a resize or a desktop switch is taken without sliding, and the slide is asked for rather than taken away (`motion-safe`, as the window travel is) -- and the drop commits it through the move route (section 5.2), naming only the shortcut that was dragged: the shell displaces the occupant by the same rule and its answer stands. The two searches differ in their bounds -- the drag searches the grid, the shell the unbounded plane -- so on a desktop whose free cells near the target are all off the grid the shortcut settles where the shell put it rather than where the drag drew it.
- **Phone showing** (render only): a phone shows one window at a time whatever its layout says of it, and writes no placement for showing it (`plan-phone-interface.md`).
- **Tear-out** (the pull-out-window spec): when the embedder has said it can pull windows out, every title-bar drag is announced to it (`minds:window-drag-started`, with the window's rendered size and the grab offset) and the embedder watches the cursor from there, since the shell's own pointer events stop at the embedder window's edge on some platforms. On its word (`minds:tear-out`): `out`, the chrome is dragging a desktop window of its own under the cursor, so `is_detached` is set with the frame untouched and saved at once (a return lands where the drag began, and the chrome's window reads a placement that already says it is out, in this shell's stacking order), and this one hides, offering no snap zone; `in`, the chrome dropped that window and this one is brought back (raised, its state kept) and shows again where the drag has it, saved at once; `released`, the gesture is over and nothing more is written. The dragged window holds the top of the stack for the whole gesture, the return included (the embedder window's focus comes back with it, and a page reporting that focus does not displace it). The desktop's shell is the one writer during a drag; the chrome's window only reads. The shell's own gesture end (a release it sees, or Escape) tells the embedder how it ended (`minds:window-drag-ended`, `isDetached` and `isCancelled`). The embedder's word stands even when it lands after that release (a fast drag's release can beat its `out`): a late `released` after a release inside puts back the placement the drag began at and detaches it, saved at once; a late `in` after a release taken as out brings the window back; a cancelled drag takes no late word.
- **Detach and reattach** (fixed): `detach` sets `is_detached` and clears `is_minimized` where the placement stands; `reattach` clears `is_detached` and `is_minimized`, sets the state to `NORMAL`, moves the placement to the top, and takes the frame a drop back onto the desktop names (clamped into the unit square) or keeps the placement's own. Every verb that shows a window on the desktop (focus, restore, maximize, snap, and place) clears `is_detached`; `show` leaves a pulled-out window out and has its own desktop window raised (section 8); `minimize` on a detached placement sets `is_minimized` and leaves the window out, changing nothing on screen, and `detach` on a placement already detached clears `is_minimized` again. An agent's op reaches these verbs only as section 8 allows: on a window popped out for a connected client, `focus` raises its own window instead and the others are refused unless forced, and a forced (or disconnected client's) `minimize` minimizes onto the desktop (`is_detached` cleared) rather than leaving its own window up.

`--desk-window-move` and `--desk-window-move-ease` time a window's travel to a rectangle the pointer did not move it to (a snap, a `place`, an `open` with `beside`): the window's root transitions over them, a press turns the transition off for its whole length through `data-window-motion="off"` on the desktop's root, and and the transition is declared inside `prefers-reduced-motion: no-preference`, so a platform that does not say motion is welcome gets the arrangement without the travel.
