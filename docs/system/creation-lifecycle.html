The Creation Lifecycle

Live first, ratify at turn-end — how skills, apps, and services get built, changed, and fixed.

Every piece of real work is split into two halves. The foreground half keeps the conversation interactive: confirm the basic shape of the thing fast and cheap, with the user reacting to something real. The background half does the expensive, thorough work (tests, review gates, polish) in an isolated worker, after the shape is confirmed — so the user is never waiting on hardening, and hardening never targets a shape the user is about to change. The two halves meet at an explicit user confirmation.

Foreground — user watches and steers, minutes Background — worker on an isolated branch, up to ~90 min Gate — explicit user confirmation required

1 · Entry points: the seeding skills

Foreground
The request arrives; a seeding skill runs the interactive foreground flow. Each one later hands its confirmed result to a lead (section 3).
net-new: data fetch-process-show “Go get this data, do something to it, show me.” Validates auth first (the risk not under your control), then loops a real sample.json covering every data shape.
net-new: web view build-app “Build me a page / dashboard / tool.” Scaffolds cheaply, then loops a throwaway mock with hard-coded content so the user judges look-and-feel before any real backend exists.
existing creation update-app A change to an app or service that already runs. Owns the live change loop: apply, refresh the user’s view, verify — hardening deferred to turn-end.
no seeding skill Ad-hoc turn work The turn itself is the foreground half: you did something by hand, or worked around a breakage live. If it’s repeatable (or broken), it feeds a lead at turn-end.

3 · The seam: a lead dispatches a worker

Lead skills: crystallize-creation (create) · update-creation (change) · heal-creation (fix) Each seeding flow ends by handing its confirmed result to one of three generic leads:
  • fetch-process-show → crystallize-creation (type=skill) — the confirmed sample plus staged scripts become a tested, script-centric skill.
  • build-app → crystallize-creation (type=app) — the confirmed working site gets its thorough tests and review gates.
  • update-app → update-creation (or heal-creation if the change fixed a breakage). A system-interface change takes the same path with an extra preview/safe-reveal wrapper.
  • Ad-hoc turn work → crystallize-creation standalone (with the user’s go-ahead) if repeatable, or heal-creation if a creation broke and you worked around it.
The lead is still foreground, but brief and mechanical: it packages context so a fresh agent can do the work without the chat history — opens a tracking ticket, writes a task file (operation × type, plus verbatim transcript anchors so the worker finds the right turns), commits pending work, launches the generic harden-worker from committed HEAD on its own branch, and starts a background poll for the worker’s reports. Then the conversation moves on.

Two knobs shape what happens next: operation (crystallize / update / heal) decides which approval gates the worker raises; type (skill / app / service / system-interface) decides where it works and how the result goes live. For updates, a further toggle: a change already discussed and committed live skips the design gate; an emergent change (hand-work with no design conversation) gets one.

6 · What buys what: the quality / speed / robustness levers

Speed (foreground)
  • Everything is throwaway until confirmed — a wrong guess costs minutes, not a rebuild.
  • Mock with hard-coded content; render the confirmed sample directly rather than waiting for the pipeline.
  • Defaults are declared, not asked: only genuinely uncertain and expensive-to-reverse forks become questions.
  • Architecture is elicited and written down, never built during the interactive phase.
  • Narrowest scope: one user, one use, the data at hand — no speculative generality.
Quality (the gates)
  • Every transition is gated on the user confirming something real: a data sample, a mock, a working site, an outline, a final diff.
  • This kills the dominant failure mode: expensively hardening the wrong shape, inside a worker that can’t see corrections the user hasn’t made yet.
  • Cheap iterations reset the clock — a change request during the loop costs nothing because no gates or tests have run.
  • Confirmation is explicit, never inferred from silence or a timeout.
Robustness (background)
  • Isolated branch: live state is untouched until merge; the system interface additionally gets preview + rollback.
  • The bar is “genuinely well-tested and clean,” not “it ran once” — fixtures for anything parsing external data.
  • Pipelines survive partial failure and resume from what already landed; raw payloads are preserved with source references.
  • Every growing store gets a bounded retention policy, covered by a test.
  • Review gates run before the final report, so the user sees one already-reviewed result.

7 · What the user actually experiences

Foreground — visible, interactive
  1. A couple of plain-language questions at most, then a short plan to nod at.
  2. Something real to react to within minutes: a rendered sample, a mock tab, a changed page.
  3. Each round of feedback visibly applied before the next look.
  4. One explicit “yes, that’s the shape” moment.
  5. They keep using the confirmed thing right away; new capabilities arrive one at a time, each asked about first.
Background — invisible until it matters
  1. The harden pass runs silently; the conversation is free for the next request.
  2. Occasionally a notification: approve an outline, or sign off on the final version. Routine calls are made for them.
  3. Nothing interrupts newer work they’ve moved on to.
  4. Success shows up quietly — a tab refreshes, a skill exists next time it’s needed.
  5. Failure is honest: a “stuck” report says what blocked and where the work stands, never a false “done.”
