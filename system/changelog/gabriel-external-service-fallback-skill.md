Secrets an agent needs now enter the workspace through a chat card and leave it only through a wrapper. `system/scripts/with_secrets.py data/.secrets/<name>.env -- <command>` loads the file's variables into a child process's environment and execs the command; it is the one sanctioned reader of `data/.secrets/`, and it refuses a file outside that directory or readable by more than its owner.

Two tool-call policies enforce that. P8 (`agent_secrets_guard.sh`, `agent_secrets_guard_check.py`) refuses any shell command that mentions `data/.secrets` unless it runs the wrapper or the request script, `ls`, or `rm` (a `bash -c` string is judged by the same rule, so a supervisord program passes), and refuses claude's, codex's, and pi's file tools on a path under the directory; the README stays readable. P9 holds the connect-external-service skill's `request_secret.py` to the same one-per-tool-call rule as a latchkey permission request, in the same checker. Both are registered for claude, codex, the agy shim, and pi, where the secrets guard is the first checker to run on every tool call rather than on bash alone.

`.claude/settings.json` sets `enableAllProjectMcpServers`, and the `ENABLE_CLAUDEAI_MCP_SERVERS=false` comment in `.mngr/settings.toml` now says what it does and does not forbid: claude.ai's connector sync is a side channel around latchkey for services latchkey supports; a service's own MCP server, wired through `.mcp.json` for a service latchkey does not support, is fine. `AGENTS.md` and the build-app planning prompt point at the new skill.
