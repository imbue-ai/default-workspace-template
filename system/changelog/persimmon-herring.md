The shared frontend library gains the geometry a hover menu needs, and a third tooltip placement.

`flyout-position.ts` places a combo card's side flyout and guards the pointer's trip to it. `placeFlyout` lines the flyout's FIRST ROW up with the row that opened it, and when that would run the box off the bottom of the screen it slides the flyout up by exactly as much as it takes to fit rather than giving up height to hold the alignment -- a list squeezed into the space below a low row has about three rows to work with, which is no use to a thousand-model catalog. `isInSafeTriangle` answers whether a pointer is inside the wedge between the last point on the opening row and the flyout's near edge, which is what tells travel apart from a change of mind: without it, every row crossed on the diagonal to the flyout takes the hover and replaces the flyout being aimed at.

`menuRowClass` draws a row's highlight as an inset rounded slab: 4px in from the card's edges with a 4px radius, which is what the card's own 8px corner leaves once you step 4px inward, so the highlight reads as concentric with the card rather than pasted into it. Every menu in the workspace moves together -- the chat's card and flyouts, the provider chooser, the tab kebab menu, the rail's row menus, the launcher's filter menu.

`placeTooltip` gains `above` beside `below` and `right`: centred over the trigger with the same 6px gap, flipped below when it would overflow the top and there is room down there, then clamped. Each placement prefers its own side and gives way only when that side has no room, so a caller's choice holds wherever it can. It is an addition rather than a change of default -- every caller that does not ask for it keeps the centred-below behaviour -- and it exists for a surface whose tooltips are raised by controls sitting on the rows of a list, where a bubble below the pointer covers exactly the rows being chosen between.
