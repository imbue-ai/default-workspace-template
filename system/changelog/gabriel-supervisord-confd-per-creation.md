Background programs now live one per file under `system/supervisord.conf.d/`, pulled in by an `[include]` glob. `system/supervisord.conf` holds only the supervisord daemon's own configuration. Adding a service is writing `system/supervisord.conf.d/<name>.conf`; removing one is deleting that file.

Two agents building two independent creations in one workspace used to block each other. Every new app appended a `[program:*]` block to the single shared `system/supervisord.conf` and added entries to the root `pyproject.toml`, so one agent's in-progress work sat as uncommitted changes in the other's tree. That bites hardest at the hardening step, which refuses a dirty tree the agent cannot clean because the dirt is not its own -- so agents skipped the background pass and substituted an inline review. Removing the shared files from a creation's footprint makes the two lines of work genuinely independent.

`system_interface` is the one program still declared in the main config, and only because moving it is the follow-up change; nothing depends on it being there.

One reader does have to keep up, and it is cross-repo: the minds evals evidence capture reads a workspace's `system/supervisord.conf` to learn which program supervises each registered app, and neither a plain `cat` nor `configparser` follows supervisord's `[include]`. Against this layout it sees only `system_interface` and reports every other app as unsupervised -- silently, since an app-free workspace gives the same answer. `system/test_supervisord_layout.py` turns that into a release gate this repo's CI can see: while any program lives in a drop-in, the mngr vendored under `system/vendor/mngr` must carry the include-aware capture. It is red until that mngr change is vendored, which is the point -- provisioning is tag-pinned, so what a `minds-v<N>` template tag ships with is what binds.

Start order is unchanged: supervisord orders programs by `(priority, name)` and every program uses the default priority, so the declaring file has no bearing on startup.
