Background programs now live one per file under `system/supervisord.conf.d/`, pulled in by an `[include]` glob. `system/supervisord.conf` declares no programs at all -- it is purely the supervisord daemon's own configuration plus the `[include]` of the drop-ins. Adding a service is writing `system/supervisord.conf.d/<name>.conf`; removing one is deleting that file.

Two agents building two independent creations in one workspace used to block each other. Every new app appended a `[program:*]` block to the single shared `system/supervisord.conf` and added entries to the root `pyproject.toml`, so one agent's in-progress work sat as uncommitted changes in the other's tree. That bites hardest at the hardening step, which refuses a dirty tree the agent cannot clean because the dirt is not its own -- so agents skipped the background pass and substituted an inline review. Removing the shared files from a creation's footprint makes the two lines of work genuinely independent. The root `pyproject.toml` now says which dependencies must stay listed and why: the built-in services supervisord starts with `uv run <name>`, whose console scripts a root-closure-scoped `uv sync` would otherwise prune. A scaffolded app is deliberately absent from that list, and what keeps the same sync from pruning it is that mngr's restore and update scripts sync with `--all-packages`.

The drop-in directory is a convention, not something readers discover: neither `configparser` nor a plain `cat` follows supervisord's `[include]`, so every reader of the config -- the OOM band checks, the scaffolder's port pre-flight and name guard, `migrate-workspace`'s port scan, and the cross-repo evals capture -- reads `system/supervisord.conf.d/*.conf` by name rather than parsing the glob out of the config. `system/test_supervisord_layout.py` is the one place that expands the declared glob, and it pins the two together: the glob reaches every drop-in on disk, and every in-repo reader sees exactly the programs the glob reaches. If the glob and the readers ever named different places, a reader would still parse a valid config, just an empty one, and assert over nothing.

One reader is cross-repo: the minds evals evidence capture reads a workspace's `system/supervisord.conf` to learn which program supervises each registered app. Against this layout the old capture finds no `[program:*]` at all and reports every app as unsupervised -- silently, since an app-free workspace gives the same answer. `system/test_supervisord_layout.py` turns that into a release gate this repo's CI can see: while any program lives in a drop-in, the mngr vendored under `system/vendor/mngr` must carry a capture that reads the drop-ins too. The gate asserts on what the capture *does*, not on how its shell is written -- it builds the capture's own shell out of the vendored source and runs it against this repo from an unrelated working directory, then checks it reached every program declared here. What the gate is coupled to is the shape of the upstream API: a builder of that name returning a shell string, and the one constant it formats in. Rename either, or read the config in Python instead of emitting shell, and the gate goes red -- deliberately, since it cannot tell that apart from the capture being dropped; its assertion names which of the two names went missing and says to re-point the test rather than drop it. It is red until that mngr change is vendored, which is the point -- provisioning is tag-pinned, so what a `minds-v<N>` template tag ships with is what binds.

Start order is unchanged: supervisord orders programs by `(priority, name)` and every program uses the default priority, so the declaring file has no bearing on startup. Verified the split is a no-op on the realized config: read both layouts through supervisord's own `ServerOptions.read_config` and diffed the resulting process configs -- the same 15 sections (14 programs plus the `oom-tag-backstop` event listener), identical order, identical commands and options, no include warnings.

The changelog gate's own tests are now hermetic. They build throwaway repos in `tmp_path` but read `CHANGELOG_BASE_REF` / `GITHUB_BASE_REF` from the process environment, so under CI they inherited the real PR's base branch -- which does not exist in a throwaway repo, and which `resolve_diff_base` deliberately refuses to resolve by falling back to `main`. It only surfaced on a stacked PR: when the base is `main` the throwaway repo has one too, so the leak resolved by coincidence and the tests passed for the wrong reason. An autouse fixture in `system/scripts/conftest.py` now clears all four Actions variables the gate reads -- the diff-base pair `CHANGELOG_BASE_REF` / `GITHUB_BASE_REF` and the branch pair `GITHUB_HEAD_REF` / `GITHUB_REF_NAME` -- for every test in that directory.
