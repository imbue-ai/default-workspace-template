The in-workspace backup provisioning (`system/scripts/provision_backups.py`, run over owner-exec during a hosted web-create) now retries `restic init` through the R2 credential-propagation window. A freshly minted R2 API token is not yet valid at Cloudflare's S3 edge for a few seconds, and the web-create path runs `restic init` immediately after minting the bucket key -- so it reliably lost that race and failed the whole create's backup step with "restic init failed (exit 1): ... signature ... does not match". The init now retries for up to 60s on transient auth signals (InvalidAccessKeyId / signature-mismatch, matched against both the raw S3 codes and restic's rendered phrasings); a genuine non-auth failure still fails fast, and an already-initialized repo is still treated as success.
