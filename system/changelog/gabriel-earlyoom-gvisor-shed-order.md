earlyoom now sheds in priority-band order under gVisor. gVisor reports every process's `oom_score` as 0, so the stock earlyoom shed the largest process first whatever its band: a chat or the chat app could go before a runaway pytest. The workspace now installs the imbue-ai fork of earlyoom (`system/scripts/install_earlyoom.sh`, chained from `setup_system.sh`), which computes the kernel's badness from `oom_score_adj` and memory itself. On runc hosts (lima, local Docker) the order is unchanged. The apt `earlyoom` package is no longer installed; a re-provision purges it, and on systemd hosts masks its unit, which was running a second, unconfigured earlyoom. The plan is in `docs/system/blueprint/earlyoom-gvisor-shed-order/`. `AGENTS.md` now says how to check for gVisor instead of listing which providers use it.
