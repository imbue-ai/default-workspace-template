Bootstrap installs a permanent update-apply recovery cron entry (`/etc/cron.d/update-apply-recover`, every 5 minutes) at each boot: a plain-python3 `update_self.py recover --if-stale` that rolls back an update apply killed hard without a container restart. It is a silent no-op in every normal state -- it acts only when the apply marker exists, its recorded process is dead, and the marker has gone a grace period without an update. The drop-in carries its own `PATH` line, because cron does not inherit the image's `ENV PATH` and the recovery shells out to `mngr`, `uv` and `npm` to put the running state back, and takes a `flock`, because a tick that acts routinely outlasts the five minutes until the next one; it logs to `/var/log/supervisor/update-apply-recover.log` alongside the other scheduled jobs.

It is written at every boot rather than once by `setup_system.sh`: `/etc/cron.d` lives on the container rootfs, so an entry laid down at provision time is gone the moment the container is recreated -- and this guard is the only thing that recovers an apply whose driving agent is also gone. Writing it from bootstrap, which already knows where the recovery script lives, also stops that path being spelled out in a second place. It goes down before the entries under `data/.state/cron.d`, so a deliberate same-named entry there still overrides it.

`setup_system.sh` pins `HOME=/root` at the top and installs the pinned restic binary by decompress-then-rename, fixing the two live re-provision failures that broke real updates: the Claude installer following an agent's `HOME=/home/user` into the wrong home while the version check read `/root/.local/bin/claude`, and `bunzip2 -c > /usr/local/bin/restic` truncating a binary the running `host_backup` service was executing (ETXTBSY). `_provision_guard.sh` honors `PROVISION_FORCE=1`, which runs a guarded step even when the tree's marker matches: the update apply's rollback re-provisions from the restored tree, and that tree is exactly the one the marker was written for, so the re-run that puts the global toolchain back would otherwise be skipped. The root pytest config stops recursing into `data/`, so a staged skill copy under `data/.tasks/` (which ships its own test file) no longer breaks a bare `uv run pytest` with a basename collision.

`setup_system.sh` is now the only path that installs a global binary: the owner-exec daemon and the dufs file-viewer server, previously each its own Dockerfile layer, are chained from it like the secret scanners and agy, so an already-running workspace taking an update that ships or bumps either gets the binary from the apply's live provisioner re-run instead of a service that starts, fails to find it, and retry-loops until a rebuild. A new `system/test_provisioner_single_entry.py` holds the Dockerfile to that shape (no `RUN default-workspace-template-install-*` other than the in-repo dependency installer, and every `install*.sh` under `system/scripts/` named in `setup_system.sh`).

The Dockerfile no longer carries the toolchain version pins as `ARG`/`ENV` (Claude Code, Codex, Node, pi, opencode, the pi extensions). Nothing ever passed a build arg, and the `ENV` half persisted the image's versions into every process in the container, where a live re-run of `setup_system.sh` read them over the merged tree's `:=` defaults: an update bumping Claude Code reinstalled the image's old version, passed the script's own pin check against the same stale variable, and reported success, after which the merged `agent_types.claude.version` pin refused every new claude agent. `setup_system.sh` is the single source of truth for every pin, and `test_workspace_claude_config.py` asserts the Dockerfile stays free of them. The `@playwright/cli` pin, which only the Dockerfile's `ENV` had carried, now has its `setup_system.sh` default too, and `test_provisioner_single_entry.py` checks that every `*_VERSION` the script expands has one.

The mngr plugin set the workspace registers now lives in one place, `system/config/mngr_plugins.toml`, naming each plugin's path and which tool environments (mngr, system-interface) it goes into; `system/scripts/list_mngr_plugins.py --tool <name>` prints one tool's paths. `build_workspace.sh` reads it for the image build's `uv tool install --with-editable` and `mngr plugin add --path` calls, and the update-self apply reads the same file after a merge, so a release that adds a plugin registers it in the workspaces it updates rather than only in freshly built images.

The safe-update-apply blueprint keeps only its plan; the incident review and the review findings that used to sit beside it are folded into the mngr-internal tracker (`blueprint/inner-workspace-updates/open-threads.md`), which the plan now points at, so there is one record of what is still open across both repos.
