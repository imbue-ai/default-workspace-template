A new script, `system/scripts/run_in_background.py`, runs a command in the background and, when the command exits, sends its exit code and output to the calling agent's own chat as one message. That message starts the agent's next turn, so it works on every harness. Only claude's own background tool wakes the agent when its command finishes; codex, pi and opencode have no such tool. The chat shows the user only a one-line summary. The run's output and exit code are also kept in `data/.tasks/run-in-background/<task>/`.

If the report can't be delivered, the runner keeps retrying with backoff for up to four hours. That covers a chat that is mid-handoff, and an agent that was shed for memory and is waiting for its lead to restart it. It gives up at once only when the chat no longer exists. The runner also outlives a stop of the agent that started it (a handoff retiring it, or its restart after a shed), which kills every process tagged with that agent's id: the runner drops the tag, and only the command keeps it, so the command still ends with the agent and the report says how. `message_chat.py` now exits 8 when the chat app doesn't know the chat and `mngr` has no agent with its id. Before, `mngr message` exited 0 for an id that matched nothing, so a message to a chat that no longer existed looked delivered. The runner also lowers its own OOM priority to the user-service band once its command has started, so under memory pressure every agent but the workspace's primary is shed before it. The command itself keeps the caller's band.

`message_chat.py --system` now says what it does: it wraps a message in the browser fleet's tag, which the chat shows as a "Browser fleet" chip. A codex lead had used it to report a worker's result, and the chat showed that report as a browser-fleet message.
