The Screen spec (`docs/system/specs/screen/spec.md`) designs a neko-streamed Linux desktop as one workspace window, with the browser as a launch path of it and the browser app deleted: packaging, the Screen service, the viewer, the control lease over neko's `locked_controls`, sizing through added RANDR modes, three video profiles, visibility and audio policy, a never-stop-for-emptiness lifecycle whose group ends together, occupancy-aware OOM bands, clipboard and files, mobile, the three fullscreen layers (a `FULLSCREEN` placement state, Studio's immersive mode, and the X session's own), the share gateway's brokering, the browser migration, the `screen` command, tests and the implementation order.

The Screen's first two implementation steps land the infrastructure around the new `system/apps/screen` package:

- The env.d unit `system/scripts/env.d/2000-screen.sh` replaces `1000-playwright-fortress.sh`: it installs the Screen's apt packages (Xorg with the dummy driver, XFCE, PulseAudio, GStreamer with x264, xdotool, wmctrl, xclip) from the pinned snapshot and the pinned neko v3.2.0 binary at `/opt/neko/bin/neko` (taken from the `ghcr.io/m1k1o/neko/base` image's one layer through the registry API, checked against pinned digests), and carries Fortress and the Chrome extensions over unchanged, `DWT_SKIP_BROWSER_UNIT` included. The offload configs and `offload_sandbox_init.sh` point at the new unit.

- `system/supervisord.conf.d/xvfb.conf` is gone: display `:99` is the Screen's Xorg from now on (the browser program keeps `DISPLAY=:99` and renders onto the Screen until its migration). New drop-ins: `screen.conf` (the service and the `screen-stack` group), `screen-xorg.conf`, `screen-pulse.conf`, `screen-session.conf`, `screen-neko.conf` (the group's members, started by the service on demand) and `screen-watch.conf` (the event listener that ends the group together).

- `system/test_app_manifests.py` pins the Screen's manifest, accepts an event listener as a declared wiring program, and treats programs an app's manifest wires as that app's rather than standalone. The Dockerfile's npm manifest layer and `system/package.json` carry the viewer's frontend; its build output is gitignored like the other frontends'.

- The Screen's launch path for its own page is `screen` rather than the spec's `open`, which the manifest schema reserves for the launch path the shell synthesizes.

The desktop interface's documents take the Screen spec's `FULLSCREEN` placement state: `contracts.md` adds the `screen` manifest row (the browser row stays until its migration), the state in the placements file and the `place` op, the viewport as the fullscreen frame under the geometry rules, and the strip's selectors; `concepts.md` lists the state, the strip and the Fullscreen and Immersive menu rows, and marks decision 17 superseded; `plan-desktop-interface.md` 9.4 describes the browser as a launch path of the Screen. `geometry_vectors.json` gains the `fullscreen` cases and `snap_frames.FULLSCREEN` (`"viewport"`).

Step 8, the browser's migration and the deletions (the Screen spec, sections 16.2 and 18):

- `system/apps/browser` is deleted (its changelog entries with it; the browser's history continues in `system/apps/screen`'s), with `system/supervisord.conf.d/browser.conf`, the `pixelflux` and `pcmflux` dependencies (`uv.lock` regenerated), and what the image baked only for the browser: `xvfb`, `xclip`, the libva and pixman runtime libraries, `x11-utils` and the baked PulseAudio (`system/scripts/setup_system.sh`); the Screen's env.d unit installs xclip and PulseAudio with the rest of the stack on first boot. `system/test_app_manifests.py` and `docs/system/blueprint/desktop-interface/contracts.md` section 2 lose the browser's rows.

- `system/scripts/env.d/2000-screen.sh` keeps Fortress at v151.0.7908.0 (x64 from the official release, arm64 from the fork build the previous unit pinned), checked against the pinned SHA-256 sums; the tree is installed under a versioned directory and `/opt/fortress/tilion-fortress/tilion`, the path AGENTS.md, the root conftest and the Screen service use, is a symlink the unit repoints at the pinned release, so a pin bump reinstalls (an install the previous unit made of the same release is accepted as it is). Fortress v153 (Fortress v3) was tried and dropped: its license now charges organizations of our size for production use, and its recorded-human mouse motion makes CDP mouse clicks hang under Playwright, which would stall agents driving the browser fleet. The Chrome extensions are fetched for Chrome 151.

- The workspace shell's `open https://...` opens the page through the Screen's `browser` launch path (`system/libs/workspace_layout`), and the shell's layout pipeline test expects the Screen app to be named when it is not registered.

- `docs/system/blueprint/workspace-app-model/contracts.md` loses the browser app too: the Screen takes its row in the built-in manifest table and the `wiring` and `launcher_rank` examples, and the instances API's browser-specific notes and row are gone with the app.

Step 9, the document sweep of the Screen spec's section 19: `concepts.md` decisions 16 and 18 follow the Screen's rule (the browser is no longer window-bound; an agent opens the Screen's window), the services README names the Screen's stack sidecars where it names the rule they follow, and the Screen spec's status line says implemented, with an "Implementation notes" subsection at the end of section 22 recording the deviations the implementers verified (the `screen` launch path id, the `screen-stack` group, the admin-password event session, the REST clipboard route for HTML, the file drop that does not land, mouse events for taps, the hidden pointer lock, the gateway's `/connect-info` route, no audio null-device fallback, Chromium's renderers shed before programs on the Screen, `GET /json/version` on the CDP proxy, and Chromium starting maximized so its window fills the Screen).

- `system/scripts/env.d/2000-screen.sh` also installs neko's Xorg input driver, `/usr/lib/xorg/modules/input/neko_drv.so`, from the pinned `ghcr.io/m1k1o/neko/base:3.2.0` image (one layer per architecture, pinned by digest and by the module's SHA-256, through the same registry fetch as the binary; the image builds it on Debian trixie against xorg-server 21.1, XInput ABI 24.4, which is what the pinned snapshot installs), so a phone's taps reach the Screen as real touches.

- Every create template that runs a workspace declares the Screen's published ports, `publish__extend = ["59000/udp", "59000/tcp"]` (`.mngr/settings.toml`); the `modal` template declares `["59000/tcp"]` alone, because Modal tunnels carry TCP only and mngr refuses a UDP declaration before the sandbox exists.

- `system/scripts/env.d/2000-screen.sh` also installs the Screen's browser command, `system/apps/screen/scripts/screen-browser-open`, at `/usr/local/bin/screen-browser-open` (re-installed whenever the tree's copy differs) and registers it as the `x-www-browser` alternative, so XFCE's "Web Browser" launcher, an `http(s)` link opened by a program on the Screen, and `sensible-browser` all open the page in the fleet's Chromium through the Screen's browser launch path.

- The five Screen stack drop-ins (`screen-xorg`, `screen-session`, `screen-pulse`, `screen-neko`, `screen-watch`) tag themselves by their own program name, landing in the stack's band (`SCREEN_STACK`, 850) rather than the Screen service's (72).
