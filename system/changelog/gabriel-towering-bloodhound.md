Bug reports now carry the agents' own diagnostics, not just the workspace services'. Before, the `--logs` half of a report collected `/var/log/supervisor/*.log` only -- and agents run under tmux, not supervisord, so no harness output reached a report at all. A report told you what a chat said and nothing about why its harness misbehaved. Under the same "include logs" consent, the archive now also holds `agent-logs/<agent>/<file>`: each agent's harness log files, which is codex's `app_server.log` and TUI tail, antigravity's `agy_cli.log`, opencode's `opencode_server.log`, and the `stderr.log` the claude and pi-coding harnesses now write.

For codex there is also the app-server's own log database, rendered to text as `agent-logs/<agent>/logs_2.sqlite.log`. `app_server.log` records what a thread did but not which request or connection asked for it; the database has carried that attribution all along -- codex writes it independently of `RUST_LOG` -- but nothing collected it, because the collector only ever looked at `*.log` files. It is also about a hundred times smaller than the text log for the same span of time, so where the text log's 256 KiB tail could cover as little as a few seconds on a busy daemon, the rendered database covers the whole session.

Only rows written by the app-server's own request layer are read. The database is the harness's entire TRACE stream, and on a live workspace it was measured carrying bearer tokens under two targets and an API key under a third, so this is an allowlist of what to include rather than a denylist of what to drop -- an allowlist can only ever miss something useful, while a denylist misses something secret.

Each running agent also contributes a capture of its tmux pane, for the harnesses whose crash output only ever reaches the screen. That one needs BOTH consents rather than the logs one alone: a TUI harness renders the conversation into its pane, so the scrollback is chat content as much as diagnostics, and a user who asks for logs while declining to send their chats has declined it too. The capture passes `--no-start`, so filing a report never wakes a stopped agent.

The harness logs, the log databases and the chats are each scanned and released or withheld on their own, so a finding in one no longer costs the report the rest. The database is deliberately its own class rather than part of the harness logs: a row the allowlist did not anticipate costs the report the database alone and still delivers `app_server.log` and every agent's `stderr.log`, which are the logs most likely to explain the bug.

Two limits changed to go with it. Each log class now fills to a total byte budget newest-first, so one busy harness cannot hand the secret scanner more plaintext than it can read inside the host's budget -- without which the report would time out rather than arrive trimmed. A class the budget could not fit whole says so, and how many files it left out, in `collection-notes.txt`: otherwise a trimmed class reads exactly like a complete one, and "the harness that broke wrote nothing" is the wrong conclusion to hand someone diagnosing that harness. A class the scan then withholds says only that, without the trimmed line: "one file was left out" reads as reassurance that the rest arrived, which is the same wrong conclusion pointed the other way. Panes get their own budget rather than competing with the log files: they are captured at collection time, so under a shared newest-first budget they would sort above every real harness log and displace the logs of the agent that actually broke. And the per-file line cap rose from 200 to 2000: the per-file read cap was already what bounded a member, so the line cap was discarding lines that had been read, and a chatty service can write 200 lines in under a second.
