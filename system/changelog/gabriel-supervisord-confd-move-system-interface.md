`system_interface` moves into `system/supervisord.conf.d/system_interface.conf` alongside every other program, so `system/supervisord.conf` now declares no programs at all -- it is purely the supervisord daemon's own configuration plus the `[include]` of the drop-ins.

This was the one program the conf.d split left behind. The reason it was held back -- the minds desktop client's recovery probe, which read `system/supervisord.conf` directly to source this program's inner port -- no longer exists: that probe was deleted upstream once nothing consumed it.

A cross-repo constraint remains, and it belongs to the split as a whole rather than to this one program: the minds evals evidence capture reads the config from outside the container to learn which program supervises each registered app, and it has to follow the `[include]` globs too. That is gated on the parent branch, by `system/test_supervisord_layout.py`, for every drop-in rather than only for a program-free main config.

Verified the move is a no-op on the realized config: read both layouts through supervisord's own `ServerOptions.read_config` and diffed the resulting process configs -- the same 14 sections (13 programs plus the `oom-tag-backstop` event listener), identical order, identical commands and options, no include warnings. Start order is unaffected, since supervisord orders by `(priority, name)` and every program uses the default priority.

The changelog gate's own tests are now hermetic. They build throwaway repos in `tmp_path` but read `CHANGELOG_BASE_REF` / `GITHUB_BASE_REF` from the process environment, so under CI they inherited the real PR's base branch -- which does not exist in a throwaway repo, and which `resolve_diff_base` deliberately refuses to resolve by falling back to `main`. It only surfaced on a stacked PR: when the base is `main` the throwaway repo has one too, so the leak resolved by coincidence and the tests passed for the wrong reason. A new `system/scripts/conftest.py` clears both variables for every test in that directory.
