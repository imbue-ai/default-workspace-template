- One-off commands in `AGENTS.md`, config and scripts use `uv run --no-sync`, so following an instruction never relocks or syncs the workspace. The new root test `system/test_python_launch_rules.py` fails on any supervisord program (user-added drop-ins included) or `.mngr/settings.toml` window that runs under `uv run`, and on any plain `uv run` in a tracked doc, prompt, config or script, in a string or argv of the workspace's Python, or in a living `contracts.md`; an existing workspace's own services and docs get rewritten during the update merge.

- The secrets guard recognises `uv run --no-sync` / `--frozen` / `--quiet` in front of `with_secrets.py` and `request_secret.py`; any other `uv run` option in front of them is still blocked.

This release turns the workspace's scripts into packages. An existing workspace's own skills, services and docs are migrated during the update by following `.agents/skills/update-self/references/python-packaging-migration.md`.

- `system/scripts` is one uv project with two packages. `workspace_bare_scripts` runs under the system `python3` with no venv and imports only the standard library (and the stdlib-only libraries its hook stubs put on `sys.path`). `workspace_scripts` (the changelog gate, the docs viewer, the view refresh and `verify_app`) runs from the root venv.

- A script runs from its module by path. A thin entry file stays at the old path only where something outside this release runs it (Imbue Studio, minds_evals, the web client, mngr's pin scripts, update-self on an older release's tree, the app programs users' scaffolded apps run) or where it has to put a directory on `sys.path`; each says why in its docstring. A bare one also says it finds its package only because its own directory is first on `sys.path`, so it must be run as `python3 <path>`, never with `-I`, `-P` or `PYTHONSAFEPATH`. `run_in_background.py`, `tool_env.py` and `list_mngr_plugins.py` run from `system/scripts/workspace_bare_scripts/`, and the changelog gate, the docs viewer and `verify_app` from `system/scripts/workspace_scripts/`. `verify_app` no longer re-runs itself under `.venv/bin/python` when playwright is missing; it says to run it with `uv run --no-sync`.

- The four guard hooks (pipe into tail/head, latchkey request, secrets, tk standalone) run their checks through one entry, `system/scripts/agent_hook_check.py <check>`, instead of a wrapper each. Only it, the rewrite hook's entry, the two background-task entries and the skill entry files that run with no venv (update-self's, and publish-template's two manifest tools) still edit `sys.path`.

- `background_tasks.py`, `claude_background_task_hooks.py` and `vendor_mngr_skill.py` move into `workspace_bare_scripts`, with their tests beside them. Each keeps its path as an entry file, since all three run by that path under the system `python3`: Imbue Studio and its admin and eval tools run `background_tasks.py`, Claude's Stop and SessionStart hooks run `claude_background_task_hooks.py`, and CI and mngr's pin bump run `vendor_mngr_skill.py`. `system/test_external_entry_paths.py` now runs all three. The two background-task entry files put `system/libs/chat_background_tasks` on `sys.path` (the hooks' entry also puts `oom_priority` there, for the rewrite hook's command parsing), so they are counted among the import-path edits. The modules import the library normally.

- `forward_port` has a `register()` / `remove()` API, which its command line now runs, and `message_chat` a `send()`. The shared preview script registers its servers, and launch-task and the browser fleet send their messages, through them in-process instead of starting `python3` on the scripts; `send()` takes the repo root to read the registry from and run `mngr` in. `verify_app --open` / `--refresh` surfaces the page through `workspace_layout` in-process instead of running `uv run --no-sync workspace-layout`.

- The root workspace adds the `system/scripts`, `.agents/shared/scripts` and `.agents/skills/*/python` members, so skill dependencies resolve in the one `uv.lock`.

- The CI changelog job runs the gate (`system/scripts/workspace_scripts/check_changelog_entries.py`) from a `uv sync --frozen --package workspace-scripts` venv.

- New root checks:
  - `system/test_entry_point_import_cost.py` fails an entry point -- an entry file, or a package module with its own `if __name__ == "__main__":` block -- that loads pydantic, loguru, click, tenacity, httpx or asyncio at import, with no exceptions. A heavy module that another one it loads imports counts toward that one, so it names pydantic rather than the asyncio pydantic loads on Python 3.12.
  - `system/test_external_entry_paths.py` runs every path that Imbue Studio, CI and older update-self releases call by path. The bare paths run with no site-packages; the one venv-tier path, launch-task's `create_worker.py`, runs from the root venv.
  - `system/test_python_launch_rules.py` fails a `python3 <path>.py` that names a venv-tier or missing script, and a `uv run <path>.py` whose script is not in the tree, so a path that moved is rewritten wherever it is written down. It also counts, tests included, the code that edits the import path (`sys.path` under any alias, `monkeypatch.syspath_prepend`, `site.addsitedir`, a non-empty `PYTHONPATH` handed to a subprocess, a pytest `pythonpath` setting) and the code that loads a module from a file (`spec_from_file_location`, `spec_from_loader`, the file loaders, `runpy.run_path`, `exec(compile(...))`), and fails when either count rises. A skill listed in `.agents/third-party-skills.toml` is not counted, and the import-cost and launch checks do not read its files; `system/test_meta_ratchets.py` fails on an entry naming a skill that is not in the tree. A `sys.path` edit may only add a directory the bare type check searches (where the bare packages and the stdlib-only libraries live), written as path arithmetic on `Path(__file__)`; publish-template's two `uv run --no-project` tools and update-self's runtime `oom_priority` import are named exceptions.
  - `system/test_python_launch_rules.py` also counts the places non-test code names one of the workspace's own programs to run as a process -- a path to a runnable module, `-m` with one of its packages, or one of its packages' commands in an argv -- and fails when the count rises. `running-python.md` lists when a process is still the right call.
  - The plain-`uv run` check no longer reads files that link into `system/vendor/`. Once the mngr assets were fetched, `docs/system/style_guide.md` resolved to mngr's style guide and failed the check inside a workspace.
  - The plain-`uv run` check now covers script runs too: a `uv run <path>.py` with no `--no-sync` fails it, and so does a Python argv that starts `uv run` with a computed program and no `--no-sync` before it.
  - `system/test_meta_ratchets.py` requires a `pyproject.toml` in every skill `python/` dir. Without one, every `uv` command in the workspace fails.

- The Datalib app's launcher, `system/apps/datalib/launch_datalib_http.py`, counts as a bare entry point, like oom_priority's own scripts: its supervisord program runs it under the system `python3`, so the `sys.path` insert it uses to import `oom_priority` is one of the counted import-path edits. Its tests import it by name instead of loading it from its file.

- The supervisord program readers in `system/test_app_manifests.py` and `system/test_supervisord_layout.py` share one helper, `oom_priority.supervisord_testing.supervisord_commands`, instead of loading each other's test files by path. The root checks that skip vendored content share `system/vendor_testing.py`.

Without it, `workspace-scripts` no longer depends on the chat app or mngr, so chat's tests can depend on it without a dependency cycle.

Every other template stopped in July (Claude auth moved into accounts, and GitHub sync became an opt-in skill); these two were added on a parallel branch and kept the old line.

- `system/scripts/stdlib_only_scripts_test.py` checks every module of `workspace_bare_scripts` instead of a hand-kept list of scripts, so the modules that list left out -- the four guard checks, the rewrite hook's `agent_rewrite_bash_command` and `with_secrets` -- are now held to the stdlib-only rule on their own.

- `system/test_no_type_errors.py` type-checks the root project with ty: the skills and their shared scripts, `system/scripts`, the root-level tests and `conftest.py`. A skill listed in `.agents/third-party-skills.toml` is excluded from it and from the bare checks. It also checks the bare tier (what the system `python3` runs) a second time, against an environment with no third-party packages. There, an import the system `python3` could not make at runtime shows up as `unresolved-import`, at Python 3.12. The bare check covers the bare packages, the stdlib-only modules of other packages that run under `python3` (such as `notify_user.py`), and every bare skill's script, and it searches exactly the directories a bare file may put on `sys.path`. This replaces `stdlib_only_scripts_test.py`, and fixes the errors the new check found.

- The workspace's Python floor is 3.12: `requires-python = ">=3.12"` in the root and every project, and ruff targets 3.12. The build no longer installs a uv-managed 3.12 itself: with no project allowing 3.11, uv can no longer settle on a system 3.11 that the lock rejects, and the build's `UV_PYTHON=3.12` pin has uv download a managed 3.12 when the system has none.

- Local workspaces from before 2026-09-14 (Debian 12, system Python 3.11) can no longer be updated in place (see the update-self change).

- The root launch rules read supervisord program lines the way supervisord does (`command = ...`, `bash -lc "..."`), and a bare-tier file that imports venv-tier first-party code (such as `workspace_scripts`) now fails a root test.

- The workspace-app contract (`contracts.md` section 14) now says a pre-manifest app and the background services run from `.venv/bin/<name>`, not under `uv run`, matching the launch rule.

- `AGENTS.md`'s lockfile rule now says a `uv.lock` change that follows from a `pyproject.toml` change (a dependency or a new skill `python/` project) is committed, not dropped as churn.

- Every `.venv` (the checkout's and each worktree's) is now a symlink to a target beside the uv cache (`/var/cache/user/venvs` on docker), so uv hardlinks packages from its cache instead of copying them onto the workspace volume: the root venv was a 512M copy. `system/scripts/workspace_bare_scripts/venv_links.py` keeps the links. The boot window, worker provisioning, the session-start sync, the build and the dependency install run its `ensure` before they sync. `ensure` recreates a target a rebuilt root filesystem lost, turns a real `.venv` directory into a link (putting the directory back if the sync fails), and deletes every target whose link is gone, so removed worktrees leave nothing behind. A target on a different filesystem from the cache gets a warning in the boot log.

- An image build bakes the root venv's target into the image layer, and the first-boot seed copies only the `.venv` link, not a 512M venv.

- New blueprint `docs/system/blueprint/app-environments/plan-app-environments.md`: one shared environment for the built-in packages, and a standalone project for each user package.

Built-in apps share the workspace venv, and every user-built package is its own uv project (`docs/system/blueprint/app-environments/plan-app-environments.md`).

- **One install per built-in app.** Each built-in app's supervisord program execs its entry point from `.venv/bin` instead of a bare name, and the build no longer installs each app as its own uv tool (a second copy only an agent's PATH and the update pre-flight reached; a stale one rolled back a good update). The build removes any such tool an older image still carries (`tool_env.py drop-app-tools`). The built-in apps are root dependencies, and `system/config/mngr_plugins.toml` assigns plugins only to the mngr tool.

- **Explicit root members.** The root `pyproject.toml` names every built-in library, service and app instead of globbing `system/*/*`. A package under `system/apps`, `system/services` or `system/libs` that it does not name is a user package, and `system/test_user_packages_are_standalone.py` holds each to the standalone layout: its own `uv.lock` (checked with `uv lock --check`), no workspace sources, and a program line that syncs its own project `--locked` before it execs from its own `.venv/bin`. `system/test_app_manifests.py` reads the built-ins from `members` and fails on a package that is neither listed nor standalone; the launch rules flag a root-venv one-off of a user package's command.

- **User packages at boot, build and worker setup.** The bootstrap window links every user package's venv without syncing it; `build_workspace.sh` and worker provisioning sync each from its own lock, a failure stopping only that package (`system/scripts/workspace_bare_scripts/user_packages.py`). The root test run leaves user packages out; each runs from its own directory.
