Claude agents now deal with a dialog that is holding the TUI's input at send time, instead of failing the send.

`sensibly_deal_with_dialogs` lists the confirmations mngr may answer on the user's behalf. It is set to the model bar's own two: picking a model or an effort level sends `/model <slug>` or `/effort <level>`, and claude then asks to confirm that switching mid-session re-reads the whole history. The user already made that choice in the picker, so mngr completes it — by cycling the selector onto the named option, never by pressing Enter on whatever happens to be highlighted. Anything else that needs a real answer refuses the send with an error naming what is in the way; anything Esc closes harmlessly is dismissed regardless of the list.

`auto_dismiss_dialogs` is renamed `auto_dismiss_dialogs_at_startup` for claude, codex and pi-coding. Same behaviour; the name now says when it applies, which matters more now that a second dialog setting exists.

Claude also runs with `tui = "fullscreen"`, which pins the input bar and any dialog to the pane rather than letting them scroll out of view — so what mngr captures at send time is what is actually holding the input. tmux here runs with `alternate-screen off`, so the workspace terminal panel keeps its scrollback either way.

Claude agents now answer every dialog mngr knows a sensible answer for (`sensibly_deal_with_dialogs = ["ALL_KNOWN_DIALOGS"]`), rather than the two named model and effort switch confirmations. A dialog only becomes answerable by being given a specific option to land on, and mngr reaches it by cycling the selector onto that option rather than pressing Enter on whatever is highlighted, so opting into all of them grants no power to guess: a usage-limit prompt is answered "stop and wait for the limit to reset" and an LSP-install prompt is declined. Anything with no sensible answer still refuses to send, and anything Esc closes harmlessly is still just dismissed. The previous explicit list silently stopped covering each dialog added upstream -- a usage-limit or LSP-install prompt blocked sends outright until someone noticed.


The claude agent now opts into answering dialogs with `ALL_KNOWN_DIALOGS` rather than a wildcard: every dialog mngr can name, each answered on the option named for it, growing with the catalogue without ever becoming a guess. A dialog mngr cannot name still refuses the send rather than being guessed at, whatever the list says.

Claude agents now fall back to pressing `1` on a dialog mngr cannot name, via `sensibly_deal_with_dialogs = ["ALL_KNOWN_AND_UNKNOWN_DIALOGS"]`, instead of refusing the send. A named dialog is still answered on its own chosen option; only the unnamed case is a guess. It is chosen deliberately for a workspace: chat has no good way to show a dialog nobody has named, so refusing there strands the message until someone opens the terminal tab. The guess is bounded -- the digit is only sent to a pane actually showing a numbered selector, so it is never typed as text into whatever holds the input, and a surface that does not clear still refuses the send rather than being pressed at repeatedly. Narrowing this to `ALL_KNOWN_DIALOGS` restores refusing anything unnamed.

Fixed the model bar showing "Unrecognized model" after an agent restart. Fast mode is kept in the agent's launch settings, because Claude Code deletes the key on `/fast off` rather than writing false, so the session's own state is not recoverable from what it writes. The model is not kept there -- it is re-read from the session -- so the flag outlives the model it was chosen for. Any path that changes one without the other produces "model without fast, fast=true": a restart landing on a different model than the one you picked, or a switch onto a model that has no fast. The catalog matcher treated that pairing as an unknown model and blanked the bar, which was wrong twice over, since the model is one the catalog knows perfectly well and the flag is merely stale. Fast is no longer a matching condition; a matched model that does not support it drops the flag instead. This lives in the shared reader, so claude and codex both get it and neither carries its own repair.

A send that landed and was then blocked by a dialog now says so. mngr keeps that outcome apart from a failure -- the message was accepted, so it is recorded in `blocked_agents` rather than as a failure -- and the chat read only the failure list, so a blocked send fell through to the catch-all and reported that the agent could not be reached. That was false, and because the recovery buttons follow the failure kind, it withheld the Retry that answering the dialog makes work and offered a restart instead. The blocked outcome is now carried through in the dialog's own words, classified as a blocked input.
