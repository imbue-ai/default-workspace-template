The browser-side app contract (`system/libs/workspace_ui/src/app_contract.ts`) gains one message, `shell:new-tab`: the new-tab chord fired while a page had focus, and the module posted it rather than letting it go nowhere. Every tab is a frame, so the shell's own document only ever sees the chord pressed in its chrome; a page is where the rest of the presses land. `connectToShell` installs the listener, so every app forwards the chord without a change of its own, and an unframed page (visited directly) posts nothing and leaves the chord to the browser. The workspace app model's contract, `docs/system/blueprint/workspace-app-model/contracts.md`, documents it in section 10.

The chord itself is **not** part of that contract. A keybinding is not a protocol element, and the contract module is served cross-origin to every app page, so `workspace_ui/src/chords.ts` is the chord's home and the shell reads it from there. The contract module keeps a private copy because it is built as a standalone library entry and may import nothing; `app_contract.test.ts` replays every case the shared definition is specified against through `connectToShell` and asserts the two agree, since a silent divergence would make the chord work in app frames but not in the shell's chrome, or the reverse.

Section 12's account of how a document op treats a launcher panel is narrowed to match the dock: a New Tab is an ordinary tab and an op docks beside it, except for a launcher that is the document's only other panel, which is the stand-in the browser mints for an emptied dock and is dropped from the group the op fills. A group holding nothing but launchers still counts as an empty pane for placement, so a direction fills it rather than splitting beside it.
