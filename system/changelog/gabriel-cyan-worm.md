Bug reports carry chat transcripts again, and carry them as written. Since the collector began composing each agent's target as `name@host.provider` from its own `mngr list` output (late August), every report from a workspace said "no chat transcripts exist in this workspace": inside a container the listing names the host after the record the outer provider stamped (for example `workspace-1`), a name the workspace's own mngr did not resolve, so each fetch failed and the collector read that as no transcript. The collector now hands `mngr capture` and the transcript read a target built from ids alone, `agent-id@host-id.local`, which every mngr resolves regardless of what the host record names the host, and which still pins each call to the local provider so it never probes the cloud providers a container cannot reach. The conversations themselves are now read with `mngr transcript` rather than `mngr event`, which keeps each record exactly as the harness wrote it: the event reader overwrites a record's `source` -- the field that in a transcript names who spoke -- with the path it read the stream from, so attached chats no longer said whether the user or the agent said each line. A chat opened before mngr's ATIF cutover is the one stream `mngr transcript` refuses to read, and an agent keeps the emitter it was provisioned with, so those chats never become readable; the collector falls back to the event reader for exactly that refusal, and such a conversation attaches as it always did rather than disappearing from the report. New integration tests drive the collector against the real vendored mngr over a host dir shaped like a workspace's -- one with a current transcript, one with a pre-cutover one -- so a change in mngr's addressing, or in what it makes of a real transcript, fails there rather than in the field.
