iOS home-screen web apps for a shared workspace no longer ask for a full sign-in on every launch. The launch request of such an app can leave out the browser's `SameSite=Lax` cookies, the workspace session included, even though the session is stored and any later navigation sends it. A navigation the visitor started themselves (`Sec-Fetch-Site: none`) that arrives without a session now gets a small "Signing in..." page that loads the same URL once more from the page, which carries the session. Only if that retry still has no session is the visitor sent to sign in, exactly as before. A short-lived flag in the tab's session storage limits it to one retry, and without scripts the page goes straight to sign-in. The session cookie keeps `SameSite=Lax`, which is what stops a foreign site's plain GETs from carrying the owner's session.

The share gateway also logs every sign-in it asks for and every sign-in it completes, which is how this was diagnosed. A `Sign-in required` line says whether the visitor got the retry page or the sign-in redirect. It names, for each copy of the session cookie, whether the browser sent it and, if so, why it opened no session (expired, signed with another key, issued for another domain, malformed) along with when it was issued and expires, plus the names of the request's other cookies, its `Sec-Fetch-Dest`/`Sec-Fetch-Site`, and the browser's user agent. A `Signed in` line names the user, when the new session was issued and expires, and where the visitor lands, with the same cookie names, fetch context, and user agent. A request denied for having no session now carries the same per-copy detail. Cookie and token values never reach the log.
