Each `process_shed` line in the shed ledger now records why earlyoom picked the victim: its `oom_score_adj`, `badness_kib`, `vm_rss_kib` and the `ordering` earlyoom used (`kernel_badness`, or `upstream_fallback` when its startup self-check could not read those inputs and it chose the victim the way upstream earlyoom does). Each field is null when earlyoom did not report it, as on a workspace still running the stock earlyoom. A new drill, `bin/oom_drill.py`, checks the shed order live: it sheds memory-holding sleepers at the bands you name and fails on the first victim that was not the predicted one. The README, `OOM_DRILL.md` and `bands.py` now describe the badness earlyoom actually uses instead of `/proc/<pid>/oom_score`, which gVisor serves as 0.
