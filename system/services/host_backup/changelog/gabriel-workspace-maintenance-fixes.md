Backup retention runs again after a container is replaced mid-backup. A `restic backup` killed with its container leaves its non-exclusive lock in the repository. New backups still work alongside it, but `restic forget` and `restic prune` need an exclusive lock, and restic refuses one while any other lock exists, stale or not. The runner only cleared stale locks when a backup was blocked, which never happens in this case, so every hourly tick failed `forget` and `prune` with exit 11. Old snapshots were never thinned and the repository kept growing.

`forget`, the restore-marker age-out and `prune` now do what the backup step already did: on a lock error they run `restic unlock` and retry once. Plain `unlock` removes only stale locks: one whose process is gone on this host, or one that has not been refreshed for 30 minutes. A running restic refreshes its lock every 5 minutes, so a concurrent `host-backup-now` is left alone.
