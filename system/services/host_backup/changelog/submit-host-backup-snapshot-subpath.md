Backups now actually run on workspaces whose host volume uses the legacy layout. The service snapshots the volume every hour and then hands restic a subtree of that snapshot, and the name of that subtree was decided at startup, before any snapshot existed to check it against. It always chose `home/` -- the name the volume only has when the VPS provider sets `volume_home_path`. On a host carved without that setting the volume's top level is `host_dir/` instead, so restic was handed a path that does not exist and exited with "Fatal: all source directories/files do not exist" on every tick. Nothing surfaced it: the service stays healthy in `supervisorctl`, never crashes, and only complains into a log file, so an affected workspace looks fully backed up while having no restore point at all. On the workspace this was found on, backups had been failing for eighteen hours across seventeen consecutive ticks.

The service now discovers the layout instead of assuming it: after the snapshot is produced it looks inside for `home/`, then `host_dir/`, and reads whichever is there. `home/` is still tried first, so hosts that already worked resolve to exactly the path they resolved to before. When a snapshot contains neither, the service now fails with an error naming what the snapshot actually held, rather than passing a nonexistent path to restic and surfacing the mismatch as a restic error two steps downstream.

Worth knowing on the legacy layout: only the mngr host_dir sits on the persistent volume there, so a backup covers agent state, chat history and logs, but not `/home/user/workspace`. Backups on those hosts go from failing entirely to succeeding over a narrower tree than the whole-home coverage the service is documented to provide. Closing that gap is a provisioning-side change, not one this service can make.
