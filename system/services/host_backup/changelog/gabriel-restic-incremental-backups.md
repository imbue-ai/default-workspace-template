Hourly backups on remote workspaces no longer re-read the whole home tree. restic skips an unchanged file only when the previous snapshot holds it at the same path inside the snapshot, and each tick reads from a new timestamped snapshot path (`<mount>/snapshots/<timestamp>/home`). So no file ever matched, and every backup opened, chunked and hashed everything, even though deduplication then uploaded almost none of it. restic now runs from inside the snapshot and backs up `.`, which stores the tree at the snapshot root, with `--group-by ''` so the newest snapshot is the parent and `--ignore-inode` so files are compared by size and mtime. A local test of two ticks over the same 20 files went from re-reading all 20 to re-reading only the one that changed. The first backup after this lands still reads everything once, because its parent has the old layout.

Every restic command also runs with `GOMAXPROCS=1` and `RESTIC_READ_CONCURRENCY=1`, so a backup or prune uses one core and reads one file at a time instead of competing with the workspace's agents and UI. `nice` cannot do this on remote workspaces: gVisor accepts scheduling priorities but ignores them.

Restoring a snapshot taken after this change needs a minds app that knows the new layout (it restores from `<snapshot>:/`). An older app reports that the snapshot "does not contain a machine". Snapshots taken before the change restore as before. Downloading a new snapshot likewise gives a zip with the home tree (`workspace/`, ...) at its top level, rather than nested under the snapshot path it was read from.
