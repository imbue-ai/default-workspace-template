- New library for the web latchkey auth sandbox: the commands owner-exec runs on the Imbue Studio web chrome's behalf, thin click entry points over `imbue.mngr_latchkey.core.Latchkey` (the desktop's sign-in sequence). One key per sign-in dialog: the chrome's key `K` is the sandbox store's latchkey key and the key the credentials travel to the workspace VM under, so nothing in the sandbox re-encrypts. `auth-sandbox-prepare --session-file PATH [--describe SERVICE]` installs the session the chrome writes in one file (`K`, the machine's browser state under `K` or null, the workspace host id and the user's timezone), deletes that file, and with `--describe` prints `latchkey services info --offline`'s JSON for the service (`{}` for a service latchkey does not know). `auth-sandbox-sign-in <service> [--account A] [--fresh]` describes the service itself: one that takes typed credentials launches nothing and exits 4 printing `{"services_info": ...}`; otherwise it runs the browser sign-in (`--fresh` first removes the machine's browser state, for a new account) and prints `{"accounts": ..., "services_info": ...}`. `auth-sandbox-set-credentials` prints `{"accounts": ...}`. Both run under `K` and pin the browser's fingerprint from the session (`TILION_SEED` from the workspace host id, `TILION_TZ` from the timezone, else the region, `TILION_COUNTRY` from the region). The commands exit 0 when done, 1 when latchkey refused (its reason on stderr), 3 when a material they need is missing or malformed, the `latchkey` binary and its config included, or a file or directory of the sandbox's cannot be read or written, and 4 as above; 2 stays click's usage-error code. None of them runs `latchkey --version` (the image build checks the version).

- Sandboxes start blank, so the connector can keep a warm pool: the create environment names no user (`AUTH_SANDBOX_HOST_ID`, `AUTH_SANDBOX_CHROME_ORIGIN`, required and checked, plus `AUTH_SANDBOX_REGION` and `AUTH_SANDBOX_ID`), owner-exec starts with an empty `authorized_keys` and the Screen in gate mode with no owner token digest. The connector claims a sandbox by writing `/run/auth-sandbox-claim.json` (the user's public key, the Screen owner token's SHA-256, the session's expiry); `auth-sandbox-await-claim`, which the boot script runs, validates it, installs the key as `authorized_keys` and the digest where the Screen's gate reads it, and returns at the expiry, when the boot script stops supervisord and the sandbox ends. A claim that does not validate is logged and ignored.

- The sandbox's boot script (`sandbox/boot.sh`, installed at `/opt/auth-sandbox/boot.sh`) and supervisord configuration (the Screen service with its stack group and watcher, and owner-exec; nothing else), and the image build: its steps, and `python -m auth_sandbox.modal_image_build`, which builds the product `system/Dockerfile` into a Modal sandbox, runs them, snapshots it and prints the image id for the tier's `MINDS_AUTH_SANDBOX_IMAGE_ID` (every build-time `latchkey` invocation runs under a throwaway directory and key, since the CLI refuses to start without one and a sandbox has no keychain to mint one from); the build fails when the image's latchkey is not the version `setup_system.sh` pins, or is below the floor the library's `imbue-mngr-latchkey` enforces, rather than producing an image whose every sign-in refuses to start).

- The template `config.json` the image carries: minds' hidden built-ins and registered services plus a browser entry naming the Fortress launcher, rendered by `auth-sandbox-render-config` at image build and verified with `latchkey ensure-browser --source existing-config`.

- The sandbox is reached over Modal's own TLS (`encrypted_ports` for the Screen on 8090 and owner-exec on 8793, `unencrypted_ports` for neko's ICE TCP mux on 59000), with no share gateway, relay or certificate in it; the Screen and owner-exec listen on every interface, the boot script writes the chrome's origin to `share.env` as owner-exec's CORS origin and passes it to the Screen as its `frame-ancestors`, and the Screen reads the media tunnel's address from `/run/auth-sandbox-connect-info.json`, which the connector writes.

- The boot script exports `SCREEN_VIDEO_CODEC=vp8`, `SCREEN_FIXED_SIZE=1360x864`, `SCREEN_DESKTOP_PANEL=off` and `SCREEN_ICE_LITE=on`, so the Screen streams in a codec every browser decodes over WebRTC, Firefox included, its display stays large enough for latchkey's 1280x720 login window whatever the size of the viewer's frame, its desktop session runs without the XFCE panel, and neko runs as an ICE lite agent behind the one TCP tunnel it is reached on.

- The library is its own uv project, with its own `uv.lock`, not a member of the root workspace: the image build installs it from that lock into `/opt/auth-sandbox/venv` (on the workspace venv's Python), links the chrome's commands from there onto `PATH`, and the boot script runs the claim watcher from there. No workspace installs it.
