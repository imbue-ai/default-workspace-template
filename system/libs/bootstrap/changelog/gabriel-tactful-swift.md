Bootstrap checks for an interrupted update apply at container start (the marker under `data/.state/update-apply/`) and rolls it back before the venv converge and before any service or agent starts, via `update_self.py recover --if-stale --no-restart`. The rollback is git restores plus plain copies of the pre-apply snapshots -- no network, no package manager and no working mngr -- with one exception: an apply that had reached its provisioner step is rolled back by re-running `setup_system.sh`, which does reach the network for the pinned toolchain (forced past the content-addressed provision guard with `PROVISION_FORCE=1`, since the restored tree is the one the guard's marker was written for and an unforced run would skip). Once the venv is converged, bootstrap wakes and messages the DRI agent the marker names, best-effort, so someone verifies state and talks to the user about retrying; the wake is held until after the converge so the woken agent's `uv run` calls cannot race it. A boot-time rollback that restored the tree but could not put a pre-apply copy back (the script's exit 3, which now records an `emergency.json` for the system interface's banner) is logged as an error rather than alongside a clean rollback, and still wakes the DRI agent: the services are booting over that mismatch, which is the state that most wants a person.

Bootstrap also owns the every-5-minutes recovery cron entry, which it lays down in `/etc/cron.d` at each boot (before installing the user-editable entries under `data/.state/cron.d`, so a deliberate same-named entry still wins). It belongs at boot rather than at provision time because `/etc/cron.d` lives on the container rootfs and does not survive the container being recreated -- which is exactly the window this guard exists to cover. Composing the entry here also means the recovery script's path is spelled out once rather than twice.
