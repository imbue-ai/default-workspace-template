The live browser view is now a real low-latency video stream instead of a JPEG slideshow. Each browser runs headful under its own virtual display, captured and encoded as striped H.264 (with a JPEG fallback) over a dedicated WebSocket and decoded in your browser with WebCodecs -- smoother and more responsive, and it only encodes while someone is actually watching.

Full-fidelity interaction now works: native right-click context menus, native dropdowns and date pickers, and real click-and-drag all behave like a local browser, because your input is injected at the display level rather than into the page. The mouse pointer is rendered into the view. Escape passes through to the browser like any other key; to stop sending keys, click "Lose browser focus" (or click outside the view). The control bar shows when keys are going to the browser and has a "View tips" button that explains sharing/queuing, captcha hand-off, saved logins, and which keyboard shortcuts pass through.

Because every browser now has its own display, copy/paste no longer leaks between two open browsers, and a copy made inside the remote page (for example via right-click -> Copy) now reaches your local clipboard automatically. Copying is reliable: Ctrl/Cmd+C is driven off the keypress rather than the browser's unreliable copy event (which only fired the first time on a page), and a website's own "Copy" button works too -- the browser now grants pages clipboard access and its window holds keyboard focus, which the JS clipboard API requires.

Resizing the pane resizes the real browser window (and the capture) to match, and the view now stretches to fill its pane, so viewing a browser fullscreen fills the whole screen instead of stopping at a smaller size -- still frozen while an agent is driving and reported back to the agent on hand-back. A freshly opened browser now shows its live view immediately on first open (no more black pane until you close and reopen the tab) and fits its pane on first load, without needing a manual resize to kick it. The pane keeps its "starting" spinner up until a real video frame is actually on screen -- it never claims to be loaded before the picture is there -- and streaming is reconciled on a one-second heartbeat off the pane's real visibility, so a missed or mistimed view signal can't leave it stuck loading. While it's connected but still blank, it keeps asking the browser for a fresh frame until one paints -- so a browser that's ready but static (nothing repainting to trigger a frame) shows up on its own instead of staying blank until you reopen it. Chromium's yellow "unsupported command-line flag" banner (from the --no-sandbox we need in-container) is suppressed via a managed policy, so it no longer shows in the view. The old CDP screencast, its JPEG frames, and page-scoped input have been removed -- this stack replaces them entirely. A crashed browser now frees its virtual display and audio sink immediately (instead of holding them until you close the crashed pane), and closing a browser can no longer strand a concurrent request that was mid-flight. Closing the last tab no longer kills the browser: it reopens a fresh home tab and stays alive (the browser process is kept alive across a last-tab close), so only a genuine Chromium death shows the crash screen.

Typing is robust: a modifier combo whose key-release the browser drops (Chrome does this for letters held with Ctrl/Cmd) no longer makes the key repeat forever. Pasting an image from your clipboard into the remote browser now works even when the paste event doesn't carry the image (a common browser quirk).

The live view now has SOUND. Each browser plays into its own audio channel, which is captured and streamed alongside the video, so a video or call in a remote browser is audible in your live view -- only while you're actually watching the pane (it stops when hidden, like the video), and it starts after your first click on the page (browsers require a gesture before playing audio). Sound that isn't playing costs no bandwidth.

Opening a browser cold-starts a real headful Chromium, which takes several seconds; if the live view is still waiting on the video encoder (for example while a fresh workspace finishes installing it) the pane now says so instead of sitting on a silent "Loading page…". If your browser advertises H.264 support but can't actually decode the stream, the view now detects that no frame is painting and automatically falls back to the JPEG mode (which works everywhere) rather than staying blank. A `libs/browser/scripts/selfcheck.py` helper measures where those startup seconds actually go on a given box and reports whether the video encoder is even present.

- Adapted to main's env-converge install model: the headful display/audio runtime (Xvfb, xclip, PulseAudio + ffmpeg, pixelflux's libva*/libgbm libs, the chromium flag-warning policy) now installs via a new env.d unit `system/scripts/env.d/1010-browser-display-audio.sh` (idempotent, dpkg-based satisfied-check, no marker files), and the Playwright default-chromium symlink moved into the fortress unit as its own converge step. Headful readiness gates on the Xvfb binary instead of a deferred-install marker.

- Removed a video-encoder setting that never did anything. The capture set `video_vbv_multiplier`, described as capping the encoder's rate variability so a keyframe burst would not spike a thin connection. pixelflux only applies VBV on its constant-bitrate path; the constant-quality (CRF) path the live view actually uses ignores the value entirely, so keyframe bursts were always reaching the network unshaped. No behaviour changes -- the setting was inert -- but the comment claiming the protection is gone, so the next person does not assume the stream is rate-capped when it is not. Actually bounding burst size means opting into constant-bitrate mode, which is a real quality-versus-latency tradeoff and needs measuring first.

Live-view latency: a batch of deterministic stream fixes.

- A stripe row whose decoder loses sync (a dropped or rejected delta -- common on a jittery connection, which delivers stripes in bursts) now asks the encoder for a fresh keyframe immediately instead of showing stale pixels for up to the 2-second periodic-keyframe interval. The request is throttled on both ends (the server side caps a desync storm at ~2.5 keyframes/s) so a struggling viewer cannot make the shared encoder spend all its time on full-frame refreshes.

- The per-viewer send buffer now keeps only the newest unsent stripe per screen row instead of a fixed 64-stripe backlog. The old depth assumed many stripes per frame; on a 2-core cloud host the encoder produces 2 per frame, so 64 stripes was 1.6 seconds of stale video delivered before anything was dropped. Staleness is now bounded at about one frame no matter the host size, and dropping a stripe that would break the row's decode chain triggers the same throttled keyframe recovery as above.

- The capture rate is raised from 20 to 40 fps, and a per-browser watcher now raises it further to 60 fps while the screen is actually changing, decaying back after two quiet seconds. The capture loop is a fixed-rate tick (nothing wakes it when a pixel changes), so every screen change waited half a frame interval on average before being looked at: ~25 ms at 20 fps, ~12.5 ms at 40, ~8 ms while boosted. Encode CPU was measured at ~27% of one core during sustained scrolling on the smallest cloud workspace, so the old rate's CPU rationale no longer held; an idle page still costs near zero either way because encoding is damage-driven past capture.

- The viewer canvas opts into desynchronized rendering (skipping a compositor queue stage where the platform honors it), and a dropped video socket now reconnects immediately -- with backoff while attempts fail -- instead of waiting for the 1-second reconciliation heartbeat, which remains as the backstop.
