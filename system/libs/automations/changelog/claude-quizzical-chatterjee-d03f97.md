`run_job.sh` keeps a job's state under `data/.state/jobs/<job-id>/` again, as documented. Since the runner moved into `system/libs/automations/`, it had been writing to `system/data/.state/jobs/<job-id>/`, which git neither tracks nor ignores and the docs did not mention. On its next tick, a job with state left there moves it into place, keeping whichever copy has the later last successful run, and the empty `system/data/` directories are removed.
