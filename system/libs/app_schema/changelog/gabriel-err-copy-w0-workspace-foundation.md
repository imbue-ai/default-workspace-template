`ErrorResponse` carries three optional fields beside `detail`: `user_facing_message`, a sentence written for the person using the workspace that its frontends show as written; `routine`, whether the refusal is ordinary operation that sentence fully explains (an app still starting), so nothing is broken and the frontends offer no help with it (unset, the frontends treat the failure as owing help); and `kind`, which case of refusal it was, for a frontend that offers different controls per case. `error_response` takes all three. Each is left out of the JSON when unset, so a route that sends none answers exactly `{"detail": ...}` as before, and every route may send them without listing a richer failure model.
