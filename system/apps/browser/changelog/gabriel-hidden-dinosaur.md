- The browser daemon is no longer the first thing shed under memory pressure. It used to be tagged into the shared-browser band at the absolute ceiling (1000), above every Chromium process it manages, which made it the highest-scoring process in the entire workspace -- so earlyoom took it first in every memory-pressure episode. Shedding it frees almost nothing: measured on a real workspace with one tab open, the daemon held 125 MB while the Chromium tree it managed held 1069 MB, and killing the daemon released none of that (all 11 Chromium processes survived; the daemon restarted 13s later and re-adopted the same session). It is now tagged as an ordinary supervisord service -- the most expendable one, but far below the agents and below the browser band.

- Chromium's own processes now spread across the whole browser band instead of its bottom third, so a renderer sits at the ceiling. The re-tagging sweep maps Chrome's self-assigned gradation (browser/zygote 0, gpu/utility 200, renderers 300) into the band, but it scaled that against 0-1000 rather than Chrome's real 0-300 range, so renderers reached only 937 and the top of the band was left to processes that had merely *inherited* a high value -- never a renderer, since a renderer always self-writes. Renderers hold nearly all of a browser's memory and cost one tab to shed, so they belong at the top.
