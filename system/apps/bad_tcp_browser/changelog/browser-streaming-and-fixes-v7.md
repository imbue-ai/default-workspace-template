New app: Bad-TCP Browser -- a deliberately-naive foil to the optimized browser fleet, so the two can be run side by side to show how poorly TCP pixel streaming performs without flow control. It streams a full Chromium as damage-driven H.264 (pixelflux stripes, CPU-only) over one WebSocket with display-level Selkies input -- the same base as the fleet -- but with EVERY latency defense removed: no per-stripe credit-ack, no capture-rate adaptation, no RTT-adaptive window, no delay-gated quality. Stripes are shoved at the socket as fast as they encode, so on a congested or high-latency link the send buffers fill with reliably-delivered-but-ever-later frames and interaction latency climbs without bound -- exactly what the browser app's credit-ack prevents. Only correctness is kept (sticky-IDR resync, a newest-wins OOM-guard mailbox). Shows up as its own /service/bad-tcp-browser/ tab.
