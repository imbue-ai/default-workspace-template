Connect your browser

What the tester sees: their real, installed browsers, with the exact right one-click destination — not a search box.

under the hood

Two different claims live on this one screen. Detecting installed browsers and writing the native-messaging manifest (org.keepassxc.keepassxc_browser.json) into the right Application Support folder — that part we do ourselves, zero clicks, format and paths already confirmed. Installing the extension itself still needs a real click in the store; no API installs a browser extension unattended. What we can fix is deep-linking straight to the verified listing, instead of a search box — testing found the official extension was hard to distinguish from lookalikes.

under the hood

When the browser extension pairs, KeePassXC writes a KPXC_BROWSER_<id> key into the vault's own metadata — plain data, zero crypto. Our app already has the vault open for the list screen, so it just polls for that key. This is the one live-status claim in the deck that's fully de-risked already.

The screen we're honest we can't confirm

What the tester sees: exact instructions and a manual "I've done this" acknowledgement — not a checkmark we can't back up.

under the hood

This toggle lives inside the browser extension's own settings page — a separate, sandboxed process our native app can't read or write. We considered a companion browser extension whose only job is reporting this one bit of state back to us, and rejected it: it adds an install step, which fights the entire point of the app. So this screen guides, but doesn't verify — and we'd rather say that plainly than fake a green check.

The payoff moment

What the tester sees: a harmless practice site, then confirmation their passkey actually landed where they think it did.

under the hood

A passkey created through the extension lands in the vault as a normal entry carrying KPEX_PASSKEY_* attributes — the exact schema was decoded straight from KeePassXC's source. After the practice flow, we re-read the vault and look for a new entry whose KPEX_PASSKEY_RELYING_PARTY is webauthn.io. If it's there, we know for certain — not a guess — that it went into the vault and nowhere else.

best-effort only

The scariest finding, screen form

What the tester sees: a plain warning the moment we can't confirm success — instead of silence.

under the hood

When another passkey provider — 1Password, or Apple's own iCloud Keychain — intercepts the browser's request, KeePassXC shows no error at all; the request just goes elsewhere. We can't observe that interception directly. The best we can do is a timeout heuristic: start a short timer the moment the user approves a passkey prompt, and if the matching entry hasn't shown up in the vault a few seconds later, assume it went elsewhere and say so. It's a real safety net, but it's inference, not detection — not overclaiming this one.

Open questions for review

Four decisions this deck raises but doesn't answer on its own.

01
Stage 4 is an unproven automation claim.Worth a 30-minute spike before Phase 2 build — or should it become a guided manual step like stage 6, if the config file turns out to be off-limits?
02
Stage 6 has no verification path without a companion extension.Rejected once already for adding an install step — still the right call, or worth revisiting given how central "enable passkeys" is to the whole flow?
03
Stage 8's timeout heuristic needs a real number.How many seconds before we warn the user their passkey may have gone elsewhere? Untested — depends on how slow the real approval flow feels.
04
Tone check.This leans calm and minimal — closer to a utility than a security product. Right personality for something managing credentials, or does it need to feel more serious?
