The chat renders a secret card when an agent runs the connect-external-service skill's `request_secret.py`, modelled on the permission card. The script files the request through the new `POST /api/secret-requests`; the card shows the agent's rationale, the target `data/.secrets/<file>.env`, a note naming any existing variables a submit overwrites, one password input per variable, and Submit and Decline (with an optional note). Submit writes the file (mode 0600, POSIX single-quoted so any value survives `with_secrets.py`, merged into whatever the file already held) and sends the agent a message naming the file and the variable names; Decline sends the verdict and the note. The values reach the file and nothing else: not a log line, not the persisted request, not the transcript.

Requests persist under `data/.apps/chat/secret-requests/` so a restart keeps a pending card live; a second request for the same file supersedes the first, and only the newest accepts input (a superseded request in another chat is told by a message). The card flips from the transcript's notice, from the page's own submit, or from a status fetch after a reload, and a transcript recorded by an older backend shows an honest can't-read state.

Every harness's parser recognises the call from its input (`display: "secret_request"`) and lifts the echoed request out of its result (`secret_request`), through the one `stamp_echoed_requests` call that also lifts permission requests; the classifier reads the stored / declined / superseded notice by its tag (`display: "secret_resolution"`). The transcript walk lifts a secret request out of any open step as it does a permission request and resolves each card by its own request id.
