Phase 3 of the chat-agent split (`docs/system/blueprint/chat-agent-split/`): the chat app can read a chat that has run on several agents. Nothing creates such a chat yet (the handoff is the next phase), so nothing behaves differently for the user; the read side is in place and tested against hand-built records.

- The chat record store (`chat_records.py`): a record under `data/.apps/chat/chats/<chat-id>/record.json` names a chat's agents in order (the version-guarded, atomically written shape the accounts index uses); an in-memory store serves tests. A chat with no record is its one agent. The manager reads the records at build and resolves every chat-versus-agent crossing through them, so the two phase 2 bridging helpers (`chat_id_of_first_agent`, `first_agent_id_of_chat`) are gone.

- The instance list and the `chats_updated` snapshots show one chat per record, keyed by its first agent and listed from its active agent, with `agent_ids` in record order; an archived member is never listed (because the record names it, not because of an `archived_at` label). Status, stop, start, rename, and the pending-permission status come from the active agent; destroy runs one `mngr destroy --force` naming every member by id and then deletes the record; a re-auth restart skips archived members. An archived member disappearing from mngr leaves the chat standing.

- Multi-segment transcript reads: every harness's watcher is split into a `TranscriptLoader` (discovery, incremental reads, payload re-parsing; `HarnessSpec.loader_class`) and the watcher over it, so an archived agent's transcript is read with no thread and no filesystem watches. `ChatTranscript` reads across the segments: chat-global offsets and totals from the counts recorded on the record (the parsed count wins once a segment loads), tail, backfill, forward, and offset reads that cross segment boundaries, detail reads resolved by event id, and a lazily loaded, cached-with-the-chat loader per archived segment. The subagent routes resolve any member of the chat.

- Every event on the wire carries `agent_id`. A new chat-level `agent_switch` event sits between two agents' segments (id derived from the chat id and the retiring agent's sequence number, with `from_agent_id`, `to_agent_id`, `from_harness`, `to_harness`, `seq`); the chat page renders it as a "Switched from Claude to Codex" chip that opens the new agent's first section, and the subagent tab reads its key off the `/_instances` create response.

- Codex's position-derived fallback event ids (for a message, call, result, or turn marker codex gave no id of its own) are now derived from the line's content, so a re-read dedups and two codex agents of one chat cannot share an id.
