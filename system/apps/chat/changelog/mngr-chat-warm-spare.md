New chats start instantly. The chat app now keeps a spare agent already running on the account a new chat would use (one by default; the pool size is one constant), hidden from the chat list, and hands one to each new chat instead of starting an agent then. The chat appears at once, already running, so its first message no longer waits on "Connecting...".

- A spare counts as ready only once its harness accepts input. A new chat that arrives while a spare is still starting takes that spare, rather than starting a create that would queue behind it.

- Signing in to a provider starts the spare immediately, and a new one is started after each hand-over. With a larger pool, the refill waits while another spare is still ready so it does not slow the new chat's first turn.

- The spares follow changes to the default account, project and fast-mode setting, are replaced if their process dies, and are replaced after six hours ready, since a spare that waits that long carries the date and git state its harness loaded at start and may predate a code update. Chats created with their own name, labels, a pre-minted chat id (except one that reserved a spare, below), or a waived installation check start the way they did.

- The first chat in a workspace starts instantly too. The chat an empty chat list opens on, and one an intake mints to wait for its first message, reserve a spare that fits their account and take its name and id; the pool is topped up meanwhile. The first message then takes that spare, already running (or claims it while it starts). Sent on another account or fast mode, it has the reserved spare destroyed and starts the chat the usual way under the same id, as does a first message after the reserved spare died or waited six hours, which is when it is destroyed. Such a chat that has no spare (one opened before any sign-in, or whose spare was destroyed) has the next spare started under its own name and id, so a first chat whose user signs in from it starts instantly too. A chat left without a first message keeps its spare until the chat app restarts, which destroys it.

- A spare carries the agent label `chat_spare=true`, and every chat list hides an agent so labelled, including a chat preview (a second copy of the chat app beside the live one), which keeps no spares of its own. Handing a spare to a chat lists it at once and sets the label to false in the background, retrying on a later sweep if that fails; a preview shows the chat once the label lands. Callers cannot set `chat_spare` on a create. Nothing else about the spares is stored: after a restart, the chat app relabels an agent still labelled a spare that a chat had already taken, and destroys every other one.

- Under memory pressure a spare is shed before anything else: its label starts it, and every process it spawns, in the new `SPARE_AGENT` band (1000), above the browser's renderers, since losing it loses no work. The moment a chat takes it, it leaves the spare band, together with the processes its harness started while it waited. Once the chat's agent is up, it sits at the most protected chat level (the one a chat you are actively using sits at) for its first minute, however long it waited; after that minute it is prioritized like any chat. A spare that dies is replaced only after the five-minute backoff, so memory pressure does not churn it.
