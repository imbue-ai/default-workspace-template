Phase 10 of the workspace app model (`docs/system/blueprint/workspace-app-model/`): the chat app is its own package and program. `system/apps/chat/` holds the `chat` package (`imbue/chat/`, console script `chat-app`), moved verbatim from `system/apps/system_interface/imbue/system_interface/` (the agent manager, harnesses, accounts, sign-in flows, attachments, presence, the OOM prioritizer, the message stamps, the instances API, and the chat routes; `chat_document.py` is `server.py`, `chat_instances.py` is `instances.py`, `chat_errors.py` is `errors.py`, `SystemInterfaceState` is `ChatState`). It runs as the `chat` supervisord program from its own uv tool environment (installed by `system/scripts/build_workspace.sh` with the five mngr harness plugins `system/config/mngr_plugins.toml` now assigns to `chat` beside `mngr`), registers its manifest and port 8010 through `forward_port.py` at startup (`--no-register` skips that for a throwaway boot), and serves the chat document at `GET /<agent-id>` (with the terminal app's origin label from the registry in a meta tag), `/_instances`, every `/api/agents/...`, accounts, sign-in, uploads, lanes, and latchkey route, `/api/health` (`{"status", "is_frontend_built"}`, which the update apply polls after a restart), its own WebSocket at `/api/ws` (`agents_updated` and the proto-agent messages), and agent-authored files. Its manifest drops the `program` and `priority` carve-outs: the program is `chat` and the app runs in the `chat` memory band. `CHAT_HOST` and `CHAT_PORT` are the settings (`CHAT_JAVASCRIPT_PLUGINS` and `CHAT_STATIC_PATHS` replace the `SYSTEM_INTERFACE_` spellings).

The package has its own pytest configuration, coverage floor, `test_ratchets.py`, and CI step, and its tests moved with the code: `testing.py` builds a `ChatState` with fakes and provides `running_workspace`, the two-server fixture (the chat app and the shell served in-process on two ports over a registry) the chat's e2e tests and the shell's system tests share. `system/scripts/default_account_args.py`, `migrate_claude_auth.py`, and the scroll-verification fixture import `imbue.chat`.

The chat picks its own account. `new` launches at once on the most recently used account; with nothing signed in it mints a chat that waits for an account, and its page shows the provider chooser, whose sign-in launches the chat under the same id (`POST /api/agents/create-chat` with `agent_id`). A provisional chat has a phase (`awaiting_account`, `creating`, `failed`) that the instances API maps to `attention`, `working`, and `error`; a failed create keeps the tab with the reason (the exit status and the last lines `mngr create` printed) and a "Try again" on the same account, and deleting a waiting or failed chat drops it. The streamed creation log and its socket (`/api/proto-agents/<id>/logs`) are gone: while the create runs the page shows the composer over an empty transcript, and a message typed then is held as "Sending" until the agent registers. The page creates subagent views through its own `/_instances` and reads the terminal app's origin label from its document.

The chat page is its own frontend build: `system/apps/chat/frontend` (the old `src/chat/` plus the provider UI and the chat half of the stylesheet) builds into `imbue/chat/static/` over the shared `system/libs/workspace_ui` library, as one member of the npm workspace rooted at `system/package.json`. `test_embed_ratchets.py` holds that nothing in this frontend touches `postMessage` outside the library's boundary modules. The chat app serves its bundle's hashed assets at `/assets/<name>` and its favicon itself.

A chat that waited for an account launches on one as soon as its page finds an account signed in (a sign-in finished in another tab, a reload after one), the way `new` launches with one; a message typed while the create runs shows its "Sending" bubble on the creating page; and a create that failed while the page's socket was down settles the held message when the record is replayed. Two paths that miss a file answer a plain not-found rather than "Agent ... not found".

The chat panel takes its background from the shared token layer (the shell-only alias it named left it unstyled in the chat's own document); a send or retry to a chat the app neither lists nor is creating reaches the backend and reports its refusal instead of waiting forever; a waiting chat whose own launch on the signed-in account is refused offers "Try again" on that account beside the chooser; the instances API answers an unreadable account index with a refusal (a 409 with the reason) and a create that lands before its record is read back with the agent's own record; and the e2e suite picks free ports for both servers.

The instances API's answer for a create that lands before its record is read back (the agent's own record) and for one that vanished (a refusal) is pinned by unit tests, and the chat document's terminal-origin meta tag is tested over a registry with and without a terminal row; `document_test.py` describes the chat app's own Flask app rather than the shell's dispatcher.

The page of a chat awaiting an account waits for the account list before it launches or offers the chooser (a record replayed ahead of the accounts response no longer opens the chooser only to close it), shows the chat as starting while its own launch runs, and offers the terminal flip only once the chat's agent exists (a flip before that attached the terminal to whatever tmux session it found). The entry point's filters and `--no-register` flag are tested, relaunching a failed chat through the create route is tested, the accounts routes parse their bodies through the shared helper, and the moved prose names the chat app rather than the shell.

The page of a chat whose create failed keeps its composer under the notice, so a message held through the failure is back in it where it can be seen, and a send there is refused with the create's reason at once; a launch of a chat minted earlier that also names a `name` or `project_id` is refused (400) rather than answered with the name it was minted with; the package declares `concurrency-group`, which it imports directly.

The provisional-chat screens (waiting for the account list, the chooser offered once, the launch on the signed-in account, a refused launch with its retry, a failed create with its retry) are pinned by a unit test; a refusal a waiting page recorded is forgotten once the chat is being created, so a later failure shows only its own reason; the waiting screen's buttons drop an in-flight state they could never show; and the creation-recovery e2e suite picks free ports.

The chat frontend's dev server proxies `/_instances` to the chat app beside `/api`, so a subagent view opens under `vite dev` too; the create-chat docstring and the in-page "start a chat on this account" comment describe the `project` label as recording where a chat was started, with its tab filed by the shell that docks it.

A chat's provider menu now lets the user pin the account new chats open on: every account row carries a star, the starred account is what a launch that names no account (the New Tab tile, a rail shortcut, `layout.py open chat`) runs on, and the most recently used account only stands in while nothing is pinned. The rows are no longer greyed out: pressing an account that is not this chat's asks whether to launch a new chat on it, and does so on confirmation. The account index is at version 2 (`default_account`) and `PATCH /api/accounts/<id>` takes `is_default`.
