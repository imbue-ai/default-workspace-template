Phase 8 of the chat-agent split (`docs/system/blueprint/chat-agent-split/`): the switch is chosen in a dialog, carries a model, and shows as one node.

- Pressing another account in the composer's provider menu opens the switch dialog at once ("Switch to Codex?", one line for a rebind) instead of arming a "next" lane behind the menu. For a handoff the dialog takes the model the successor runs on. "Switch this chat" is the primary action and arms the switch: a strip above the composer says what the next message does, the model bar reads as the target, and "Switch and send" carries the switch out with no second confirmation. "Start a new chat" is secondary and opens a chat on that account and model with the draft moved over. The dialog's buttons wrap rather than overflow, and its backdrop covers the composer.

- A chat that has had no user turn skips the dialog: picking another account switches it at once, with no summary and no handoff prompt, since there is nothing to hand over. The draft stays in the composer.

- The handoff renders as one node in the transcript: "Handing off to Codex..." while it runs, "Handed off from Claude to Codex" once done, expandable to the summary turn and the handoff prompt, "Handoff called off" for a cancelled one, which it stays once another switch is confirmed rather than re-animating as that one's progress. Once the switch has landed, a rule under the node marks where the successor's segment begins. The "Asked for a handoff summary" chip and the "Switched from" chip are gone; held messages read "Sending..." like any send.

- `POST /api/chats/<chat-id>/handoff` takes `model` (model id, effort, fast); a rebind refuses one. The successor is created silent, the pick is applied through the harness's own switch path before its first message, then the handoff prompt goes to it through the send path, then the held messages. A pick the successor cannot take fails the switch at that step (`failed_step: model` on the snapshot's `handoff`): the page reads "Could not set the model on Codex", and a retry on the same account reruns only the pick and the deliveries, adopting the successor under its pre-minted id. `POST /api/chats/create` takes `model` too, for a new chat started from the dialog.

- `GET /api/accounts/<account-id>/model-options` answers what a new agent on that account could run on: the catalog for a static harness, the options the account's last agent was offered for codex.

- The handoff prompt the successor starts with carries the predecessor's summary in full, with the path it is kept at, rather than only the path, so the successor has its context before its first tool call. In the transcript it shows as a collapsed "Handoff prompt" chip inside the handoff node, after the summary turn, rather than as the user's own bubble at the top of the successor's segment. The message the user switched with, which rides inside that prompt, is shown as the successor's opening bubble under the rule: the `agent_switch` marker between the two segments carries it (`message` and `message_id`, kept on the successor's record entry), since no event of the successor's own holds it.

- The terminal back face of a chat whose agent is stopped by a switch reports the switch's phase under the chat's name ("Starting Codex...", "Restarting Claude on Anthropic 2 (Claude Code)...") instead of the retiring agent's archival name with a Start button the chat app would refuse while the chat converges.

- A step mngr refuses past a switch's point of no return (the retiring agent's archival rename, a rebind's relabel) now lands the chat in the `failed` phase with mngr's reason, so the page shows why and offers the retry, which reruns the step; before, the record kept its phase and the chat was wedged (every verb answered 409, cancel and retry were refused, sends were held) until the next restart of the chat app, as seen on a docker staging workspace.
