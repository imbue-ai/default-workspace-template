The chat app's memory prioritizer no longer re-tags every chat on the request thread of every presence heartbeat, send and lifecycle change. A heartbeat that leaves a chat as open and as visible as it was asks for nothing; an event that does change something only asks the prioritizer's one background thread for a pass, which runs at most one pass every two seconds and reads the pid registry once for all chats instead of once per chat. Previously each event ran a full pass, scanning the registry and `/proc` once per chat, with no limit on how many ran at once, so a shared workspace with dozens of open chats could pile up request threads until the chat service stopped answering. A chat's band is now written a moment after the request returns, and a pass that takes more than five seconds logs a warning.
