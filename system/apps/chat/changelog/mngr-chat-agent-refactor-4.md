Phase 4 of the chat-agent split (`docs/system/blueprint/chat-agent-split/`): the backend of the handoff, which moves a chat to another harness. Nothing in the chat page offers it yet (the UI is the next phase), so a user sees no change until then; the API and its machinery are in place and tested against a recording `mngr`.

- `POST /api/chats/<chat-id>/handoff` (body `account_id`, `message`, `message_id`, and the client fields a send carries) moves a chat to a signed-in account on another harness. The chat app drains the current agent (the stop button's interrupt, whose returned queue text comes back in the 202 answer for the composer), asks it for a summary through the new `handoff-summary` skill unless a fresh one exists under `data/.apps/chat/chats/<chat-id>/summaries/`, then stops it, archives it under `archived-<seq>-<name>-<id>` with one `mngr rename` carrying `display_name`, `chat_id`, `chat_seq`, and `archived_at`, records its segment's length, and creates the successor under a pre-minted id with the chat's name, the account's binding, the membership labels, and a first message filled in from `.agents/shared/references/continue-chat.md` (through `--message-file`). Same-harness targets are refused until the rebind lands.

- Every step is recorded on the chat record's new `handoff` entry (`chat_records.py`: phase, target, the successor's id, the held sends, the summary's outcome, the prompt, the error) and re-checked against mngr's state, so a restart of the chat app resumes an unfinished handoff from the phase it was in (`chat_handoffs.py`). A create that fails leaves the chat in the `failed` phase with mngr's reason; `POST .../handoff/retry` with an `account_id` runs the create again with the same prompt. A half-made successor from an interrupted create is destroyed and created again.

- While a chat converges it keeps listing and reading from its retiring agent, with status `working` (or `error` once the create failed); its title and name come from the handoff entry. Stop, start, rename, interrupt, the queue actions, and the model change answer 409 with the phase (the instances API's stop, start, and rename too); destroy proceeds. A send is held: answered 202 with `{"status": "held", "phase": ...}`, persisted on the record, and delivered to the successor in order once it runs; a repeated `message_id` is not held twice. `POST .../handoff/cancel` calls the handoff off while it is still draining or summarizing, returns the confirming message for the composer, and delivers the other held sends to the agent the chat stays on.

- The transcript fan-out and the SSE streams (`/api/chats/<chat-id>/stream`, the subagent streams) are keyed by chat id rather than agent id, so an open page follows the chat through the switch and receives the `agent_switch` chip the moment the successor is active.

- The `chats_updated` snapshot's `handoff` object gains `error`; the chat app's request for a summary renders as an "Asked for a handoff summary" chip.

- A delivered send to a stopped claude or pi chat marks the agent alive at once (mngr's send starts it, and the observe stream would notice only minutes later), as a codex revive already did; a handoff of a stopped chat therefore waits for the summary the revived agent writes and stops it before archiving it, instead of reading the stale lifecycle as the agent being dead.
