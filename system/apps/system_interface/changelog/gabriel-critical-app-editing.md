`app.toml` gains the shell's `[preview]` table: a preview boots `system-interface --preview --state-dir {copy:state}` over a seeded copy of `data/.state/system_interface`, reads a copied registry through `MINDS_APPS_FILE = {registry}`, and probes `/api/health`.

`system-interface --preview` boots the shell as a preview of a proposed change: the real desktop over the state directory it is given (a seeded copy) and the registry `MINDS_APPS_FILE` names. Everything that edits that copy or reaches only the preview's own windows stays live -- opening, placing, and closing windows, a refresh, the interface reload, the avatar -- so the person judging the change can use it as they would the live desktop. The two kinds of verb whose effect would land on the live workspace are refused with a 403 naming the preview: an app's stop and start (`POST /api/apps/<name>/stop` and `/start`, which act on the supervisord the live shell shares) and the update notice's confirm and roll back. The preview says `is_preview` in its inventory document, marks its page with the `system-interface-preview` meta tag, and raises no staleness banner; the frontend reads the tag and offers no Stop or Start on the window menu or a stopped window's placeholder (the store's `canStopApp` answers no in a preview).

The shell raises the update notice the careful flow's apply leaves behind. `shell/update_notice.py` reads and watches `data/.state/update-apply/last-good.json` (the record `update_self.py apply --keep-rollback-point` keeps) through the shell's shared file watch, pushes every distinct reading over the socket as `update_notice_changed` (seeded on connect, after the avatar's status), and answers `GET /api/updates/pending` (the notice, or `null`), `POST /api/updates/pending/confirm` (runs the script's `confirm-last`; `204`, `409` without a record or while a rollback is running, `500` naming a failed script) and `POST /api/updates/pending/rollback` (starts `rollback-last` detached in its own session, logging to `rollback-last.log` beside the record, and answers once the script has written its first progress; `202`, `409` while one runs, once the point was taken back, or when the script refuses, in the script's own words; launches are serialized, so two windows pressing Roll back together start one script and the other press reads its progress); a preview shell answers both verbs with its `403`. The frontend keeps the notice in the desktop state (`update_notice_changed` is a desktop event the socket delivers) and renders it as one top banner (`UpdateNoticeBanner`, beside the staleness banner) naming every app the record names ("Chat was updated a moment ago...", "Chat and the workspace interface were updated...", or "The workspace was updated..." for a change to how the workspace starts), not as a note on each touched app's windows, since the record is one rollback point and a rollback takes everything it names back together: "Roll back" asks first, naming the update, the apps (or the workspace), and the programs that restart (and warning when the restart is left to an agent), "Everything seems good" confirms, a running rollback shows its progress with no verbs, and a settled one its outcome with Close; a verb the shell refused shows its reason beside the notice for as long as the notice stays as it was, and drops it once the notice moves on (a rollback's progress arriving from another window's press). The direct-subprocess ratchet allows the one detached launch. An unknown path under `/api/` answers a JSON 404 rather than the app shell.

The README's "Updating the running UI" describes the careful flow the shell's `critical = true` routes every edit through, with `preview_app.py` in place of the removed reveal script and `--keep-rollback-point` on the apply.
