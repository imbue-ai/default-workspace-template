
Added `docs/specs/send-failure-notice.md`: a spec for showing a failed send inside the workspace instead of in a native system alert. Any send failure -- a dialog holding the agent's input, a readiness timeout, a transport error -- would open the same in-app notice the workspace already uses for declined commands, with a title, the failure text, and an OK button that Enter, Space, and Escape all dismiss. Not scoped to dialog errors, and deliberately not a harness-declared popup: those fire before a message is sent, off what the user typed, whereas this reports what the backend refused.

A send that fails now says why, inside the workspace. Previously the reason was discarded deep in the send path -- the messenger reduced mngr's result to a yes/no -- so the chat could only report "Failed to send message to agent 'Chat 2' (0 successful agents)", and it reported it through a native system alert. The harness's own words now travel to the chat, which shows them in the same notice style the workspace already uses for declined commands: a title, the reason, and an OK button that Enter, Space, Escape, and a click outside all dismiss. So a message refused because the agent is sitting on an unsubmitted shell command now says exactly that, and which keys resolve it. A failed interrupt uses the same notice. The `/welcome` resend logs the reason it failed rather than just that it did.

Specced giving that notice actions rather than only an explanation: Cancel (returns the message to the composer, prepended to any draft already there), Retry (runs the same send again), and Force (restarts the agent, then sends). Generalized deliberately -- the explanation varies per failure, the three ways out do not -- with the actions attached to the operation rather than the failure kind, so a failed interrupt, which shares this notice, still shows a single OK.

Added `docs/specs/chat-send-failure-system.md`, which maps the four layers that now decide what happens when a message does not reach an agent -- the harness-declared composer guards, mngr's send preflight and its dialog catalogue, the chat's failure notice, and the proposed recovery actions -- says which question each one can and cannot answer, and states where a given change belongs. Also records the two known rough edges: the Enter retry that can answer a picker nobody looked at, and bare `/effort` and `/model` being invisible from chat.

The failed-send notice now offers Cancel, Retry and Force instead of only an acknowledgement. Cancel returns the message to the composer, placed in front of any draft typed while the send was in flight, so neither is lost. Retry runs the ordinary send again -- useful once the user has opened the agent's terminal and dealt with whatever was in the way, which the notice now suggests. Force restarts the agent and then sends; it ends any turn in progress, so it is styled as the destructive choice and says what it does on hover. A failed interrupt, which shares this notice, still shows a single OK: the actions belong to the operation, and an interrupt has nothing to repeat.

Every notice in the chat is now one component. The overlay, the Escape key, the backdrop press and the focused first button live in one place instead of being re-typed per notice -- which they had been, and had already drifted: the agent-auth notice answered Escape not at all, and only some focused a button. A view other than the composer raises a failure through the same notice rather than a system alert, so flushing the queued messages and failing now reads exactly like failing to send, with the same Retry. Nothing in the send path opens a native dialog any more. An attachment that fails to upload also refuses the send and names the file, instead of being quietly dropped from the message.

Extended the layer map with the tmux pipeline underneath it, and with who decides which buttons a failure earns: mngr names the kind of failure, the workspace maps kinds to buttons, so a missing pane offers a restart rather than a Retry that cannot work. Also records what Retry and Force actually are, so neither drifts from the behaviour it mirrors.

A failed send now says what KIND of failure it was, and the chat offers only the recoveries that can actually work. An agent whose terminal is gone no longer offers Retry -- it would fail every time -- and says that restarting is the only way to deliver the message; a blocked input keeps Retry, because a person can clear it. mngr classifies the situation and stops there, since it has no notion of a button; the mapping from a kind to what the user is offered lives in the workspace. Anything mngr did not classify behaves exactly as before.

Force now says what it does on hover: "Restarts agent to reset it & resends message".

Fixed three ways the recovery notice could destroy what it was holding. Taking Retry or Force cleared the whole composer on success, which threw away both a draft typed while the send was failing and -- after Force -- the queued messages it had just rescued out of the agent; it now removes only the copy that was delivered. Restoring a failed message replaced the composer's attachments rather than merging, dropping anything attached while the send was in flight. And the notice component registered an Escape listener it could never remove, so every redraw left another one behind.

Force no longer leaves the message it just sent sitting in the composer. It rescues the agent's queued messages into the box before restarting, which pushed the delivered message down from the front, and the clean-up only looked at the front. A retry that fails for a different reason than the first now updates which buttons are offered, so a send that becomes unreachable mid-recovery stops offering a retry that cannot work.

Force is no longer offered while an agent is merely still starting, where restarting would discard the session it was about to finish bringing up. A retried message shows the same "sending" bubble an ordinary one does, instead of vanishing until the backend catches up. Attachments that were delivered are removed whether or not the user typed something else in the meantime -- they used to be left behind and sent again with the next message. And a failed queue flush reports the harness's own reason rather than a generic sentence.

Force no longer restarts the agent twice when it had queued messages -- rescuing those already restarts it. A failure raised from the queued-messages view now carries the same classification the composer's own failures do, so the two agree about what to offer for the same failure. An upload failure can no longer appear on a chat the user switched to while the upload was still running, and a failure raised for a chat that is never opened is dropped rather than surfacing later as a modal about something long past.
