The system interface gains an `app.toml` manifest (`internal = true`, `critical = true`, `priority = "system_interface"`), and its supervisord program registers through `forward_port.py --manifest system/apps/system_interface/app.toml` instead of `--name system_interface --no-icon`. Its registry row now carries `display_name`, `critical`, `priority`, and `program`; nothing the shell renders changes (the row was already hidden by name). The `system-interface` tool is now installed by the generic per-app loop in `system/scripts/build_workspace.sh`, with its mngr plugins looked up under its manifest name (`system_interface`) in `system/config/mngr_plugins.toml`. Phase 1 of the workspace app model (`docs/system/blueprint/workspace-app-model/`). Deregistering an app (`POST /api/apps/<name>/deregister`) now runs `forward_port.py --remove` under a plain `python3` instead of `uv run`, since the script is standard-library only.

Phase 3 of the workspace app model (the terminal app): `POST /api/terminals/notify` prefers a `terminal_id` in the body over its own lookup in `$MNGR_AGENT_STATE_DIR/commands/ttyd/clients/`. The terminal app owns the pty-to-tab records now (under `data/.state/terminal/commands/clients/`), resolves the tab id itself, and forwards each tmux hook event here with it, so live tab titles keep working until phase 7 replaces this endpoint with the generic tab route.

Phase 4 of the workspace app model (the files app): the location-beacon listener (`frontend/src/locationBeacon.ts`) accepts `{type: "shell:location", path}`, the contract's message the vendored file viewer posts now, beside the older `minds-location` spelling, which phase 7 drops together with the listener.

Phase 6 of the workspace app model (chat as a document): every chat renders inside an iframe at the registered `chat` origin, served by the system-interface process itself, and behaves as before.

- The chat pages, their bundle, and their API are a second Flask app, `imbue/system_interface/chat_document.py`, over the same state: `GET /<agent-id>` (and `/<agent-id>.<session-id>` for a subagent view) serves the new `chat.html` document with the chat's ids in meta tags; the chat routes moved off `server.py` verbatim (every `/api/agents/<id>/...` route except `destroy`, `start`, and `stop`; `create-chat`, `harnesses`, `uploads`, `claude-auth`, `accounts`, `lanes`, `latchkey`, `proto-agents`); the instances API of `contracts.md` section 4.3 is served at `/_instances` over the agent manager (`chat_instances.py`: agents, chats still being created, and subagent views as instances, with status from the activity state, a pending permission request, and the lifecycle; `503` until the agent list has been read from mngr once); and `POST /api/agents/<id>/presence` replaces the frontend's `/api/activity` reports as the OOM prioritizer's open and visible inputs (`presence.py`: per client, `visible`, `hidden`, `closed`, ten-minute expiry, a sixty-second heartbeat from the page; a subagent view posts none, since one report per chat and client is kept; the send route records `messaged`). Requests reach the chat app by path (`wsgi_dispatch.py`), never by origin label, so loopback callers such as the minds evals bridge keep working.

- The shell (`server.py`) keeps `GET /api/agents`, the three agent verbs, the projects, member, terminal, browser, app, and layout routes, and the WebSocket; it gains `GET /api/health` (`{"status", "is_frontend_built"}`) and serves the browser-side contract module at `GET /_static/app_contract.js` with `Access-Control-Allow-Origin: *`. `/api/activity` is gone.

- The agent manager nudges the shell on every agent-list broadcast (`set_nudger`; `main.py` installs a `ThreadedNudger(ShellNudger("chat"))`), reports whether its agent list is known, tracks pending permission requests per agent from the transcript events (the chat row's `attention` status), and owns the destroy path (`destroy_chat_agent`) the shell's route and the instances API share. `naming.py`'s canonical-name rule delegates to the instances library's.

- The frontend is two documents from one build: the shell (`index.html`) and the chat page (`chat.html` -> `src/chat/index.ts`), with the chat views, models, plugin API (`window.$llm`, hooks, slots), and markdown moved under `src/chat/`; the shell bundle imports nothing from there (a new check in `test_embed_ratchets.py` holds it). `src/app_contract.ts` is the app page's contract module (`connectToShell`; `contracts.md` section 10), built as its own library into `static/_static/app_contract.js`; `src/relay.ts` is the shell's child-frame boundary: the minds relay of section 11 (chat pages' permission cards reach the minds chrome through it, and the chrome's verdicts come back down) and the shell side of section 10 (`shell:handshake`, sent by `IframePanel` on every load of the frame and again when the tab or view showing the page changes, `shell:shown`, `shell:hidden`, and `shell:close-request`; `shell:focused` activates the posting frame's tab; `shell:open` docks a chat or subagent page beside it, with an optional `title` hint until phase 7; `shell:location` is logged until phase 7). A chat or subagent tab is an `IframePanel` at the chat page's URL (the chat origin, or this document's own origin when the host carries no workspace coordinate). The provider chooser, the launcher's provider picker, and the first-run greeting stay on the shell until phase 10; the chat page renders the chooser too for the model bar's "+ Add a provider".

- `system/apps/chat/app.toml` (with `icon.svg`) is the chat manifest, registered from the shell's supervisord line at the shell's own port; until phase 7 and 10 it declares `internal = true`, `program = "system_interface"`, and `priority = "system_interface"`, each with a `# CLEANUP:`. `system-interface` depends on `app-instances` and `app-manifest`.

Phase 7 of the workspace app model (the shell core): the shell is a generic window manager over apps and their instances, addressed as `app:<name>` and `app:<name>?instance=<key>`. Nothing is opened for a fresh browser: the first landing is the New Tab page, until phase 9's migration creates the starter project.

- The shell's backend is the new `imbue/system_interface/shell/` subpackage: an inventory over the registry and every app's `GET /_instances` (registry watch, liveness, coalesced nudges, a 30-second sweep, diffed `apps_updated`), the relay routes of `contracts.md` section 6 (`POST /api/apps/<name>/instances`, `.../<key>/rename|delete|location`; a key that fails the key rule is a `400` before the app is consulted; the relay waits out the slowest verb an app runs, a chat's `mngr destroy` included), stop and start for supervised, non-critical apps, projects as tab sets plus shortcuts in `data/.state/system_interface/projects.json`, per-client layouts with per-device seeds under `layouts/<view>/`, `clients.json`, the client-activity log, the generic tab route `POST /api/tabs/<tab_id>/instance` (with the `tab_rebound` broadcast), and `POST /api/client-activity`. `system-interface --state-dir` overrides the state directory. The referenced-deletion rule runs after every save and tab-set removal. `layout.py context` lists every connected client with its live view and device kind, a client that has not messaged or switched views yet included.

- Every open in a project files the address into the project's tab set, subagent pages included; "Remove from project" unfiles it; Delete goes through the app; a tab whose address the machine no longer lists is pruned on the next observation. Deleting the mounted project moves the client to the view it would land on afresh.

- The frontend has one content kind: every non-launcher panel is an iframe of an address (panel ids are minted `tab-<hex>` ids), titles, status dots, icons, and recency come from the app's records, the tab and rail menus are built from one definition keyed by the record's capabilities (`tabMenu.ts`), rail shortcuts are the project's stored shortcuts (Everything: every app's primary action), the "All apps" popover pins an action to the project's rail, and the New Tab page's tables are the tab set and the machine, each with an app filter. The per-kind models and stores (`AgentManager.ts` on the shell, `AppInstances`, `Browsers`, `MemberTitles`, `MemberLastUsed`, `MemberLocations`, `appLiveness`, `derived-names`, `objectMenu`, `locationBeacon`, `TerminalBanner`) are gone; the shell stops accepting the `minds-location` beacon spelling.

- `GET /api/agents` and the agent verbs `destroy`, `start`, and `stop` moved to the chat app (dispatched by path at the same port, so loopback callers keep working); the shell's chat "Stop" verb is gone and "Stop agent" lives in the chat page's model bar menu. Chat sends post to the shell's client-activity route; the chat keeps its own last-messaged stamps under `data/.apps/chat/` (`message_stamps.py`) for the OOM restart seed. Until phase 10, two marked carve-outs remain: the shell's WebSocket still carries `agents_updated` and the proto-agent messages for the chat pages, and the chat's `new` action takes the provider account picked beside its launcher tile (opening the chooser when nothing is signed in).

- The dock keeps every restored tab until the inventory has arrived (an empty inventory is not a reason to prune), abandons a view mount that a later switch overtook (so one view's arrangement is never saved under another's), focuses an already-docked instance on a `split` instead of docking it twice, keeps the pushed project list when the initial listing fails, reports a created instance its app never listed, normalizes a rail rename like the tab editor, resolves a `tab_rebound` push by the tab id its record carries, holds autosave until a switched-to view's content is mounted (so the outgoing arrangement is never saved under the incoming view), files an instance created for a view the user has since left into that view, lets the launcher's filter toggle close its own menu, withholds Stop and Start from a row running inside a critical app's program, as the shell does, gives an open tab of the app precedence over an instance that was active more recently but is not open when a focus-mode shortcut picks where to go, and flushes the outgoing view's pending autosave before a view switch (the flush was refused as a mid-mount save, so an edit made inside the debounce window right before a switch never reached the outgoing view's layout file). On the backend, the inventory sweep and the daily client prune outlive a failed pass, one app's lists are folded in fetch order (a sweep fetch can no longer overwrite the refetch after a create and unfile the new instance), a layout op's explicit `client` is held to the client id rule, a failed atomic state write leaves no temp file, and a chat send is reported to the client-activity log only when it names a device kind as well as a client and a view.

- Deleted routes: every `/api/terminals*`, `/api/browsers*`, `/api/member-*`, `/api/apps/instances*`, `/api/projects/members*`, `/api/projects/panels/*`, and `/api/apps/<name>/deregister`. `test_e2e.py` and `test_layout_pipeline.py` run over addresses against a stub app registered beside the chat row; `test_embed_ratchets.py` forbids the retired ref prefixes as string literals in the shell package and the frontend.

- The phase 7 shell views follow the frontend design system that landed on `delicate-adder` (`frontend/style_guide.md`): semantic colour and type tokens in the markup, the shared `Button`, `Modal`, and menu recipes under `views/components/` for the rail's row actions, the tab and launcher menus, the stopped-app placeholder's Start button, and the add-to-project dialog. The chat-specific tool-call block moved from `views/components/` to `chat/views/`, beside the expansion store it reads.


Phase 8 of the workspace app model (the layout file is the truth): a client's layout file on the shell is the truth of its arrangement, and agent ops no longer need a connected browser. The shell applies `open`, `focus`, `split`, `close`, and `move` to the target client's file itself (`shell/dockview_document.py`, a pure editor over dockview's saved document: tree-based neighbours, splits as a share of the anchor's extent, a nominal root for a never-arranged view, launcher panels dropped from the group docked into) and announces every write of a client layout, its own and a browser's, as `layout_updated {view_id, client_id, save_id}`; the owning client's windows refetch and apply it without reloading any page (pages live in the live-surface layer, so re-mounting the grid tears down slots, not pages), skip their own save ids, and record the dock's serialization after applying so two windows of different sizes never save their rescaled copies at each other. A browser's save carries a `save_id` and the `base_updated_at` it was based on and answers `{"updated_at"}`; a save over a newer stored arrangement is refused with 409 and the window takes the shell's, and a save that changes nothing is skipped; only browser saves rewrite the per-device seed, while the shell's own prunes and tab rebinds edit the seed files directly. Every op targets exactly one client (`--client`, else the client that last messaged the requesting agent, else the one connected client; otherwise a 412 naming the connected clients and never "every client"); `--view` edits that view's file and switches the client to it; `open` of an app with instances creates through the relay inside the op (`--action`, `--param`; a bare URL is the browser's `new` with `url`) and answers with the created address, so an app's refusal is the op's error; only `maximize`, `restore`, `refresh`, and the interface reload still travel to the browser as `layout_op` messages, targeted at the client's windows. The active view lives on the client record: `GET /api/clients` (with `is_connected`) is what a window reads on boot, local storage no longer holds it, `active_view_changed` is broadcast only when a stored view actually moves (a `client_state` report, a `load`, an op's `--view`), a follower reports without a previous view, and `load_layout` is gone. `GET /api/inventory` serves the document of contracts section 9 with every client's `docked` addresses. Deep links (`?view=`, `&open=`, `&action=`) are applied by the browser on load and stripped from the URL. The advisory layout mutex, the "no client on view" 412, and `layout.py`'s wait-stable polling are gone, and so are the op route's `list` and `views` ops (the script reads the inventory endpoint; the route's read ops are `inspect` and `context`). The dock root carries `data-view-id`.
