- The "Parts of this workspace were updated but not yet activated" banner no longer fires when an agent adds a new app. Building an app appends the new package to the workspace-root `pyproject.toml` (`[project].dependencies` and `[tool.uv.sources]`) and relocks `uv.lock`, and the staleness check counted both as evidence that the running system interface was serving old code. It was not: the root is not a package the system interface depends on, and adding a sibling app changes nothing it resolves. The banner then stayed up on every page load until the process happened to restart, which trained users to ignore the one variant that matters.

- The staleness check now looks only at the per-package manifests the system interface actually resolves from (`system/apps/system_interface/pyproject.toml` and the `oom_priority` / `tk_command_parsing` manifests), so a change to what this process runs still raises the banner while routine app-building does not. One case goes unreported in exchange: a root `[tool.uv.sources]` re-point, or a `[tool.uv.workspace]` members/exclude edit, that no per-package manifest accompanies. That is rare, and worth not paying a near-permanent false banner for.
