Point the composer's Opus entry at Claude Opus 5. It selects the `opus[1m]` alias, which Claude Code resolves to whichever Opus is current, so on the new 2.1.227 pin that entry serves Opus 5.

Two things had to move with it. The label read "Opus 4.8 (1M)", naming a different model than the picker actually selects. More consequentially, `harness_reported_model_id` was still `claude-opus-4-8`: `match_option` keys the live model-state read against that id, so once the statusline started reporting an Opus 5 id nothing in the catalog would have matched -- neither the reported id, nor the option id, nor the prefix-tolerance pass -- and the model bar would have fallen through to the shrug case with no model shown. Both now say Opus 5. Fast mode still applies to the entry.

A live 2.1.227 binary, launched exactly as the workspace launches it, reports `claude-opus-5[1m]` -- the `[1m]` launch suffix survives into the reported id, and reaches the Opus option through `match_option`'s prefix pass rather than by an exact key hit. The catalog docs claimed the suffix never appears in a reported id; they now say what the binary does, and a new unit test pins the three observed ids (`claude-opus-5[1m]`, `claude-sonnet-5`, `claude-haiku-4-5-20251001`) to the options they must resolve to. Only sonnet reports the bare catalog key; the other two rely on the prefix pass.
