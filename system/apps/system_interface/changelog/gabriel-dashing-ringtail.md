The app shell HTML is now served with `Cache-Control: no-store`, so reloading the interface always lands on the build that is currently on disk.

The shell is assembled per request and the assets it links are content-hashed, which makes its freshness the only thing deciding which bundle a reloaded page runs: a cached shell names the old bundle forever. A page cannot drop its own HTTP cache -- the `location.reload(true)` form is a Firefox-only extension -- so `reloadInterface` can only reload and trust the response to be fresh, and `no-store` is what makes that trust well-founded. This matters most for anyone viewing the workspace through a shared Cloudflare tunnel, where an intermediary is free to cache whatever is not marked otherwise.

The interface also now carries a *view epoch*. `system/scripts/refresh_workspace_view.py` bumps `data/.state/view_epoch` on every reveal; the server injects that value into the shell it serves and sends it on every WebSocket connect. A page whose loaded epoch is older than the one it is told about on connect reloads itself.

This is what reaches a browser that was not connected at the moment of the reveal. The reload broadcast is a live fan-out with no replay, and a services restart puts every browser on reconnect backoff (up to 30s), so the broadcast routinely fires when nobody is listening -- including for a viewer on a shared tunnel, and for anyone whose window was simply shut. The epoch is deliberately not the server's own boot id: that would reload every open page on any unrelated restart, including a crash-loop, taking unsent chat drafts with it.

Together with the helper, this is what makes a reveal of a changed interface actually visible to whoever is looking at it, instead of leaving them on the previous build until they navigate away and back.
