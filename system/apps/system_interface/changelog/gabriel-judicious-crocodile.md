Fix two chat-transcript desynchronization bugs (both reproduced live against an imbue cloud workspace), plus diagnostic logging for the investigation:

- A failed snapshot refetch during an SSE reconnect is no longer terminal: it retries with backoff until it succeeds. Previously one failed refetch (typical while the transport was still flapping) left a permanent hole in the transcript -- events emitted during the outage never appeared even though the reconnected stream kept delivering new ones, so the chat silently disagreed with the TUI.

- The transcript window can no longer freeze permanently after such a hole poisoned its offset arithmetic. A forward page that comes back empty now snaps the window's believed start to the tail (the server's authoritative "you are at the end"), so hasMoreAfter cannot stick true forever -- the state that made the client silently discard every incoming live event, spam the events endpoint with the same cursor, and show a stuck "Loading messages..." overlay until a manual page reload. Backfill/forward pages that land after the window changed are discarded (staleness fence), a non-abutting older page is rejected instead of corrupting the window (contiguity guard), and all transcript fetches carry a 30s timeout so a hung request can never pin the panel's single-fetch guard.

- Diagnostic logging: the backend logs every /api/ws connection open/close with a disconnect reason, client_state registrations and layout switches, and SSE stream open/close with a close reason; the 412 layout-op rejection logs and reports the connected-client registry. The frontend logs ([si-ws] / [si-sse] / [si-transcript] console prefixes) WebSocket open/close/reconnect, client_state sends, SSE stream lifecycle, snapshot retries, and discarded stale pages.
