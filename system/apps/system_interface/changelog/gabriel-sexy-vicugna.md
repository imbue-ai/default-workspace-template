A chat whose transcript failed to load no longer stays stuck on its error screen until the page is reloaded, it offers a Refresh right there, and the error it shows now says something.

The root: when the workspace was briefly unreachable -- a laptop waking to a tunnel that has to be re-dialled, so the proxy answers the transcript request with a 503 -- the chat recorded the failure privately and never revisited it. The tab menu's Refresh and the chat's own background reconnect both re-fetched successfully, and neither could clear it: the panel went on rendering the error over a transcript that had been fully re-synced behind it. The failure is now recorded against the agent, next to its events, so any successful reload clears it no matter who asked for one. Only the newest reload speaks for the chat, too: a request the dead tunnel held open for its full 30 seconds used to land long after a later one had already recovered the chat, and put it straight back on an error screen (or, when it came back a 404, on "No conversation data" with the live stream cut). A late reload that *succeeds* is discarded for the same reason -- letting its older snapshot land would revert the transcript to a stale window and strand everything the newer load and the live stream had placed since, with no way to page back to it.

The error screen now carries its own Refresh button. Recovering already only took one reload, but the only control that did it sat in the tab's overflow menu, which nothing about the error screen pointed at -- so a chat that was one click from working read as a dead end.

A reload that fails over a transcript that is already on screen keeps that transcript, but it no longer does so silently: it reports in a strip above the conversation, carrying the same Refresh, and clears once a reload succeeds. It used to leave no trace at all outside the browser console, which was most misleading exactly when the user had just asked for the reload themselves.

The message itself read "Error: null". A proxy 503 has no JSON body, so the request layer had no reason to report and fell through to a message that was literally the word "null". Chat and sub-agent views now both route through the shared `describeRequestError`, which was written for exactly this case but had the same hole -- an uninformative message was let through as long as it was non-empty. It now falls through to the status, so the same failure reads "Error: request failed (HTTP 503)".
