A chat whose transcript failed to load no longer stays stuck on its error screen until the page is reloaded, and the error it shows now says something.

Both had the same root: when the workspace was briefly unreachable -- a laptop waking to a tunnel that has to be re-dialled, so the proxy answers the transcript request with a 503 -- the chat recorded the failure privately and never revisited it. The tab menu's Refresh and the chat's own background reconnect both re-fetched successfully, and neither could clear it: the panel went on rendering the error over a transcript that had been fully re-synced behind it. The failure is now recorded against the agent, next to its events, so any successful reload clears it no matter who asked for one -- and a Refresh or reconnect that fails against an already-loaded transcript leaves that transcript on screen instead of blanking it. Only the newest reload speaks for the chat, too: a request the dead tunnel held open for its full 30 seconds used to land long after a later one had already recovered the chat, and put it straight back on an error screen (or, when it came back a 404, on "No conversation data" with the live stream cut).

The message itself read "Error: null". A proxy 503 has no JSON body, so the request layer had no reason to report and fell through to a message that was literally the word "null". Chat and sub-agent views now both route through the shared `describeRequestError`, which was written for exactly this case but had the same hole -- an uninformative message was let through as long as it was non-empty. It now falls through to the status, so the same failure reads "Error: request failed (HTTP 503)".
