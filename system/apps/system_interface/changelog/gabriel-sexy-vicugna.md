A chat whose transcript failed to load now recovers by itself, and the error it shows in the meantime says something.

The root of all of it: when the workspace was briefly unreachable -- a laptop waking to a tunnel that has to be re-dialled, so the proxy answers the transcript request with a 503 -- the chat recorded the failure privately and never revisited it. The tab menu's Refresh and the chat's own background reconnect both re-fetched successfully, and neither could clear it: the panel went on rendering the error over a transcript that had been fully re-synced behind it. The failure is now recorded against the agent, next to its events, so any successful reload clears it no matter who asked for one. Only the newest reload speaks for the chat, too: a request the dead tunnel held open for its full 30 seconds used to land long after a later one had already recovered the chat, and put it straight back on an error screen (or, when it came back a 404, on "No conversation data" with the live stream cut). A late reload that *succeeds* is discarded for the same reason -- letting its older snapshot land would revert the transcript to a stale window and strand everything the newer load and the live stream had placed since, with no way to page back to it.

Recovery no longer waits to be asked for. A failed load now retries on its own, on the same growing backoff the live stream reconnects with, until it succeeds or the chat is closed. Previously only a dropped stream scheduled a retry -- so the common case, where the stream itself is fine and only the transcript request lost the race with a waking tunnel, was left sitting on a dead error screen with a backend that had been answering for some time. Recovering meant picking Refresh from the tab menu, or reloading the page.

A reload that fails over a transcript that is already on screen keeps that transcript, but it no longer does so silently: it reports in a strip above the conversation, naming the failure and that a retry is running, and clears once one lands. It used to leave no trace at all outside the browser console, which was most misleading exactly when the user had just asked for the reload themselves.

The message itself read "Error: null". A proxy 503 has no JSON body, so the request layer had no reason to report and fell through to a message that was literally the word "null". Chat and sub-agent views now both route through the shared `describeRequestError`, which was written for exactly this case but had the same hole -- an uninformative message was let through as long as it was non-empty. It now falls through to the status, so the same failure reads "Error: request failed (HTTP 503)".
