Finish the Claude 2.1.227 catalog pass. The picker becomes Fable 5 / Opus 5 / Sonnet 5 / Haiku 4.5, and the catalog behind it is completed so that no model id the harness can report falls through to the shrug case.

The catalog is maintained by hand against the aliases `claude --model` accepts, and the Opus 5 pass that preceded this one only corrected entries that already existed. Reading the alias table out of the pinned binary rather than the release notes, the full set is `default`, `fable`, `fable[1m]`, `mythos`, `opus`, `opus[1m]`, `opusplan`, `opusplan[1m]`, `sonnet`, `sonnet[1m]`, `haiku`. `default` and `opusplan` stay out on purpose -- neither names a model, so neither can carry a stable `harness_reported_model_id` -- and their absence is now documented rather than merely true.

The load-bearing fix is Sonnet, which was a live bug rather than a missing model. Its entry selected the bare `sonnet` alias. In Claude Code `[1m]` is an explicit opt-in -- the binary's own help text is "append [1m] to the model name for 1M" -- so every agent switched to Sonnet was quietly running on a smaller context window than the workspace provisions, while the Opus entry beside it carried the suffix and got the full one. Every offered entry now takes `[1m]` where the alias exists: `fable[1m]`, `opus[1m]`, `sonnet[1m]`, and `haiku`, which has no such variant.

Fable took the suffix on a second pass. The first version left it bare, reasoning that 1M is already that model's default *and* its maximum so the suffix would be noise. That is an API-level property of the model; `[1m]` is a harness-level opt-in layered on top, and only the second one governs what Claude Code actually requests. The failure mode argues the same way: both forms are accepted and both answer "Set model to Fable 5", so a bare alias that silently hands back a smaller window is indistinguishable at the prompt from one that does not. Asking for 1M explicitly cannot return less.

Worth stating plainly, because it reads as contradictory: the switch alias and the reported id are different strings, and the suffix appears in both. An agent launched as `opus[1m]` reports `claude-opus-5[1m]`. `harness_reported_model_id` is nonetheless the suffix-free `claude-opus-5`, deliberately -- `match_option` treats it as a prefix, so one key matches both forms. The catalog does not need to tell them apart, because for display both are "Opus 5"; the alias is where the window is chosen.

The substantive addition is completeness. Thirteen further models are declared with `in_picker=False`: Mythos 5 and Mythos Preview, every previous-generation Opus and Sonnet 2.1.227 still carries, and bare family catch-alls. They are not decoration and not merely display -- they exist so the catalog describes the whole model surface the harness can report, which is measurable rather than a matter of taste. Every one of the 42 model ids extractable from the binary's strings now resolves to an option of the right family, pinned by two tests: one asserting nothing shrugs, and one asserting nothing resolves to the *wrong* family, since a prefix pass that mislabels everything would also report zero shrugs.

That completeness closed two real gaps. Ten ids resolved to nothing at all -- the entire Opus 4 / Sonnet 4 family, whose dated form (`claude-opus-4-20250514`) is not prefixed by its alias form (`claude-opus-4-0`), which is what the bare catch-alls now absorb. And twenty-eight more resolved only while fast was off, because `supports_fast` gates matching rather than merely rendering.

The fix for that second gap was initially to declare `supports_fast` permissively everywhere, which was wrong for the reason the hidden entries exist at all: if the catalog is a description of the model surface, an entry should say what its model actually does. It now follows the binary, which scopes fast to "Opus 5/4.8" -- so Opus 4.8 declares it and nothing else does. Opus 4.8 with fast on is a reachable state and needs the flag; 4.7 and 4.6 had fast removed, which is also why their legacy `claude-opus-4-*-fast` ids cannot arrive with fast on and are safely absorbed by their families.

Efforts deliberately do not follow that rule and stay permissive. Per-model effort support is not something the binary states plainly (Opus 4.5 takes low/medium/high, Sonnet 4.5 rejects the axis outright), the same matching gate applies, and a hidden option's effort set is never shown in a picker -- so guessing narrow trades a real shrug risk for no benefit. The asymmetry with `supports_fast` is intentional and commented at the definition.

Ordering inside the hidden set is load-bearing. `match_option`'s prefix pass takes the first key a reported id starts with, so a general key ahead of a specific one swallows it: `claude-opus-4` before `claude-opus-4-8` would label every dated Opus 4.8 as "Opus 4". Specific keys come first, family catch-alls last, and a test asserts no key precedes one it prefixes -- the trap the next person to extend the list would otherwise walk into.

Labels drop the "(1M)" Opus carried, so the picker reads as four plain model names. The window is stated once in the module docstring instead, next to the reason each entry does or does not take the suffix.

Two notes for whoever touches this next. The module carries an explicit instruction not to hand-write the model/alias/fast table into any doc, changelog or PR body: it goes stale silently and the stale copy is what people then trust, so generate it from `CLAUDE_CATALOG` at runtime instead. And two ids here are derived rather than captured from a live binary -- `claude-sonnet-5[1m]`, which follows from the suffix surviving into Opus's reported id, and Mythos's `claude-mythos-5`, taken from the binary's model table because the model is invite-only and there was no agent to launch and read.
