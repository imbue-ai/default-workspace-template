The update-staleness guard that pins "scaffolding an app must not raise the restart banner" now covers the file a scaffold actually writes. It listed `system/supervisord.conf`, which the `build-app` scaffolder no longer touches, and not the program's own `system/supervisord.conf.d/<name>.conf`, which it now writes -- so the guard's stated invariant (every file the scaffolder writes is listed here) had stopped holding. The banner's rules are unchanged and neither path raises it; what changes is that a future rule matching a drop-in would now fail here rather than in a user's workspace.
