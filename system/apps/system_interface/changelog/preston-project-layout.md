Replace named dockview layouts with **projects**: views over one machine-wide pool of objects, with a project rail, a New Tab launcher, machine-wide names and recency, and per-kind tab verbs.

The machine holds one pool of objects -- chat agents, terminal sessions, browsers, registered apps, and ad-hoc pages -- and a project is a filter over that pool plus its own dockview arrangement. Membership is an explicit, durable list of refs kept separately from the layout, and it is many-to-many: the same object can sit in any number of projects at once, nothing owns anything, and there is no "move". A member with no panel is *backgrounded* -- still running, still listed in the sidebar -- so closing a tab stops nothing and files nothing away. "Remove from project" hides an object in that one view only. **Everything is the unfiltered view, and it is the home**: not a project (no registry entry, no member list, cannot be renamed or deleted) but with its own layout, enumerating the machine, so an object filed in no project at all still appears there. An existing machine upgrades into one starter project ("Project 1") holding its whole old `desktop` arrangement, so nothing moves and nothing is lost.

Objects are singletons: **one live page per object, machine-wide**. An app open in three projects is one iframe and one document; a view decides only whether and where it is shown, never whether it is running. Switching projects, closing a tab, and re-arranging panes no longer reload or duplicate anything, because the element holding a page never leaves the DOM. Type into an app, switch to a project that does not include it, and switch back: the same page is still there, holding everything that was typed. A page is torn down only when the object behind it is destroyed. Two consequences: an app's Refresh reloads its backgrounded panes too, and a restored arrangement naming the same object twice keeps the first tab.

The old top-bar picker is gone; a **project rail** runs down the left edge, 37px at rest and expanding on hover to float over the dock. Top to bottom: the view's glyph and name (the row opens the view switcher; right-click opens project settings), shortcut rows for Chat, File Viewer, Browser, and Terminal, the project's pinned apps, a quieter "All apps" popover, a search pill that filters by label and kind with matches bolded, and the tab list itself -- open members as primary text, backgrounded ones as tertiary, each row with a hover kebab offering the verbs for its kind (Remove from project, Share app, Delete from this machine). The shortcuts go to what the view already shows and create only when it shows none; backgrounded objects count and are opened into the active pane. File Viewer renders disabled until a file-viewer app exists.

**Every project is created with a chat of its own**, opened in place of the launcher an empty view would mount, carrying the project's id in its agent's `project` label; the rail's Chat shortcut goes to that chat rather than minting another. Everything is not a project and has no chat of its own. The chat is started in the background and the project is usable either way; a failure reports its reason and points at the Chat shortcut to retry.

**Pinning an app in a project is the same fact as its membership.** The rail's app shortcuts are the project's app members in member order, and the "All apps" popover has exactly two headings -- "Pinned in <project>" and "Unpinned" -- whose toggles add or remove the member ref and nothing else. Unpinning never stops the app and touches no other project. Because it is membership, pinning is server-side and shared across browsers. Everything pins nothing (it already lists every app), so its popover is one flat list. The old per-browser `si-sidebar-app-pins` preference is not migrated; the new default shows strictly more than the old one did.

The "+" dropdown and the empty-state overlay are both replaced by a full-page **New Tab launcher** that opens as a real tab: tiles to start a chat, browser, or terminal from scratch, an "In this project" table that is the member list itself, and an "On this machine" table of everything else. Each table has a checkbox kind-filter (only kinds it actually holds, with a "Reset filters" action, and an explicit "No tabs match this filter" state) and a genuine last-active column. Opening a row from the machine table *adds* the object to the project on screen and takes it from nowhere; in Everything the launcher shows the single machine-wide table and changes no membership. The dock never goes empty -- closing the last tab opens a launcher -- clicking "+" in a pane that already has one flashes it, and a launcher folds up on its own once another panel takes focus.

Visually the dock is a set of connected tab cards: a flat grey canvas inset from the window frame, each pane a white card with a hairline border and 12px radii, and an active tab that shares its pane's outline. Every tab renders at the same width, recomputed on layout, pane, and window changes, with overflowing titles fading out rather than ellipsizing. When the strip runs out of room, the hidden tabs' dropdown lists each one as a plain row -- icon and title only, under the same friendly name the strip shows, no close or options controls -- whose whole job is to focus the tab. Workspace tooltips were restyled and retimed to match the minds shell's. Dragging a tab reads more like an edit than a selection: the drop overlay is a light neutral wash rather than dockview's opaque blue-grey slab, and dropping onto a tab draws a thin insertion line on the seam the tab would land against instead of shading half of its neighbour. Dropping into a pane still shows the filled region, since there the question really is which half of the pane you mean.

Because putting a tab away and ending the thing behind it are different acts, they wear different controls. Each tab carries a hover-revealed **minus** -- Close tab, which closes the tab and nothing else -- and a menu offering Refresh (not on terminals), Share for app tabs, Rename, Close tab, and one confirm-gated destructive verb per kind wearing an **x**: Shut down agent, Shut down terminal, Shut down browser. Those are machine-wide -- the object leaves every project at once -- and each confirmation spells out what it takes down. An app's verb is deliberately the weaker **Unregister app**: confirming calls the new `POST /api/apps/<name>/deregister`, which removes the app's row from `data/.state/apps.toml` and its member ref from every project, while the program answering on the port keeps running, because nothing in the workspace supervises it -- the confirmation and the response (`is_process_stopped: false`) both say so. A launcher tab carries only the minus, and an ad-hoc page has no destructive verb at all.

**Names and recency belong to the object, machine-wide, not to any one view's layout.** Names are keyed by ref in `workspace_layout/member_titles.json` (`GET|POST /api/member-titles`), and per-object last-used timestamps -- touched, throttled, and server-stamped whenever a tab is focused or opened -- live beside them in `member_last_used.json` (`GET|POST /api/member-last-used`). Every surface therefore agrees: the dock tab, the rail, the launcher tables, the settings dialog, and Everything all call an object the same thing and rank it the same, and changes broadcast so other clients repaint live, including views they never opened. Destroying an object drops its name and recency with it, so a reused ref never inherits a dead one.

Renaming happens from any tab: double-clicking the title (or the menu's Rename) turns it into a field -- Enter or blur commits, Escape restores, an empty name is refused -- and names the object everywhere it appears. The same double-click works in the project settings dialog's member list, where renames and removals are now *staged* and obey Save/Cancel like the rest of the form. A name the user chose wins over machine renames (a tmux session rename no longer takes a chosen name off a terminal tab), and the agent-facing `layout.py rename` goes through the same path with the same validation. **Things you create are named automatically** -- "Chat 1", "Terminal 1", "Browser 1", taking the lowest free number -- so the "New chat" and "New browser" naming dialogs are gone and machine identifiers stay internal. A hand-picked name reserves its number; destroying "Chat 1" frees the slot.

**Apps can carry their own icon.** A registry row written by `forward_port.py --icon` / `--icon-file` holds the app's SVG markup, which reaches the client with the rest of the app list and is drawn wherever the app appears -- the rail's shortcut and tab rows, the "All apps" popover, the launcher tables, and the dock tab's leading glyph. The markup is treated as untrusted at the point it enters the DOM: one DOMPurify-based sanitizer stands in front of every surface, refusing anything that could execute or reach off the page, namespacing ids per icon, and falling back whole to the generic glyph on anything doubtful; an adversarial test battery holds that rule down. An app with no icon wears its monogram in the house style -- the initial in an outlined tile, currentColor strokes on a transparent ground -- since color is the projects' identity language, not the apps'.

Storage and API: projects live under `workspace_layout/projects/<id>.json` with a `projects_meta.json` registry holding metadata, member lists, and the last-active id. Member endpoints joined the project ones: `POST /api/projects/<id>/members`, `POST /api/projects/<id>/members/remove`, `POST /api/projects/members/share`, and `GET /api/projects/members`; membership changes broadcast over the existing WebSocket. Deleting a project is confirm-gated, enumerates what it will stop, and never offers to stop anything another project still holds. Agent-driven layout ops keep working: a connected client reports its active view as its active layout, so `--layout <name>` resolves through the projects registry, `Everything` included.

Dead code from the rework is swept out: the named-layout save/load/delete dialog and its API client are gone (the layout backend stays for the migration path), along with the old "create agent" naming modal -- every create path now names things automatically.

**Shutting an object down now clears it out of Everything too.** Everything keeps its own saved arrangement but has no registry entry, so the destroy sweep used to miss its content file: reopening Everything would restore the dead tab -- and a restored terminal panel would silently respawn a fresh tmux session under the old id, wearing the raw id instead of its chosen name. The sweep now strips Everything's saved layout in the same locked pass as the projects', and clients showing the destroyed panel in any still-mounted view (Everything included) drop it live on the `project_panel_removed` broadcast instead of ignoring it, so a later autosave can no longer write the dead panel back.

The same sweep now also finds panels by the destroyed object's ref, not just by one panel id: browser and app pane ids are minted per open, so the same object sits under a different id in each view's saved file (and in each client's live dock), and a destroy used to leave those other copies behind as dead tabs. Each saved panel's params resolve to the object's one stable ref, which is what the sweep and the broadcast now match on.

Deleting a project stops its terminals and fleet browsers, and what it stops now gets the full destroy sweep too: the stopped object's panel leaves Everything's saved arrangement and every surviving project's, its ref is unfiled everywhere, and the removal is broadcast so clients still showing the tab drop it live -- previously the panel lingered in Everything and would respawn a fresh tmux session under the reused name on the next restore.
